# 2026-08-23 — 릴레이가 실어 나른 Codex 블록: 데몬이 자기 것보다 약한 값을 방송했다

### 문제

세션 브리지가 릴레이한 `usage_update` 가 Claude 퍼센트를 실으면 데몬은 그 이벤트를
**그대로** 방송했다. 계정 절반(quota, scoped caps, 구독, Codex/Ollama, `usageStale`)이
데몬의 권위 있는 집계에서 온다는 주석은 `else` 가지에만 해당했고, `hasClaudeData` 가지에서는
`codexRateLimits` 가 **브리지의 것**으로 나갔다.

세션 브리지는 설계상 호스트 프로세스를 띄우지 않으므로 `codex app-server` 경로가 없다.
패시브 rollout 읽기뿐이다. 데몬은 둘 다 가진다. 플랜에 맞는 rollout 이 **하나도 없을 때**
두 값이 갈라진다 — 데몬은 실제 창을 가진 라이브 스냅샷을 들고 있는데, 브리지는
`normalizeCodexRateLimits` 가 창 없는 블록으로 void 시킨 것을 들고 있다. 그래서 연속된
이벤트가 실제 Codex 창과 void 된 블록 사이를 **번갈아** 오갔고, 모든 표면에서 Codex 게이지가
깜빡이거나 비었다.

### 해결

- 분기 판단을 콜백에서 꺼내 `bridge/src/relayed-usage.ts` 의 `resolveRelayedUsageEvent`
  라는 순수 함수로 만들었다. 인라인 분기에는 seam 이 없어서, 이 결함이 그만큼 오래 살아남았다.
- Claude 가지에서 두 Codex 블록을 **덮어쓰지 않고 화해시킨다**. 데몬이 자기 두 읽기에
  이미 적용하는 `pickBestCodexRateLimits` 와 같은 규칙이다.
- 데몬은 자기가 **와이어에 올린** 블록을 기억한다 (`BridgeCore.lastBuiltCodexRateLimits`) —
  `buildUsage()` 의 입력이 아니라 정규화·플랜 화해까지 끝난 출력이다.

### 핵심 설계 결정

**여기서는 계정 티어를 읽지 않는다.** 두 블록 모두 각자의 생산자가 같은 `auth.json` 에 대해
이미 정규화한 것이다. void 처리는 mismatched 블록에서 `capturedAt` 을 이미 떼어냈고, 그게
바로 그 블록이 플랜 무관 newest-wins 에서 stamped 블록에 지는 이유다. 즉 `readCodexAuthStatus()`
를 이 hot path 에 새로 들일 이유가 없다 — 이슈가 상정한 것보다 싼 프리미티브가 이미 있었다.

**화해이지 덮어쓰기가 아니다.** 데몬 블록이 보통 더 낫지만 그것은 데몬의 **마지막 빌드**에서
기억된 값이다. 데몬보다 새 rollout 을 방금 읽은 브리지는 recency 로 이겨야 한다. 한쪽을
무조건 이기게 만들면 방향만 바뀐 같은 결함이 된다.

**`buildOwnUsage` 가 thunk 인 것이 계약이다.** `buildUsage()` 는 throttled `codex app-server`
스폰 게이트를 arming 하고 계정 절반 전체를 다시 유도한다. merged 가지에서만 돌아야 하는데,
Claude 가지는 데몬에서 가장 플리커에 민감한 경로이고 그 역사 전체가 "대시보드를 뭉개지 말 것"이다.
주석 대신 **시그니처**에 넣었기 때문에, 호출되지 않았음을 테스트가 단언할 수 있다.

**계측기부터 검증했다.** 새 테스트 9개 중 실제로 동작 변경을 잡는 것은 2개다 — 나머지 7개는
살아남아야 하는 불변식(뭉개지 않음, 빌드하지 않음, retain-on-absent)을 고정하므로 수정 전후
모두 green 이 맞다. 수정을 되돌려 그 2개가 red 로 떨어지는 것을 확인한 뒤에 커밋했다.

Issue #253. #252 에서 주석만 고치고 동작은 남겨둔 것을 여기서 닫는다.
