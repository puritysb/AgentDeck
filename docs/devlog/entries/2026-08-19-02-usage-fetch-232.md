# 2026-08-19 — 실패한 usage fetch 가 스스로를 신선한 것으로 세탁했다 (#232)

### 문제

"Claude 사용량이 갱신이 안 된다"로 시작했다. API 도 데몬도 멀쩡했다 — 캐시
파일이 **08:25:43 / 08:28:43 / 08:31:43**, 초 단위까지 정확히 갱신되고 있었다.
그 케이던스를 재는 것에서 결함 셋이 나왔다.

**하나. 실패한 fetch 와 살아있는 fetch 가 구별되지 않았다.** `fetchUsageFromApi`
의 모든 실패 분기(429 / 401·403 / `!res.ok` / API-error / network-throw)가
`fileCache?.data ?? null` 을 돌려줬다 — `null` 이 아니라 공유 캐시 파일의 마지막
정상 숫자를. 호출자의 `if (usage)` 는 성공 분기를 탔고, `updateApiUsage()` 가
`lastApiFetchTime = Date.now()` 를 찍고 `apiUsageStale` 을 지웠다. 결과는 전부
조용했다 — `usageStale` 와이어 플래그는 가장 흔한 실패 모드에서 **도달 불가**,
`USAGE_STALE_TTL` 은 시계가 방금 갱신됐으니 안 걸림, `fetchUsageIfStale` 의 5분
가드도 매 실패마다 리셋. 7분짜리 freeze 가 낡은 `0%` 를 `usageStale: false` 로
모든 표면에 실어 보냈다.

**둘. 폴 간격이 TTL 의 약수면 그 틱에서 캐시는 절대 만료되지 않는다.**
`fetchedAt` 은 HTTP 왕복이 **끝난 뒤** 찍히므로 120초 틱은 언제나 `120초 −
latency` 에 도착해 히트를 읽고 한 주기를 통째로 더 기다렸다. 의도한 120초 갱신이
**180초 바닥**이었다. 세 번 연속 180초가 초 단위로 일치한 게 단서였다 — 경합이면
가끔은 120초가 나와야 한다.

**셋. 위 하나를 고치자 릴레이 페이로드가 lossy 해졌다.** 실패 시 시계를 안 밀게
바꾸니 `{숫자 있음, fetchedAt: 0}` 쌍이 처음 가능해졌다 — 라이브 fetch 를 한 번도
완료하지 못한 브리지. Node 릴레이는 나이가 커져 무해하게 스킵하지만, Swift 소비자는
블록 전체를 `fetchedAt > 0` 으로 게이팅한다(#231 참조).

### 해결

`UsageFetchResult { data, fresh }` — `null` 은 "숫자가 아예 없음" 하나만 뜻한다.
`updateApiUsage(usage, fresh)` 는 stale 결과에서도 숫자는 갱신하되 시계는 건드리지
않는다. 데몬에 손으로 복붙된 apply 블록 5개는 — 옛 반환 계약 아래에서 전부 도달
불가 死코드였고 오직 운으로만 일치하고 있었다 — `core.applyUsageResult()` 하나로
접었다.

180초 바닥은 **상수가 아니라 비교**를 고쳤다: `age >= TTL − slack`, slack 15초
(실효 TTL 105초 — dedupe 가 시작했던 60초보다 여전히 훨씬 위). `index.ts` 의 PTY
브리지는 90초 폴로 같은 함정을 구조적으로 갖고 있어 60초로 정렬했다.

`/usage` 는 스탬프가 없으면 `usage: null` 을 낸다 — 소스가 등록되지 않았을 때 이미
내던 것과 **같은 모양**이라 소비자는 분기 하나면 된다.

관측성도 같이 고쳤다. 실패는 `debug()` 로만 나갔고 데몬은 `DEBUG` 없이 돈다 —
그래서 freeze 는 **어디에도 기록을 남기지 않았고 그 사유는 아직 모른다**. 캐시
파일 mtime 으로 역산해야 했다. `noteFailure`/`noteSuccess` 가 첫 실패, 이후 5회마다,
그리고 복구를 사유·백오프와 함께 남긴다.

### 핵심 설계 결정

**우아한 폴백은 자기가 폴백이라는 사실을 같이 실어야 한다.** 실패해도 그럴듯한
값을 돌려주는 설계는 그 자체로는 좋지만, 결과 종류를 반환형에 싣지 않으면 신선도
계측 전체를 무력화한다. 이건 오늘 나온 같은 계열 셋 중 하나이고, 일반화는 #230
항목의 "핵심 설계 결정"에 있다.

**캐시 TTL 은 그것을 읽는 폴 간격과 함께 정한다.** 정수배 관계면 스탬프가 왕복
후에 찍힌다는 이유만으로 항상 한 틱을 손해 본다. 값이 아니라 비교에 여유를 두는
쪽이 폴 간격이 바뀌어도 견딘다.

**릴레이 소스는 숫자와 나이를 함께 내거나 아무것도 내지 않는다.** 라이브 fetch 를
완료한 적 없는 브리지는 릴레이 소스가 아니다. 생산자에서 닫으면 소비자 둘이 다
덮인다 — #231 이 소비자 쪽도 닫았지만, 그건 방어 분기가 그 자체로 옳아야 하기
때문이지 생산자 수정을 대신해서가 아니다.

**"고쳤다"는 옛 코드가 낼 수 없는 값으로 증명한다.** 데몬 재시작 후 케이던스는
`20:24:20 → 20:26:20 → 20:28:20`, 120초가 두 번 연속 정확히. 옛 빌드는 180초를 세
번 초 단위로 찍었으므로 120초는 그 코드로 나올 수 없는 값이다. "빨라 보인다"가
아니라 그 쪽이 증거다.

**새 게이트는 수정을 되돌려 red 를 확인했다.** TTL slack 1건, 세탁 3건, 릴레이
소스 1건 — 전부 옛 코드에서 실패함을 확인한 뒤 남겼다.
