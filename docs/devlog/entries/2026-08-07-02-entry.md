# 2026-08-07 — 노브가 질문에 답한다, 그리고 데몬이 자기 포트를 잃지 않는다

### 문제

두 가지가 겹쳤다.

**(1) ESP32 는 질문을 그리기만 하고 답할 수 없었다.** ask-gate 는 답이 어떤 질문에 대한
것인지 **이름을 대지 않으면** 거부한다(`askPressVerdict`). 어떤 보드도 echo 를 싣지 않아
전부 안전하게 거부되고 있었다.

**(2) Swift 데몬이 자기 포트를 잃었다.** #141 의 hold 를 실기 검증하다 발견 — 데몬이
`Canonical port 9120 is free — reclaiming it from fallback port 9121` 를 찍고
`shutdown()` 에서 영원히 나오지 않았다. 로그가 `Daemon shutting down...` 에서 끊긴 채
리스너는 계속 서비스 중이었다. 바로 위 항목(22시간 데몬 없음)과 같은 기계장치다.

### 해결

**질문 echo — knob 만.** 네 파일 중 실제 옵션 목록을 렌더하는 건 `knob_ui` 의 `MI_OPTION`
하나뿐이다. `hud_bar` / `pocket` / `ticker` / knob `MI_APPROVE` 의 `select_option(0)` 은
managed-PTY 프롬프트용 **이진 approve 대용**이고, 4지선다에 대해서는 답이 아니라 추측이다.
거기에 echo 를 달면 추측이 "사용자가 말한 답"으로 커밋된다 — 거부되는 쪽이 정답이다.

두 개의 지뢰를 먼저 치웠다. `OUTBOX_LEN` 은 200 이라 echo 를 실으면 JSON 이 중간에서
잘려 파싱 불가가 된다(→ `Net::OUTBOUND_MAX_LEN` 320 으로 노출, `util/json.h` 이스케이퍼
추가). 그리고 `SessionSnap.question` 은 이미 `sanitizeLvglText` 를 거쳐 문장부호가
치환되고 비-한글 CJK 가 공백이 된 상태 — 그걸 echo 하면 데몬이 묻지 않은 질문 이름이 된다
(→ 원본을 락 안에서 raw 로 읽는 `rawSessionQuestion`).

**echo 는 prefix 로 매칭.** 질문은 120 **자** 상한인데 펌웨어 버퍼는 160 **바이트**다.
한국어 질문은 잘려서 도착하므로 exact match 는 "한국어 질문엔 전부 실패, 영어엔 전부 성공"
이라는 길이 의존 실패가 된다 — 기기가 고장난 것처럼 보이지 규칙으로 보이지 않는다.

**teardown 이 포트를 인질로 잡지 못하게.** `stopAll()` 은 task group 이고 task group 은
자식 전부를 기다린다 → 모듈 하나가 먹통이면 그 아래 리스너 해제에 영영 도달하지 못한다.
`withBudget` 으로 묶었다. 취소가 아니라 **포기**다 — 취소는 협조적이라 영영 resume 되지
않는 continuation 에 걸린 서브시스템은 관측하지 못한다.

**인계 핸드셰이크는 양쪽 다 경주 중이었다.** `waitForDaemonExit` 은 데몬이 *응답을 멈췄다*
는 것만 증명하지 포트가 비었다는 걸 증명하지 않는다 → CLI 가 그 틈에 bind 해서 조용히
9121 로 내려앉고 성공을 보고했다(= 9120 주인 없음). 이제 실제 bind 가능까지 기다린다
(`waitForPortBindable`). 반대편에선 `connectToExternalDaemon` 이 3.6초만 기다린 뒤
들어오는 CLI 를 stale 로 판정하고 **방금 양보한 포트를 다시 잡았다** → 스스로 연 
`yieldUntil` 창을 존중하도록 고쳤다.

### 핵심 설계 결정

- **`withBudget` 은 abandon 이지 cancel 이 아니다.** `withTaskGroup` 은 scope 이탈에서
  자식 전부를 await 하므로 먹통 자식 하나에 호출자가 같이 매달린다 — 바로 이 버그의 형태다.
- **liveness ≠ availability.** "응답 없음"과 "포트 비었음"은 다른 명제다. 사이에 소켓
  종료가 있고, `NWListener.cancel()` 은 그게 끝나기 전에 반환한다.
- **포트가 안 돌아오는 건 데몬 탓이 아닐 수 있다.** 측정 결과: 리스너가 하나도 없는데
  `bind()` 가 ~14초간 EADDRINUSE(macOS NECP 예약, `lsof` 에는 소켓 0개), 그리고 잠든
  ESP32 보드가 큐에 바이트를 남긴 채 `LAST_ACK` 로 포트를 붙든다. Network.framework 엔
  `SO_LINGER` 가 없어 RST 로 빠져나갈 방법이 없다. **그래서 CLI 는 fallback 포트로 가되
  이유를 말한다** — 조용한 fallback 이 애초에 9120 을 주인 없게 만든 원인이다.
- **손으로 미러링한 문자열 규칙은 같은 단위로 비교해야 한다.** Swift `String.count` /
  `hasPrefix` 는 grapheme cluster + 정규화 동치 기반이고 TS `.length` / `startsWith` 는
  UTF-16 code unit 이다. 기기는 UTF-8 **코드포인트** 경계에서 자르므로 grapheme 내부가
  잘린 echo 를 한쪽은 거부하고 한쪽은 수락했다 → Swift 쪽을 `.utf16` 비교로.
- **부수 발견: ObjC 예외는 Swift 에러가 아니다.** `ApmeScorers.toolKey` 가 untyped
  `input` 을 `JSONSerialization.data(withJSONObject:)` 에 그대로 넘겼고, 이건 유효한
  최상위 JSON 컨테이너가 아니면 **raise** 한다. `try?` 는 이걸 잡지 못해 백그라운드 eval
  태스크에서 앱 전체가 abort — 데몬과 모든 기기 연결이 함께 죽었다. 크래시 리포트로 발견.

### 남은 것

인계가 완전히 신뢰 가능해지려면 **WS 기기 소켓용 write-stall reaper** 가 필요하다. 지금은
읽기를 멈춘 보드에 데몬이 계속 브로드캐스트를 큐잉하고(한 보드에 11901 바이트 적체) 그
소켓이 teardown 때 포트를 붙든다. 이번엔 손대지 않았다.
