# 2026-08-08 — npm 1.0.14: tarball을 발행 머신에서 독립시키다

### 문제

npm 페이지 점검("설치 방법이 안 보인다")에서 시작해 배포 방식 자체의 결함으로 이어졌다.

**① 네 패키지 모두 README·description·keywords가 전혀 없었다** (`readmeFilename=''`).
hooks는 `repository`/`license` 필드조차 없었다.

**② tarball 내용이 발행한 머신에 따라 달라졌다.** bridge의 `prepack`이
`assets/fm-helper/agentdeck-fm-helper`(gitignored, arch 전용, ad-hoc 서명 Mach-O)를
발행 머신에서 구워 넣었다. 1.0.13은 arm64 Mac에서 발행되어 **arm64 전용 바이너리**를
실었고, Intel Mac에서 발행하면 x86_64가, CI ubuntu에서 발행하면 **아무것도** 실리지
않는다(files 항목 부재는 npm이 조용히 건너뜀). 같은 버전 번호가 세 가지 산출물이 되는
구조였고, CI 발행(NPM_PUBLISH_ENABLED)을 켜는 순간 지뢰가 터질 예정이었다.

**③ 소비 측도 그레이스풀하지 않았다.** `resolveFoundationModelsHelper`는 arch 검사가
없어서 Intel Mac이 1.0.13의 arm64 바이너리를 그대로 spawn → `EBADARCH`로 죽고,
해석이 이미 그 경로에 커밋된 뒤라 소스 컴파일 폴백은 영영 돌지 않았다.

### 해결

- **결정적 tarball**: `prepack` 제거, files에서 `assets/fm-helper` 제거. 헬퍼는 Swift
  소스 + 빌드 스크립트로만 실리고 데몬이 첫 사용 시 `~/.agentdeck/fm-helper/`로
  온디맨드 컴파일한다(macOS 26+, Xcode CLT 필요 — 실패 시 사유에 설치 안내 포함).
- **arch 게이트**: `machoMatchesArch`(thin/fat 헤더 파싱)를 env override·dev 트리
  bundled·캐시 세 경로 모두에 적용. 다른 CPU용 바이너리는 spawn 대신 재컴파일.
  env override의 arch 불일치는 조용한 폴백이 아니라 명시적 거부(의도 선언이므로).
- **게이트**: `fm-helper-arch.test.ts` — Mach-O 판정 + "files에 assets/fm-helper 금지,
  prepack 금지, 소스+스크립트 필수" 패키징 불변식.
- **메타데이터**: 4패키지 README 신규(환경별 설치 절차 포함, npm은 상대링크가 깨지므로
  절대 URL만), `description`/`homepage`/`keywords`/`engines>=22` 추가.
- RELEASING.md npm 섹션에 머신 독립 불변식 명문화, docs/voice-setup.md에 온디맨드
  컴파일 경로 추가.

교훈: **발행 수명주기 훅(prepack)에서 머신 상태에 의존하는 아티팩트를 굽지 말 것.**
"내 머신에서 발행하면 잘 된다"는 발행자가 한 명일 때만 성립하는 암묵 전제다.

### 후기 — 1.0.15: pnpm publish는 README를 packument에 안 싣는다

1.0.14를 `pnpm --filter publish`로 내보낸 뒤 npm 페이지가 여전히 비어 있었다.
tarball **안에는** README.md가 있는데 레지스트리 packument의 `readme` 필드가 빈
문자열 — npmjs.com은 packument를 렌더링하므로 페이지에는 아무것도 안 뜬다(비교:
vite packument에는 readme 본문이 실려 있음. pnpm 11.5.2에서 검증). 해결은
`scripts/publish-npm.mjs`: 각 패키지 **디렉토리에서 `npm publish`** 를 실행하고
(디렉토리 발행만 read-package-json이 readme를 manifest에 채운다), pnpm이 해주던
`workspace:*` → 구체 버전 재작성은 발행 전후 write/restore로 대신한다. 수동 발행과
npm-release.yml CI 발행이 같은 스크립트를 타도록 워크플로도 교체. 1.0.14는 레지스트리에
남는 중간 버전(immutable)이고 공식 태그는 npm-v1.0.15만 만든다.

### 문제

D200H VOICE 키를 누르면 녹음은 시작되는데 세션에 아무것도 들어오지 않았다.
Stream Deck 은 잘 됐다. 원인은 **서로 다른 층의 버그 두 개**였고, 하나만 고쳤다면
증상은 그대로였다.

**① 헬퍼 read loop 의 head-of-line 블로킹.** 헬퍼는 프로세스 하나가 stdin 으로 모든
요청을 받는다. `record` 는 응답이 나중 `record_stop` 줄까지 지연되므로 이미
`Task.detached` 였지만, `generate`/`transcribe`/`speak`/`synthesize` 는 **읽기 루프
위에서** 돌았다. LLM 호출이 도는 동안엔 다음 줄을 *읽지조차* 못하므로 그 뒤에 줄선
`record_stop` 이 통째로 대기했다. 헬퍼를 직접 구동해 측정:

    +0.3s  record / +1.0s generate / +2.0s record_stop(무시)
    +25.2s generate 응답 → 그제서야 {"stopped":true} → +25.3s 녹음 종료(24초 캡처)

데몬은 타임라인 요약·APME 심판을 상시 돌리므로 stop 이 그 틈에 떨어지면 30초 상한까지
녹음되고, 대부분 침묵인 30초를 전사해 빈 결과가 나온다. **SD 가 "잘 되던" 것도 운이었다**
— 두 데크는 동일한 `{type:'voice',action:'stop'}` 을 보내고, 성패는 그 순간 데몬이 LLM
작업 중이었는지에만 달려 있었다. 갓 재시작한 데몬에선 항상 성공한다.

**② D200H 키가 탭 토글이었다.** stop 이 "데몬의 `voice_state` 가 돌아와 타일이 다시
칠해져야" 나가는 구조라, SD 손버릇대로 **누르고 있으면** 아무것도 안 나갔다. 실기 로그:

    17:35:10.399 keydown / 17:35:10.401 press→voice(start) / 17:35:13.298 keyUp(무시)
    (두 번째 프레스 없음 → 30초 상한 → 미전달)

같은 로그가 토글의 전제도 깨뜨렸다 — keydown/keyUp 은 진짜 타이밍으로 도착한다
(down→run 2ms, keyUp 은 실제 뗀 시점). "단일 `run` 이라 홀드는 표현 불가"가 틀렸다.

### 해결

읽기 루프는 파싱·디스패치만 하고 느린 작업은 `WorkQueue` actor 로 내렸다(직렬성은
루프가 주던 그대로 유지). D200H VOICE 는 keydown/keyUp 쌍으로 구동하고 `run` 은 그 키만
건너뛴다 — stop 이 타일 상태에서 분리된다. `voice-ptt.ts` 는 재구현 대신 `shared` 로
승격해 두 데크가 한 상태기계를 쓴다(<250ms 탭=cancel 포함). 홀드 중 키가 사라지면
`onClear` 에서 cancel. 타일 문구도 동작에 맞췄다(`hold to talk` / `● listening`), Swift
프리뷰 미러까지 포팅하고 SYNC-HASH 재핀.

진단 구멍 셋도 함께 막았다: `stopHelperRecording()` 의 rejection 을 삼키던
`.catch(() => {})`, 빈 전사가 전달 블록과 **그 로그까지** 건너뛰던 경로, 그리고
`daemon restart` 가 `stdio:'ignore'` 로 떠서 **모든 로그를 /dev/null 로 보내던** 것
(`daemon start` 는 처음부터 회전 로그 파일을 썼다 — 이 불일치가 오늘 진단을 몇 시간
지연시켰다).

### 교훈

**"A 는 되고 B 는 안 된다"는 A 가 멀쩡하다는 뜻이 아니다.** SD 가 잘 된다는 사실이
"데몬·헬퍼는 무죄"로 읽혀 D200H 쪽만 파게 만들었지만, 실제로는 SD 도 같은 지뢰를
밟고 있었고 타이밍이 맞아 살아났을 뿐이었다. 두 표면이 **같은 와이어 명령**을 보낸다면
차이는 표면이 아니라 **그 순간의 서버 상태**일 수 있다 — 명령 모양을 비교해 동일함을
확인한 시점에서 공용 경로를 의심했어야 했다.

**그리고 화면에 안 보인다고 없는 게 아니다.** 이번 조사에서 "openView 가 동작 안 한다"
(창이 Studio 뒤에 있었다), "Studio 가 PI 를 캐시한다"(패널이 짧은 스크롤 뷰포트였다),
"TTS 무장이 어긋난다"(다른 세션 응답이 정상적으로 걸러진 것) — 세 번을 오판했고 셋 다
뷰포트·z-order·로그 끝까지 읽기로 즉시 반증됐다.

검증: 헬퍼 단독 재현(2.0s 즉시 stop), 데몬 경로 LLM 부하 중 stop 즉시, 실기 D200H
홀드→발화→릴리스 →
`voice: "안녕 반가워" -> observed:claude:aa5bb152 delivered=true via iterm2`,
낭독까지 확인. vitest 169파일 2727테스트 green.
