# 2026-10-25 — Attention requires a user wait across agent sources

The follow-up to the [Codex automatic-review incident](docs/devlog/entries/2026-10-25-codex-auto-review-attention.md) found two Claude sources with the same evidence error. The PreToolUse predictor treated an unlisted command, or an ask rule, as a human decision before Claude evaluated session approvals, sandbox policy and other hooks. That created a 25-second device hold itself. PermissionRequest was also displayed immediately although [Claude's current hook contract](https://code.claude.com/docs/en/hooks#permissionrequest) explicitly includes calls that will be denied headlessly and calls decided by hooks or SDK hosts. The [October 19 incident](docs/devlog/entries/2026-10-19-claude-permission-request-and-windows-hook-answers.md) had recorded the brief headless false prompt as a known limit.

Both daemons now keep those signals passive. Attention comes from the actual waiting permission_prompt Notification, normally about six seconds after the dialog appears. This delay is the cost of a signal that distinguishes a human wait from automatic handling. Permission policy and Claude hook decisions are unchanged. Predicted Allow/Deny holds are retired; real permission dialogs use the terminal. AskUserQuestion retains its structured choices, device answers and bounded hold. The old predictor/matcher API remains compatible and generated, but never authorizes a hold. Unknown agents or tools cannot re-enable speculation.

The managed Claude/monitor and dedicated Codex PTY fallbacks also matched permission words anywhere in command output. Quoted `Always allow`, `Yes, allow once` and `(y/n)` examples could emit permission_prompt. Matching now requires a choice line or the yes/no affordance at the end of a line; existing numbered, cursored and boxed choices stay covered. Short unmarked numbered response lists also triggered option_prompt; they now require a selection marker or an already confirmed interactive prompt. Legacy cursorless redraw fixtures are exercised only after that real prompt context. Legacy untyped Notification matching accepts only Claude's anchored permission sentence rather than arbitrary status prose.

Source audit:

| Agent path | Evidence for Attention | Result |
| --- | --- | --- |
| Claude observed, Node + Swift | Waiting permission_prompt; structured AskUserQuestion | Remove speculative permission hold and early PermissionRequest display |
| Codex observed, Node + Swift | PermissionRequest plus latest reviewer evidence | Existing explicit auto_review suppression retained |
| OpenCode observer + SSE | Pending permission/question event with request ID; reply/reject/turn end clears | No command-based approval prediction found; existing lifecycle coverage retained |
| OpenClaw Gateway | Pending exec/plugin approval ID; resolve, expiry, list reconciliation, disconnect | No command-based approval prediction found; existing lifetime coverage retained |
| Kiro, Antigravity, Hermes observed | No permission-wait producer | No invented approval state found; this does not claim unsupported approval detection |
| Managed Claude/monitor PTY | Rendered permission choices | Narrow substring matching; preserve real choice fixtures |
| Managed Codex PTY | Codex's dedicated prompt parser | Anchor approval affordance lines; reject quoted prompts and policy prose |

The audit is source and regression evidence, not a claim of interactive runtime acceptance for every installed agent or device. A printed example identical to a real terminal prompt remains inherently ambiguous in the legacy PTY path; daemon-first structured sources avoid that ambiguity. No new parser dependency or managed-session capability is introduced.

Runtime evidence: the installed Claude Code **2.1.309** was exercised with an isolated config directory and a local synthetic Anthropic endpoint (no external model call). A single harmless Bash tool call in `-p --permission-mode default` emitted PreToolUse and PermissionRequest, then finished with no waiting Notification. In a second run, a PermissionRequest hook answered allow automatically: the same two events were followed by PostToolUse, again with no waiting Notification. Neither path offered a human choice. The isolated Node daemon E2E test replays both pre-wait signals without an awaiting frame, confirms a waiting Notification does show Attention and tool progress clears it, and checks the installed notification hook prints no decision. Swift runs the generated passive policy and the corresponding display predicate tests; this is not an interactive Swift-app acceptance claim.

Verification pitfall: while universal optimized Xcode builds were consuming both compiler workers, the existing WebSocket auth tests intermittently interpreted the open handshake as admission before the close frame arrived. Their helpers return success on a 50/60 ms timer. The focused tests passed; the complete Vitest suite with four workers passed 6,823 tests (17 skipped). No auth implementation or timeout was changed for this Attention fix. Preserve this distinction if the timing failure recurs under build load.
