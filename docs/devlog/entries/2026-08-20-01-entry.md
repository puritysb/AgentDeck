# 2026-08-20 — 성공을 보고하는 폴백과, 화면을 안 봐도 되는 줄 알았던 이유

### 문제

t_display_pro 한 대가 하루째 1.0.3 에 멈춰 있었다. 전 세션이 라이브 WiFi OTA 를
두 번 실패한 뒤 문서화된 절차대로 `--stage`(pull OTA) 로 우회했고, CLI 는
`Staged for 192.168.68.74` 로 **성공을 보고했다**. 그런데 하루 뒤에도 보드는 그대로였다.

같은 날 두 번째 문제. 2026-08-17 커밋 #217 이 Kiro 를 여섯 표면에 그리도록 배선하면서
스스로 이렇게 적어뒀다 — "NOT visually verified — 여섯 보드가 전부 시리얼 연결이라
WebSocket 이 parked 되고 WiFi OTA 가 불가능하다. 이것은 컴파일되는 코드지, 누가 본
화면이 아니다."

### 해결

**`--stage` 는 이 트리의 보드에 대해 구조적으로 무의미했다.** 두 겹이었고 각각
단독으로 충분했다. ① `stageEsp32Fw` 가 **raw target 을 그대로 맵 키로** 썼다 —
같은 board 2대를 구분하려면 IP 로 지목하라는 것이 문서화된 절차인데, 조회는
`stagedFwAdvert(device_info.board)` 로 하므로 만날 수 없는 짝이 된다. ② 애초에
`grep -rl "/feed" esp32/src` 는 비어 있다. pull 클라이언트는 외부 XTeink 포크에만
있고 이 트리의 보드는 전부 상시 WS 라 feed 를 당기지 않는다 — 데몬 실측도
`card-feed: {clients: [], recent: []}` 였다. 키를 board 로 정규화하고, feed pull 이
관측되지 않은 보드에는 CLI 가 경고를 내도록 했다(#234).

**보드는 시리얼 플래시로 해결했다.** 라이브 OTA 3회 실패 → stage 2회 무의미 →
시리얼 1회 성공.

**그리고 "화면을 못 본다"는 전제가 틀렸다.** `esp32/sim` 은 펌웨어 렌더 소스를
각 보드의 실제 해상도로 그대로 컴파일해 PNG 를 낸다 — 보드도 플래시도 필요 없다.
`./render.sh ips10 demo:kiro:idle` 한 번에 결함이 나왔다: **카드 헤더가 Kiro
세션을 `Agent` 라고 부르는데, 같은 화면 왼쪽 책상은 `Kiro` 라고 쓰여 있었다**(#235).
게다가 #217 의 코드는 **이미 플릿에 올라가 있었다**(`fc64cc3a` 트리에 `kiro.cpp`
포함) — 플래시는 처음부터 육안 검증을 막고 있던 요인이 아니었다.

원인은 `hud_bar.cpp` 가 `agent_label.h`(주석에 "IPS10 mosaic card" 를 소비자로
명시)를 include 해놓고 그 위에 **같은 맵의 사본**을 선언한 것. Kiro 이전에 쓰였고
갱신되지 않았다. `default` 가 있는 라벨 맵은 전역적으로 성립하므로 — 모든 입력이
무언가를 반환하므로 — 컴파일러도 테스트도 잡을 수 없었다.

이어서 Kiro 문서 감사를 하니 코드는 다 돼 있는데 문서만 멈춰 있었고, 그 밑에
**브랜드 색 토큰 자체가 없었다**(#238).

### 핵심 설계 결정

- **"staged" 는 전송도 설치도 증명하지 않는다.** 성공 보고에 `pullSeen` 을 실어
  보내고, 관측된 적 없으면 CLI 가 경고한다. 데몬 생존 기간 상태이므로 `false` 는
  "이 데몬 시작 이후 본 적 없다"이지 "당길 수 없다"가 아니다 — `capturedAt` 과
  같은 규칙으로, 모른다는 것은 그 자체로 하나의 답이지 부정의 약한 형태가 아니다.
- **IP 타깃은 거부할 대상이 아니라 정규화할 대상이다.** `findWifiOtaTarget` 이
  ambiguous 에러로 사용자를 IP 로 보내놓고 stage 가 그 IP 를 키로 쓰면 안 된다.
  단 `resolveStagedFwBoard` 는 `findWifiOtaTarget` 과 달리 **열린 소켓을 요구하지
  않는다** — 소켓을 안 가지는 보드가 staging 의 존재 이유이기 때문이다.
- **"보드가 시리얼이라 화면을 못 봤다"는 유효한 사유가 아니다.** 시뮬레이터가
  같은 소스를 같은 해상도로 굽는다. 앞으로 렌더 변경의 미검증 사유로 쓰지 말 것.
- **SSOT 를 include 하고 그 위에 로컬 사본을 두면 아무도 경고하지 않는다.**
  새 에이전트를 넣을 때 `grep -rn '"Agent"' esp32/src/` 로 손복제본을 먼저 훑는다.
  남은 사본이라 적었던 `office.cpp` 의 `agentShort()` 는 **호출부가 없다** —
  파일 생성(#16) 이래 한 번도 불린 적이 없고, 그래서 SSOT 와 이미 어긋나 있어도
  (`monitor`/`daemon`/미지 id 를 전부 `"Agent"` 로 뭉갠다) 화면에는 아무 영향이
  없었다. 접을 대상이 아니라 지울 대상이었다(#240). 사본은 렌더러가 읽는지부터
  확인하고 판정할 것 — 안 읽히는 사본은 정확해 보여도 정확한지 아무도 모른다.
- **플래시 여부는 커밋 목록이 아니라 net 트리 diff 로 판정한다.** squash 머지
  때문에 `git log <boardHash>..HEAD` 는 이미 내용이 들어있는 커밋도 보여준다.
  `git diff <boardHash>..HEAD -- esp32/src/` 로 파일을 뽑고, 그 파일이 어느 pio
  env 에 컴파일되는지 `build_src_filter` 로 확인한다. 이 기준으로 7대 중 4대만
  실질 델타가 있었고, 나머지는 버전 문자열만 달랐다 — 데몬 종료를 동반하는
  시리얼 플래시를 근거 없이 하면 순손실이다.
- **버전이 같은데 buildHash 가 갈리면 그게 드리프트다.** ttgo 를 굽기 직전
  이미지가 태그(`1e974271`)가 아니라 그 위 README 머지분을 물고 있는 걸 발견했다.
  릴리스 태그에서 worktree 로 다시 빌드했고, 결과적으로 1.0.6 네 대가 모두 같은
  해시를 보고한다.
- **에이전트 지원 표면에는 문서와 토큰도 포함된다.** 특히 심사관에게 가는
  `APP_REVIEW_NOTES.md` — 앱이 `~/.kiro` 를 폴더 권한으로 읽는데 그 열거에
  Kiro 가 없었다. **폴더 접근 권한은 훅 설치보다 강한 고지**라 누락은 앱이 하는
  일을 축소 진술하는 것이 된다. 그리고 `design/tokens.css` 에 Kiro(#7C3AED)와
  Antigravity(#5F6368) 브랜드 색이 아예 없었다 — DESIGN.md §6 이 #5F6368 을
  허용 색으로 인용하면서 정작 그 규칙이 가리키는 파일엔 없는 상태였다. 순서가
  중요하다: 토큰 → 미러 7곳 → 뷰어 카운트 → 페이지. 반대로 하면 색 없는
  크리처가 나간다.
- **로컬 산출물로 Pages 를 판정하지 않는다.** 크리처 시뮬레이터 프레임은
  gitignore 된 빌드물이라 로컬은 201개(kiro 0)였지만 **라이브는 240개(kiro 포함)**
  였다. 판정은 `curl .../demo/sim-frames/manifest.json`.
