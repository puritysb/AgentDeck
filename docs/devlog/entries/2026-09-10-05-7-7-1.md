### 분류기 순서를 뒤집은 이유

워커는 40개 실제 task 측정으로 `foundationModels → mlx → rules` 를 골랐다. 표는 FM 16/40 완료·룰
일치 5/15, MLX 7/40 완료·1/7. 이걸로 순위를 정할 수 없다고 판단했다: (1) 그날 MLX 서버에 27B 모델이
올라가 있어 15초 예산은 서버 부하를 쟀다, (2) 살아남은 표본 15 대 7, (3) "룰과 일치"는 정확도가
아니다 — 룰은 LLM 이 개선해야 할 대상이다. 그래서 **기존 결과를 가장 적게 바꾸는 순서**로:
`mlx`(Node 의 원래 유일 레그, 프롬프트 보정 대상) → `foundationModels`(MLX 서버 없는 Mac 의 폴백 —
오너의 "대부분 Mac 에 기본" 요구) → `rules`. 측정 노트는 "불충분"으로 기록하고 재측정 조건(평소
모델·양쪽이 맞출 예산·오너 라벨 정답)을 적어뒀다. 워커의 한 Swift 벡터가 "mlx 가 첫째일 때만" 으로
self-skip 하고 있었는데 이제 돈다.

### 머지 순서와 충돌

로테이션 → #307 → #272 → 사다리 → #302 → 분류기. 마지막 머지에서 4파일 충돌: 분류기 워커가
사다리 머지 **이전** 시점에서 분기해 `ApmeJudgeMlx.swift` 의 옛 본문(억제 메모리 포함)을 들고
있었다. 해소 규칙: 사다리(HEAD) 유지 + 분류기의 새 진입점(`classifyTaskCategory`)만 가져오기,
`classifier.ts` 는 두 워커의 import 합집합(prune 의 `isPrunedPayload` + 공유 규칙). 머지 후 게이트:
vitest 4,291 · XCTest 803.

### 실기·부작용

- 워커가 전체 XCTest 를 돌리자 테스트 프로세스가 실제 앱 컨테이너의 로거를 띄워 **프로덕션
  518MB 로그가 실제로 회전됐다**(`.1` 에 보존, 유실 없음). 그 로그의 98% 가 DEBUG 줄이다.
