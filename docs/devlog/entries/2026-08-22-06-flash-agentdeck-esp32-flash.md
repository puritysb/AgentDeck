# 2026-08-22 — 그 펌웨어에 닿는 길을 냈다: `/flash/` 웹 플래셔 + `agentdeck esp32 flash`

앞 항목이 **merged factory image 와 `manifest.json` 을 만들어 둔 상태**에서 멈춰 있었다.
쓸 물건은 생겼는데 그걸 쓰는 도구가 없었다. 이 항목이 Phase 3·4·5 — 브라우저 표면,
CLI, 문서 — 이다.

### 브라우저가 릴리스 에셋을 못 읽는다는 사실이 배포 구조를 결정했다

GitHub Release 에셋에는 **CORS 헤더가 없다**(302·200 양쪽 모두 `access-control-allow-origin`
부재, 실측). 즉 웹 플래셔는 펌웨어를 **동일 오리진**으로 서빙해야 한다. Pages 가
`build_type: "workflow"` 라서 배포 시점에 `_site` 로 넣을 수 있고 — git 커밋은 불필요하다.

`scripts/fetch-flash-firmware.mjs` 가 그 단계다. 결정 세 가지:

- **태그 해석은 두 규칙을 이 순서로 쓰고, 어느 쪽을 썼는지 출력한다.** `config.h` 의
  `FIRMWARE_VERSION` 만 쓰면 버전 범프 후 태그 전 master push 에서 깨지고(그 릴리스가
  아직 없다), 최신 릴리스만 쓰면 배포 펌웨어가 비결정적이 된다. 둘 다 필요하다.
  조용히 고른 태그는 **잘못된 펌웨어 배포와 올바른 배포가 구분되지 않는다.**
- **sha256 은 캐시 히트에도 매번 재검증한다.** 캐시 키가 증명하는 것은 *출처*지
  *무결성*이 아니다. 비트가 상한 캐시 이미지는 벽돌이 된 보드다.
- **매니페스트가 아예 없는 릴리스는 실패가 아니라 명시된 스킵이다.** `esp32-v1.0.6`
  까지 전부 그 상태고, 여기서 실패시키면 다음 펌웨어 컷이 나올 때까지 **사이트 전체가
  안 나간다.** 페이지는 배포되고 "배포된 펌웨어 없음" 을 사용자 언어로 말한 뒤 CLI 를
  건넨다. 반대로 **매니페스트가 있는데 파일과 안 맞으면 배포를 실패시킨다** — 그건
  검증할 수 없는 바이트를 쓰는 페이지가 나간다는 뜻이니까.

`webFlash` 보드만 받아 ~26MB 가 아니라 ~6MB, 경로는 태그 주소(`fw/<tag>/…`)라서 낡은
브라우저 캐시가 최악의 경우 *이전* 릴리스 디렉터리를 가리킬 뿐 이번 릴리스 이름으로
지난 비트를 서빙할 수는 없다.

### 가드는 우회 버튼이 없고, 규칙은 한 곳에만 있다

브라우저와 CLI 는 esptool-js 구동 코드를 공유하지 **않는다**(하나는 Web Serial, 하나는
`serialport` shim). 그래서 **판정**을 SSOT 로 올렸다 — `esp32PreflightVerdict`
(`shared/src/esp32-boards.ts`). 두 번 존재하는 규칙은 언젠가 한 번 어긋나고, 여기서
어긋나면 벽돌이다.

여기서 설계를 한 번 고쳤다. 처음엔 `webFlash: false` 를 무조건 거부로 넣었는데,
**`webFlash` 는 "브라우저가 제공한다"이지 "써도 된다"가 아니다.** 그대로 뒀으면
`esp32_c6_147` — OTA 슬롯이 없어 **USB 가 유일한 업데이트 경로**인 보드 — 가 어떤
도구로도 업데이트할 수 없게 된다. 그래서 판정이 `surface: 'browser' | 'cli'` 를 받고,
그 축의 극성을 테스트가 고정한다.

크기 가드는 여전히 **방향성**이 있다(선언 ≤ 검출). InkDeck 은 물리 16MB 인데 BSP 가
8MB 를 굽기 때문에 등호 비교였다면 **올바른 설정을 불합격**시킨다. 그리고 읽히지 않은
flash id 는 **모름으로 남는다** — `detectFlashSize()` 가 디코드 실패를 조용히 `"4MB"`
로 위장하므로, 믿으면 "응답 없음"이 확신에 찬 오답이 되고 그 오답이 쓰기를 게이팅한다.

### lease 가 파일인 이유는 데몬을 멈추는 게 아니라 **되살아나는** 데몬 때문이다

기록된 실패에서 포트를 훔친 것은 내가 멈춘 데몬이 아니라 **재스폰된** 데몬이었다.
인프로세스 일시정지는 재스폰을 못 넘는다. 그래서 `~/.agentdeck/esp32-flash-lease.json`
이고, `startESP32Serial()` 이 시작할 때 그것을 읽는다.

**만료는 타이머가 아니라 읽는 시점에 강제한다.** 잠든 노트북에서 늦게 발화한 타이머는
약속보다 정지를 연장한다 — 데몬이 그만큼 더 모든 보드에 대해 귀를 닫는다. 읽기 시점
검사는 그럴 수 없고, 플래셔가 중간에 죽어도 **아무것도 실행되지 않은 채로** 회복된다.

열지 않는 것만으로는 부족해서 `releaseESP32SerialPorts()` 도 추가했다. 이미 잡고 있는
포트는 플래셔의 open 을 막고, macOS 에서 한 TTY 에 두 리더는 깔끔히 실패하는 게 아니라
서로의 바이트를 훔친다. 타이머는 살려 두므로 lease 가 만료되면 다음 poll 이 알아서
다시 연다 — 아무도 resume 을 기억할 필요가 없다.

**정직한 공백**: 샌드박스된 Swift 데몬은 `~/.agentdeck` 를 못 읽으므로 lease 가 덮지
못한다. 그래서 CLI 가 `lsof` 사전 점검을 하고, AgentDeck 이 아닌 프로세스가 잡고 있으면
**시작을 거부**하며(허용 목록 극성 — 모르는 홀더는 외부로 분류), 언제나 쓰기 후 검증한다.

### MD5 는 바이트가 도착했음을 증명하지 부팅을 증명하지 않는다

플래시 크기 헤더가 틀린 이미지는 MD5 를 **완벽하게 통과한 뒤 부트루프**한다. 그래서 CLI 는
115200 으로 포트를 다시 열고 `device_info` 를 기다린다.

**`ulanzi_tc001` 은 이 단계를 건너뛰어야 한다.** CH340 TX 가 하드웨어적으로 고장 나 있어
어떤 시리얼 프로브에도 답하지 않는다 — 검사를 돌리면 **정상 플래시가 실패로 보고된다.**
SSOT notes, `docs/esp32.md`, 브라우저 완료 화면 카피 세 곳에 예외로 박아 뒀다.

### 옮겨 심다가 걸린 두 가지

- **esptool-js 의 published ESM 은 Node 가 못 읽는다.** `lib/index.js` 의 상대 import 가
  **확장자 없음**(`from "./util"`)이라 번들러는 해석하고 Node ESM 로더는 첫 import 에서
  `ERR_MODULE_NOT_FOUND` 로 거부한다. 브라우저는 Vite 가 번들해서 안 걸린다. `bundle.js`
  가 같은 라이브러리를 자기완결 ESM 하나로 묶은 것이고 필요한 export 를 정확히 갖고 있어서
  Node 쪽은 전부 `esptool-js-node.ts` 를 거친다(타입은 로컬 `.d.ts` 로 붙였다 —
  `@ts-expect-error` 로 넘겼으면 ESPLoader 가 통째로 `any` 가 된다).
- **`calculateMD5Hash` 는 `image` 가 아니라 esptool-js 가 flash-params 헤더를 패치한
  뒤의 버퍼를 받는다.** 그래서 콜백이지 `md5(image)` 가 아니다. 브라우저 쪽은
  SubtleCrypto 에 MD5 가 없어서(의도적으로 없다) RFC 1321 을 ~70줄 직접 구현했고,
  기대 다이제스트 표를 붙여넣는 대신 **`node:crypto` 와 대조**해 테스트한다 — 55/56/64
  바이트 패딩 경계 포함. 미묘하게 틀린 해시는 **모든 플래시를 실패**시키고 증상은
  "잘못된 쓰기" 와 구분되지 않는다.

### 배선

`/flash/` 는 여섯 번째 Pages 표면이다. GNB 마커(markup 은 `index.html`, CSS 는 링크된
`style.css` — 디자인 시스템 뷰어와 같은 분리), `sync-pages-nav.mjs` SURFACES 항목,

이미 다섯 장이었고 이제 여섯 장이다. 잊히기 딱 좋은 편집이라 플랜에 따로 적어 뒀었다).

`design/lint.sh` 는 `./tools/creature-simulator` 를 prune 하지만 `./tools/web-flasher` 는
하지 않는다 — 즉 새 앱은 린트 범위 안이다. prune 항목을 추가하는 대신 토큰 청정하게 썼고
위반 0 이다. Apache-2.0 고지(`THIRD-PARTY.txt`)는 설치된 패키지의 LICENSE/NOTICE 에서

가져야 할 유일한 성질이 "실제로 나간 것에 대해 정확함" 이다.

### 적대적 리뷰가 잡은 것 (머지 전, 2종 병렬)

**세 가지가 blocking 이었다.**

1. **CLI 태그 해석이 지금 이 순간 깨져 있었다.** `resolveFirmware` 가 `config.h` 의
   `FIRMWARE_VERSION` 을 **존재 확인 없이** 썼다. 내가 그 파일을 1.0.7 로 범프했는데
   `esp32-v1.0.7` 은 아직 없으니, **문서가 첫 줄에 적어 둔 `agentdeck esp32 flash 86box`
   가 모든 체크아웃에서 실패**했다. 게다가 오류가 두 번 오진했다 — 없는 릴리스의 404 와
   없는 에셋의 404 가 바이트 동일이라 "이 릴리스엔 매니페스트가 없다"로 보고했고,
   "더 새 --tag 를 쓰라"는 1.0.7 이 이미 최신이라 실행 불가능한 조언이었다.
   웃긴 건 `scripts/fetch-flash-firmware.mjs` 에는 **내가 올바른 규칙을 이미 써 뒀고
   그 주석이 정확히 이 버그를 설명한다** — "규칙 2 단독은 범프와 태그 사이 master push
   에서 깨진다". CLI 가 규칙 2 단독이었다. 범프→태그 창마다 재발한다.
2. **워크플로 스텝의 자기 폴백이 `set -e` 때문에 도달 불가능했다.** GitHub 은 `run:` 을
   `bash -e {0}` 로 돌리므로 대입문 안의 실패한 명령 치환이 스텝 전체를 죽인다
   (`bash -e -c 'V=$(echo x | grep -oE NOPE); echo reached'` → `reached` 안 찍히고 exit 1).
   즉 `VERSION` 이 비는 경우를 대비해 써 둔 `${VERSION:-<unset>}` 분기가 **영원히 실행되지
   않고**, `gh release list` 의 일시적 rate limit 하나가 리포트·디자인시스템·디바이스까지
   **사이트 전체를 내린다** — 정작 그 아래 두 스텝은 빈 태그에 대해 조심스럽게 fail-soft 인데.
3. **태그 해석이 두 번 구현돼 있었고 테스트된 쪽이 CI 에서 죽어 있었다.** 워크플로가
   `--tag` 를 넘기니 `resolveTag()` 는 항상 `source:'flag'` 를 반환했다. 실제 결정은
   테스트 없는 bash 복제본이 내리고, `docs/pages-site.md` 는 스크립트가 "어느 규칙을 썼는지
   출력한다"고 적어 뒀는데 CI 에선 `--tag` 밖에 출력할 수 없었다. → `--print-tag` 모드를
   만들어 **해석기를 하나로** 합쳤다(캐시 키도 그 출력에서 온다).

**그리고 두 가지 HIGH.**

4. **suspend 가 진행 중인 `openPort()` 와 레이스한다.** `pollForDevices` 는 `await
   openPort()` 동안 포트를 `openingPorts` 에 들고 있는데(fd open + `stty` exec, 수백 ms~초),
   `releaseESP32SerialPorts` 는 `connections` 만 본다 — 그 포트는 아직 거기 없다. 그래서
   open 중에 도착한 suspend 는 `released: 0` 을 보고하고, CLI 는 "Daemon serial suspended"
   를 찍고, 1초 뒤 open 이 완료되며 **살아 있는 연결을 push** 한다. lease 때문에 poll 이
   조기 반환하니 아무도 그걸 거두지 않고, `sendHeartbeat` 가 5초마다 **esptool 이 펌웨어를
   쓰고 있는 바로 그 TTY 에 JSON 을 쓴다.** 정확히 lease 가 막으려던 실패다.
   → 세대 카운터(Swift `ESP32Serial` 의 `OpenAttemptToken` 과 같은 규칙).
5. **teardown 의 `await` 가 무한히 멈출 수 있고, 그게 lease resume 을 막는다.**
   `Transport.disconnect()` 는 `waitForUnlock()` 에서 데드라인 없이 스핀하고,
   `Transport.write()` 에는 **try/finally 가 없다** — 보드를 뽑아 `writer.write()` 가
   reject 되면 writable 이 영구히 잠기고 그 스핀은 절대 끝나지 않는다. 그 teardown 이
   CLI 의 `finally` 가 기다리는 자리라, 명령은 출력 없이 멈추고 데몬 시리얼은 lease 만료
   (420s/900s)까지 죽어 있는다. → 전부 bounded. (레포 규칙: 외부 peer await 엔 timeout.)

**MEDIUM 셋.** `--erase` 가 `stub: false` 보드에서 **조용한 no-op** 이었다
(`eraseAll` 은 스텁 전용) — 하필 `ttgo_t_display` 가 `webFlash: true` 라, 보드를 남에게
넘기며 erase 를 체크하고 "MD5 verified" 까지 본 사용자가 **이전 소유자의 WiFi 자격증명과
페어링 토큰이 남은 보드**를 건네게 된다. 이제 양쪽 다 거부한다. // 가드는 `board.flashSize`
를 검사하는데 쓰이는 건 `entry.flashSize` 였다 — 둘은 의도적으로 분리돼 있으므로(매니페스트는
릴리스 태그에서, 스펙은 번들에서) **가드가 아무도 쓰지 않는 값을 검증**할 수 있었다.
`imageGeometry` 를 SSOT 판정에 추가. // `whoHoldsPort` 가 "볼 수 없었음"을 "아무도 안
잡고 있음"으로 세탁했다(lsof 미설치·타임아웃·EPERM 전부 `[]`) — 이건 lease 가 닿지 못하는
샌드박스 데몬에 대한 **유일한** 가드다.

**후속으로 더 고친 것 (리뷰의 "minor" 항목들 — 전부 같은 부류라 남겨 두지 않았다).**

취향이 아니라 사고 기록인데 그걸 조용히 덮어쓰는 셈. // 릴리스 목록의 `--limit 100` /

없이 ~16라운드면 최신 esp32 태그가 한 페이지에서 빠지는데, 그때 나오는 건 "모름"이 아니라

도달 불가지만, 그 보장은 **캐시 키가 아니라 스크립트에** 있어야 한다. // `callDaemon` 이
비-2xx 를 전부 "데몬 없음"으로 접었다: **답을 하고 거부한 데몬**과 없는 데몬은 다르며,
401 을 "정지할 것 없음"으로 보고하면 사용자를 *포트를 아직 쥐고 있는* 데몬 위로 플래시하러
보내면서 방금 아니라고 말한 셈이 된다. 이제 세 결과로 나누고, 거부에는 플래시를 중단한다.

**LOW.** `parseInt` 미검증(`--baud abc` → NaN 이 `?? ` 를 통과해 칩을 정의되지 않은 보율로
보낸다) · 펌웨어 미배포 상태에서 비활성 보드가 `· verified` 로 렌더(정확히 "미지원으로
읽힌다"는 그 혼동) · `i18n.ts` 의 `head.kicker` 가 KO/JA 에 없음 · `pages-nav.html` 이
자기를 "four committed surfaces" 라 부름 · 리드 문구가 카드 여섯에 절 다섯.

리뷰가 확인한 것도 기록해 둔다: 프리플라이트 우회 경로 없음, 데몬 인증 게이트가 세 라우트
전부 커버, lease 만료/손상 처리 정상, md5 는 14개 크기에서 `node:crypto` 와 일치,
esptool-js API 사용이 0.6.1 소스와 전부 일치, npm 패키징 정상(`bundle.js` 가 tarball 에 있음).

**리뷰가 스팟체크에서 남긴 관찰 하나 — 고치지 않고 못 박았다.** geometry 검사가
**엄격한 동등**이라 보수적 방향(매니페스트 8MB vs SSOT 16MB)까지 거부한다. 얼핏 과하게
보이고, 나중에 누가 "방향성으로 고쳐야 한다"고 생각하기 딱 좋다. 그래서는 안 된다:
크기 규칙과 달리 이 둘은 *같은 보드에 대한 두 서술*이고 서로 일치해야 하는 출처에서
왔으므로, 어느 방향이든 불일치는 "둘이 다른 보드를 말하고 있다"이며 어느 쪽이 참인지
알 방법이 없다. 결정적인 이유는 따로 있다 — **flash id 를 못 읽는 보드에서는 이게 유일하게
남는 크기 검사다.** stubless TTGO 는 `0xffffff` 를 답하므로 `esp32FlashSizeIsSafe` 가
undefined 를 내고 크기 축이 통째로 검사되지 않는데, 방향성으로 풀면 **정보가 가장 적은
바로 그 경우에 가드가 0개**가 된다. 실측으로 확인하고 테스트 둘로 이유까지 고정했다.
대가는 결함이 아니라 **릴리스 순서 제약**이다: SSOT 플래시 크기를 바꾸면 Pages 가 새
매니페스트로 재배포될 때까지 브라우저가 그 보드를 거부한다. RELEASING.md 에 기재.
