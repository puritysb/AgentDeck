# 2026-08-17 — "같은 머신"과 "나"는 다른 질문이다 (로드맵 P0 1~5)

### 문제

데몬의 같은-머신 신뢰는 `isLocalConnection` — **순수 IP 검사**다. 한 사람이 CLI 데몬과
macOS 앱을 함께 쓰던 시절엔 "127.0.0.1 에서 왔다 = 내 것"이 맞았다. 공유 호스트에서는
틀리고, 그 위에 얹힌 권한이 전부 문제가 된다:

- **자격증명 유출**(§1.2): B 의 `daemon start` 가 9120 의 `/health` 를 읽고 A 의
  pairing token 을 자기 홈으로 복사한다.
- **서비스 거부**(§1.3): 같은 경로가 A 의 데몬에 `/stand-down` 을 쏜다. 더 나쁜 건
  자동인 쪽이다 — **데몬 시작 시 포트 윈도우 sweep 이 발견한 Swift 데몬을 전부
  shutdown 시킨다.** 공유 박스에서 한 사람이 CLI 데몬을 켜면 동료들 macOS 앱이 전부
  죽는다. Swift 쪽 `reclaimCanonicalPortIfNeeded` 는 반대 방향으로 대칭이다: 남의
  데몬에 스스로 stand down 하고 client 로 붙어 **남의 세션·프롬프트·프로젝트명을 내
  대시보드에 그린다.**
- **세션 오배치**(§1.4): 자기 `daemon.json` 이 없는 사용자의 포트 스캔은 윈도우에서
  처음 응답한 데몬 — 사무실이면 동료 것 — 에 세션을 등록한다. 그 동료의 Stream Deck
  이 그 세션을 focus 하고 키를 주입할 수 있다.
- **mDNS 이름 충돌**(§2.1): 두 데몬 다 `AgentDeck-9120` 을 광고했다. DNS-SD 인스턴스
  이름은 **세그먼트당** 유일해야 하는데, 사무실 서브넷의 50개 데몬이 한 이름을 두고
  싸운다. Node 쪽은 충돌 시 이름을 바꾸지 않는다 — "already in use" 를 non-fatal 로
  삼키고 5초마다 영구 재광고한다.

### 해결

**술어 하나, 값 셋.** `localPeerOwnership()`(`bridge/src/auth.ts`) 이
`same-user` / `other-user` / `unknown` 을 답한다. 세 번째는 앞 둘의 반올림이 아니다.

**`unknown` 은 의도적으로 관대하다.** 증명 못 하면 거부하는 쪽은 "한 머신 한 토큰"
수렴을 깨고, 그건 페어링된 플릿 전체가 인증 못 하는 사고(2026-08-08)로 이어진다.
공유 호스트에서 토큰이 사용자 경계를 넘는 것보다 훨씬 흔하고 훨씬 나쁘다. 대신
**절대 조용히 넘어가지 않는다** — 증명 없이 진행하는 분기는 로그를 남긴다.

**Swift 미러는 syscall 이 아니라 계약을 복제한다.** Node 는 `kill(pid, 0)` 의 EPERM
을 "다른 사용자"로 읽는다. 샌드박스 앱에서 같은 EPERM 은 대개 "샌드박스가 거부함"
이고, 그걸 그대로 쓰면 **평범한 같은-사용자 인계가 전부 거부**된다 — 플릿을 잠그는
바로 그 실패 모드다. Swift 는 `proc_pidinfo` 로 uid 를 직접 비교하고 모든 실패를
`unknown` 으로 떨어뜨린다(안전한 방향).

호출 지점은 CLI 액션 안의 인라인 클로저였다. 통째로
`negotiateIncumbentDaemon`(`bridge/src/daemon-takeover.ts`)으로 들어냈다 —
효과가 있는 것은 전부 의존성이라, 테스트가 **남이 소유한 incumbent 를 상대로 실제
경로를 구동**하고 adopt/stand-down 이 일어나지 않았음을 증명할 수 있다. 술어 진리표는
호출 지점이 호출을 잊어도 green 으로 남는다(로드맵 §8 이 요구한 바). 다른 사용자
소유의 프로세스는 root 없이 테스트에서 만들 수 없으므로 소유권만 주입하고, 단언은
**호출 지점이 무엇을 했는지**에 건다.

**mDNS 이름은 SSOT + 생성기**로 갔다(`shared/src/mdns-identity.ts` →
`pnpm generate-mdns-identity`, 드리프트 게이트). 이 이름의 가치는 전적으로 "두 번
같은 방식으로 계산되는 것"에 있으므로 손 미러가 제일 안 되는 대상이다. 이제
`AgentDeck-<host>-<userTag>-<port>` 를 광고하고 TXT 에 `host`/`user` 키를 더한다.
`user` 는 `uid:username` 의 FNV-1a 4자리다 — **계정명이 아니다.** 멀티캐스트는 세그
먼트의 모두가 읽는다. `v` 는 `3` 을 유지했다: 키 **집합**을 검증하는 리더가 없고
(ESP32 는 레코드를 훑으며 `agent`/`project` 만 본다), 추가 키는 기존 클라이언트가
그대로 읽는다. 호환성 문제 없는 곳에서 호환성 이벤트를 만들 이유가 없다.

### 닫지 못한 것 — 그리고 왜인지

**로컬 프로세스는 여전히 `/health` 에서 pairing token 을 읽을 수 있다.** TCP 소켓은
peer credential 을 나르지 않는다 — `LOCAL_PEERCRED` 는 UNIX 도메인 전용이고, `lsof`
로 푸는 건 서브프로세스라 App Store 빌드에서 금지다. 그래서 이 변경은 **AgentDeck
자신의 코드가 사용자 경계를 넘어 행동하는 것**을 전부 막지만, 그냥 curl 하는 로컬
사용자는 막지 못한다. 받는 쪽 라우트에 토큰을 요구하는 안은 검토 후 기각했다 —
고의적 공격자는 `/health` 에서 토큰을 먼저 읽으므로 그에게는 아무 방어가 안 되면서,
정작 지켜야 할 같은-사용자 인계만 위태롭게 한다. 진짜로 닫으려면 UNIX 도메인 제어
소켓이나 파일시스템 핸드셰이크가 필요하다(§1.2 에 적어뒀다).

**§2.2(페어링된 엔드포인트 우선)는 Node 절반만 했다.** `sortDiscoveredDaemons` 가
명시된 호스트 → 내 userTag → 남의 데몬 → TXT 키 이전 데몬 순으로 정렬한다. 필터가
아니라 선호다(교차 사용자 attach 는 `--daemon-host` 의 정당한 용도). 정작 아픈 표면
— ESP32 와 모바일 두 경로 — 은 아직 first-seen 이다. 보드 쪽은 "저장된 엔드포인트
우선 + 4001 로 닫은 엔드포인트를 영원히 재시도하지 않기"를 같이 해야 하고 OTA 컷과
하드웨어 검증이 필요해서 별도 변경으로 남겼다.
