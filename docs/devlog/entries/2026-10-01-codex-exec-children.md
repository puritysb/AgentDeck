# 2026-10-01 — Headless `codex exec` runs become children of their launcher, and Codex runs finally close

A Claude session in another project ran a script that fanned 49 topics out through `xargs -P 4 … codex exec -C <scratchpad>/gen/work/<topic>`. Every job is a real `codex` process holding a rollout and firing the user-global lifecycle hooks, so the Node daemon minted 49 `codex-cli` sessions named after scratchpad directories (`2020s_ai_hw`, `2030s_future_sw`, …) — four live at a time, rotating through every deck — and 49 APME runs. All 49 runs, plus six from 9/29–9/30, were still open 26 hours after their processes exited: Codex has no `SessionEnd` hook, a codex run closed on nothing else, and the abandoned-run reaper skips every run the collector still holds (`isLiveRun`).

Two changes, on both daemons:

- **A headless run is a child, not a session.** `bridge/src/codex-exec-children.ts` (Swift: `CodexExecChildren.swift`) keeps one registry with two producers. The passive observer reads `session_meta.originator: codex_exec` off the rollout and walks the process's ancestry (`timeout` → `node` → `codex`, then `bash` → `xargs` → `run.sh` → `zsh` → `claude`) to another observed session's pid; a run with such an ancestor leaves the roster and is reported as that session's child (`foldHeadlessCodexSessions`). The hook path asks the same registry first: a headless rollout whose parent is visible is attached on its `SessionStart` (the process found by its `-C <cwd>` argv — canonicalized, since `-C /tmp/x` reports `cwd: /private/tmp/x` — or as the only unclaimed `codex exec`; when the cached table predates the run, one fresh table is read for that session). A run that still cannot be attached is `pending`, but its hooks flow: a review of the first cut showed that holding them left a user's own terminal `codex exec` with neither session nor run, so a pending run is a session until the observer's next scan (or the tick's table) proves it a child, at which point its row, run and open `chat_start` are retracted (`Folded into parent`). One nobody launched is `standalone` after 60 s. An argv-matched pid is a guess that may belong to a same-cwd sibling, so such a child is completed only when no run for that cwd is left; the observer's `lsof`-backed pid is exact. Attaching retracts whatever the child's first hooks created (hook row, APME run, hub-driver identity) and hands a `SubagentStart` to the parent's `SubagentTimelineTracker` — the same census a Claude `Agent` call moves, so the parent row shows `subagents: {active, peak, completed}`, the timeline folds the fan-out into one dispatch row, and the parent's active APME task records `sample_events.kind='subagent'`. The child's `Stop` (or its process leaving a non-empty table) is its completion: a `SubagentStop` with the run's last reply, or the topic directory when it said nothing. OTel treats a folded child as hook-owned so the span batch `codex exec` exports at exit cannot re-synthesize the row.
- **A Codex run closes when its session leaves the roster.** `sweepVanishedCodexRuns` (coordination tick, 5 s) tracks every Codex session this daemon holds a run for and closes the run once the id has been absent from observer rows, hook rows and OTel rows for the agent idle gap (15 min). The first cut used 90 s; after a Stop the hook row lives 60 s and presence then rests on the observer alone, which cannot see a TUI's rollout on Windows or through a slow `lsof`, so a shorter grace split a live session's run at every turn. The Swift daemon closes the run when it evicts the Codex session. This is the Codex analogue of Kiro's observed-vanish close and OpenClaw's idle close; the abandoned-run reaper remains the restart-only backstop it always was.

The Swift daemon has no process observer, so its hooks are the only producer: `CodexExecChildRegistry` resolves the run's process from the sysctl table (`ProcessEnumerator`) the same way, reads the rollout head inside the Codex directory bookmark, and hands `subagent_start` / `subagent_stop` to the existing census. Peers there are the sessions with a registered pid — Claude sessions through the hook header. The Codex hook snippet carries no `X-AgentDeck-Pid`, so a Codex TUI's own `codex exec` children are not attributable on either daemon; adding the header (three mirrored installers plus a migration) is tracked in #429.

Verified on the installed 9120 daemon (build ea9e5128d6b6, launchd unit restarted onto the worktree build): a three-way `xargs -P 3 codex exec` batch from a Claude session produced zero codex rows and a parent census of `{active 3, peak 3}` → `{completed 3}`, one dispatch row and three completion rows, `sample_events.kind='subagent'` on the parent's task, and no APME runs for the children; a detached run (`setsid`, no session ancestor) stayed a standalone row and its run closed after it left the roster. A `nohup … &` subshell reparents the run to launchd, which is what made a first attempt look like a regression — the ancestry was gone, not the fold.
