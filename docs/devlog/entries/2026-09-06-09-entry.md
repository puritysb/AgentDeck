# 2026-09-06 — 잘림 규칙은 플래그가 아니라 본문에 대한 것이고, 백로그는 독 한 알에 막혀 있었다

#286 의 항목을 처리하면서 백로그 정체의 진짜 원인을 찾았다. 둘은 다른 문제였다.

**판정 백로그는 소진되지 않았다 — 217 → 156 뒤 하루 동안 그대로였다.** 배출기는 tick 당
1건을 `ended_at DESC` 질의의 **맨 앞에서** 가져가는데, `enqueueTask` 는 park 된 task 를
**조용히 버린다**. 그래서 판정이 매번 실패하는 task 하나가 그 자리를 차지하면 매 tick 이
그 한 칸을 거기에 쓰고 뒤의 전부가 굶는다. 실측(9/6): 8/07~8/23 의 닫힌 task **156건**이
2주째 미판정인데, 같은 기간 그날의 task 는 95건 중 83건이 라이브 close 경로로 정상 판정됐다.
개수가 증거다 — 맨 앞이 판정 가능한 동안은 217→156 으로 줄다가, 그 뒤 완전히 평평하고
데몬 로그에는 park 한 줄만 반복된다. 이제 200행 창을 읽고 `pickBacklogTasks` 가 고른다
(여전히 tick 당 1건, 창은 *어느* 것인지만 정한다). 창 전체가 park 면 park 주기당 한 번
로그로 말한다 — 침묵이 이 결함을 2주간 살려둔 것이기 때문이다.

**park 의 원인은 판정 서버가 아니라 모델이다.** gemma-4-26b 는 일부 프롬프트에서
`summary` 문자열 안에서 같은 문장을 반복하다 800토큰 상한에 닿고 객체를 끝내 닫지 않는다
(실측 3,450자, `finish_reason=length`, completion 800). 이건 거부가 맞다.

**그래서 #285 의 규칙은 본문에 대한 것으로 좁혔다.** 닫힌 JSON 객체는 완성된 판정이고
닫는 중괄호 뒤에 모델이 더 쓴 것은 판정의 일부가 아니다. 객체 도중에 잘린 본문은 애초에
파싱되지 않으므로 `parseJudgeJson` 이 같은 케이스를 이미 거부한다. 완성본까지 거부하면
기본 체인에서 조용히 FM 바닥(0.580)으로 내려갈 뿐 얻는 게 없다. 잘림 검사는 실패 사유를
"잘렸다"고 말할 수 있게 남겼다.

**Anthropic `api` 레그**는 완결성 가드가 아예 없었고 두 데몬이 8배 어긋나 있었다(Node
8,192 / Swift 1,024). 양쪽 다 잘린 본문을 거부하고, 같은 상한과 같은 기본 모델을 쓴다 —
Node `claude-opus-4-8`, Swift `claude-opus-4-6` 이 하나의 settings.json 을 읽는 하나의
판정자였다. Swift 는 `temperature` 도 뺐다: Opus 4.7 이후는 샘플링 파라미터를 거부하므로
그 레그는 모든 현행 모델에서 400 이었고, 실패는 `nil` 로 보고돼 "API 키 없음"과 구별되지
않았다.

`choices` 비배열은 Node 만 뚫려 있었고(Swift 는 늘 거부), Swift 는 `reasoningEffort` 를
읽지 않았다 — 게다가 `apiKey` 는 구조체에 선언만 되고 settings.json 에서 **한 번도 파싱된
적이 없어** OpenAI 호환 레그가 설정의 Bearer 키를 못 보냈다.

작은 항목들: `claude-usage-recovery.ts` 가 쿨다운 기록을 `AGENTDECK_DATA_DIR` 무시하고
`homedir()/.agentdeck` 에 두어 데이터 디렉터리가 다른 두 데몬이 재시도 예산을 몰래 공유했다
(usage-api.ts 캐시도 같이 옮겼다 — 같은 디렉터리다). 복구 자식은 `unref()` + 종료 시 kill.
429 분기는 호출 시작 시점의 스냅샷에 `retryAfter` 를 찍어 그 사이 다른 브리지가 쓴 더 새
값을 되돌렸다.

**적대적 리뷰 3라운드, 6·9·6건. 매 라운드 최악은 직전 라운드의 수정본에 있었다.**

1라운드: 두 데몬의 `holdsCompleteJsonObject` 가 **서로 다른 텍스트를 꺼내고 있었다** —
Swift 는 균형 스캐너, Node 는 첫 `{`부터 마지막 `}`까지의 greedy 정규식. 잘린 본문을
받아들이기 시작한 바로 그 커밋에서 이 차이가 하중을 받는다: "닫는 중괄호 뒤의 텍스트"가
정확히 그 경로이기 때문이다. `api` 레그의 `judgeModelLabel` 은 상수
`api:claude-opus-4-6` 이라 실행되지도 않은 모델을 eval 행의 출처로 찍고 있었고, Node 도
반대편에서 같은 결함이었다.

2라운드(내 수정이 만든 것): 균형 스캔은 파싱 가능한 구간을 **늘리므로** "먼저 파싱되는
것"이 안전한 규칙이기를 그만뒀다 — `<think>{"overall":0.5}</think>` 뒤에 진짜
`{"overall":0.9}` 가 오면 스크래치패드가 점수가 된다. greedy 는 여기서 null(=시끄러운
실패)이었으므로, 내 수정이 **보이는 skip 을 조용한 오답으로 바꿔놓은 것**이다. 이제 판정은
위치가 아니라 `overall` 로 고르고, 그걸 가진 구간이 둘이면 모호로 보고 null 이다. 그리고
게이트의 질문 자체가 틀렸었다: "파싱되는가"는 두 파서의 관대함이 달라(실측: Swift
`JSONSerialization` 은 trailing comma 를 받고 Node `JSON.parse` 는 거부) 데몬마다 답이
갈린다. 순수하게 구조적인 질문("`{…}` 가 닫혔는가")으로 바꿨다 — 균형 스캐너는 양쪽이
동일하다.

3라운드(또 내 수정이 만든 것): 스크래치패드가 닫히고 **진짜 판정이 잘린** 본문은 닫힌
구간이 하나뿐이라 모호해 보이지 않는다 — 초안이 그대로 점수가 된다. 그리고 Swift
`parseJudgeJson` 은
여전히 **첫 블록**을 집고 있었다: Node 스위트가 null 로 고정한 바로 그 본문이 Swift 에서는
0.5 로 저장됐다(커밋 제목이 "두 데몬이 같은 방식으로 꺼낸다"고 주장하던 중에). 이를
고정하려면 벡터에 축이 하나 더 필요했다 — `accepted`(전송 게이트)와 `verdict`(그 뒤 파서가
판정을 내야 하는가). 게이트는 통과시키고 파서는 거부해야 하는 본문은 이 둘 없이는 표현할
수 없고, 그래서 아무도 이 차이를 못 잡고 있었다.

4라운드에서 **같은 메커니즘이 3라운드 연속 HIGH 를 낳는다는 신호**가 확정됐다. 3라운드의
"닫히지 않은 `{`" 규칙은 잘림이 `</think>` 와 `{` **사이**에 떨어지면 여전히 초안을
받아들였고(불완전), 동시에 꼬리 산문에 짝 없는 중괄호가 있는 **완성된 판정을 거부**했다
(과잉). 중괄호 구조로는 모델이 끝냈는지 알 수 없다는 뜻이다.

**그래서 예외 자체를 삭제하고 #285 의 규칙으로 되돌렸다** — `finish_reason=length` 는 본문
모양과 무관하게 거부한다. 근거는 두 가지다. 하나, 이 예외는 **실측 수혜자가 없다**: 이
기기에서 관측된 유일한 잘림 형태는 `summary` 문자열 **안쪽**의 반복 루프라 depth 가 0 으로
돌아오지 않고, 직접 바이트를 확인한 잘린 본문 1건도 객체를 닫지 않았다. 둘, #286 항목 3 이
스스로 나열한 선택지에 "계속 거부하고 발생률을 알린다"가 있고, 발생률은 이제 측정됐다 —
park 된 24건을 다시 판정하면 **16건이 통과**하고 8건만 다시 잘린다(잘림은 시도 단위
비결정성이지 영구 상태가 아니다). 남긴 것은 측정된 가치가 있는 쪽뿐이다: 균형 스캔 +
`overall` 로 판정을 고르는 규칙(잘리지 않은 본문의 think 블록 문제를 실제로 고친다)과
`choices`/`content` 배열 가드, api 레그의 refusal/max_tokens 거부.

4라운드는 그 밖에 Swift 의 `as? Double` 이 JSON **불리언을 숫자로 브리징**해
`{"overall":true}` 가 이 데몬에서만 만점으로 저장되던 것도 잡았다(뮤테이션 3건 확인).

검증: Vitest 260파일 4,103 통과. macOS XCTest 743, 실패 0. 새 게이트는 전부 뮤테이션으로
확인했다(판정 선택 3·구조 게이트 5·Swift 선택 1·api max_tokens/refusal 각 1·불리언 3).
실제 백로그를 이 코드로 돌려 **158 → 24**(판정 124, 자격미달 6, 53분). 남은 24건은 두 번
실패 뒤 park 되고 **건너뛰어졌다** — 수정 전이라면 그중 첫 한 건에서 영구히 멈춘 지점이다.

**아직 열린 것**: gemma-4-26b 가 일부 시도에서 `summary` 안 반복 루프로 800토큰 상한에
닿는 것 자체는 남아 있다(재현되는 8/24). 상한을 올려도 루프는 무한하므로 소용없고,
repetition/frequency penalty 가 실제 레버다 — 판정 샘플링 파라미터 변경이라 이 PR 범위
밖으로 둔다.
