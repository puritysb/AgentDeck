# 2026-10-25 — Real multi-agent approval acceptance found a Swift Gateway visibility gap

The [earlier source audit](docs/devlog/entries/2026-10-25-agent-attention-audit.md) and [installed Claude acceptance](docs/devlog/entries/2026-10-25-swift-attention-live-acceptance.md) were extended to actual Codex 0.160.1, OpenCode 1.18.35 and OpenClaw 2026.10.5 (running Gateway protocol 4). Codex and OpenCode used their real approval engines and canonical AgentDeck hooks/plugin with isolated configuration and deterministic local model responses. Codex hooks were trusted through its normal TUI review screen, never by writing trust hashes or bypassing review. OpenClaw used its real configured agent/Gateway with unique disposable session keys. No production agent permission policy or unrelated conversation was modified.

Node results: actual Codex approval appeared and cleared after the command ran; a rejected command cleared after Stop and the subsequent roster broadcast. Actual auto_review allow and deny completed without client approval requests or Attention. OpenCode permission asks appeared, replies cleared them, an allow rule executed Bash with no ask, and a deny rule removed Bash before dispatch (the attempted unavailable tool produced an invalid-tool result, not a user dialog). OpenClaw guarded exec requests appeared, allow-once and deny resolved them, workspace-mode automatic review allowed a harmless printf without Attention, and read-only mode denied a temporary-file write without a user request or created marker file.

The same installed Swift app correctly distinguished Codex and OpenCode. Codex's legacy guardian_subagent input normalized to auto_review in its actual rollout and also produced no Attention. However, the real OpenClaw guarded request remained processing on Swift while the Gateway and the Node observer showed a pending approval. This was a missed real wait, not an automatic-review false positive.

A bounded read-only probe using the same owner token established the cause while one request was pending. Both connections authenticated, and both could call exec.approval.list, but scopes operator.read/operator.write/operator.approvals returned an empty list; Node's operator.admin/operator.approvals/operator.read returned the pending request. Swift used the former default. The approvals cap and the approval RPC scope alone do not provide cross-connection request visibility on this Gateway. Empty here meant visibility-filtered, not proof of no human wait.

Automatic approval review initially rejected adding operator.admin because it also grants Gateway administration and the original task did not explicitly authorize that scope expansion. A concrete before/after proposal was provided; the user then explicitly approved the default administrator scope. The fix moves Node's existing default into the OpenClaw approval SSOT and generates it into Swift. Both connect paths use the resolver. A previously issued restricted device grant, including an explicit empty grant, is retained exactly, including shared-token fallback after device authentication fails, never unioned with the default. The regression checks cover actual Node connect payloads, missing/default selection, preservation and copying of restricted grants, Swift behavior, and mirror/wiring drift.

The runtime evidence and reproduction tools are preserved locally under ignored diagnostics/multi-agent-attention-live-01a16f08/. The first quick-check attempt used a fresh offline worktree whose install scripts had been deliberately skipped; SQLite-dependent tests failed because better_sqlite3.node was absent. Building the bridge's allowed native dependencies restored a real in-memory SQLite connection. This was test-environment setup, not a product-code regression.

The signed sandboxed development app was rebuilt and installed at /Users/puritysb/Applications/AgentDeck Development.app, preserving both the previous development bundle and the Store installation. The executable and Debug dylib matched the build output (dylib SHA-256 de8018d5fd3850f8c5d8655bf92f7141f7d68e2b7712b0f3a8913b04f4fa00e5). PID 70737 owned canonical port 9120 and reported isSwift=true with the Gateway connected. Its registry is in the app container; a legacy-only registry probe initially waited on the wrong path, so acceptance switched to the container registry instead of guessing from the port.

Post-fix actual OpenClaw acceptance passed all four cases. Guarded printf request f155b0e9-2760-44f5-84ef-179704c7355b appeared as APPROVE and ATTENTION in the Dashboard and awaiting_permission in the real roster; allow-once ran the marker and returned idle. Request 0bde69a8-5d2b-4298-9d7a-df1678cf41ff showed the same wait, then deny produced a user-denied tool result and cleared the wait. Workspace automatic review returned “Exec auto-review allowed once (risk=low)” and the marker; read-only execution returned security=deny and created no marker file. Neither automatic case raised a request or awaiting_permission. The final Dashboard showed OpenClaw IDLE without Attention. Four disposable Gateway session keys were deleted, and the two isolated Codex daemon instances were stopped through their own scoped CLI lifecycle commands. No unrelated approval was answered.
