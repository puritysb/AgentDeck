# 2026-08-17 — 데몬 포트에 "의도" 를 만들고, 잠깐 뺏긴 포트를 되찾게 하다

### 문제

앱이 9120 을 놓은 직후 `agentdeck daemon start` 를 하면 데몬이 9121 에 앉았고, 몇 초
뒤 9120 이 비어도 **아무것도 되돌리지 않았다**. 그 데몬의 남은 수명 내내 canonical
포트는 주인이 없었고, 되찾는 방법은 `stop` → 기다림 → `start` 뿐이었다.

원인은 두 겹이다. 표면은 EADDRINUSE 처리다 — 선호 포트가 bind 되지 않으면 데몬은
즉시 폴백 포트를 찾았다. macOS 는 리스너 cancel 후 ~14초 NECP 예약을 유지하므로
(2026-08-06 실측: ~17초에 bind 가능, 그 사이 `lsof` 는 소켓 0개), 그 즉시성이 곧
"14초짜리 커널 유예를 영구 이사로 바꾸는" 동작이었다.

더 깊은 원인은 **데몬에게 의도가 없었다**는 것이다. `daemon.json` 은 데몬이 어디에
*앉았는지*만 기록한다. 어디에 *앉으려 했는지* 를 아무도 모르니, 폴백 포트에 앉은
데몬은 자기가 잘못된 포트에 있다는 사실 자체를 알 수 없었다. 로드맵 11번이 요구한
"CLI 데몬 포트 영속화" 는 설정 항목이 아니라 이 의도였다.

### 해결

`bridge/src/daemon-port.ts` 가 **선호 포트**(의도)를 해석한다 — `-p` › `AGENTDECK_DAEMON_PORT`
› `settings.json daemonPort` › 9120. 이름과 역할 모두 앱의 `AppPreferences.daemonPort`
와 같다. `agentdeck daemon port [n] [--clear]` 로 읽고 쓴다.

**의도는 영속화하고 결과는 절대 영속화하지 않는다.** 시작 경로의 어떤 코드도 이 값을
쓰지 않고(테스트가 `daemon-server.ts` 에 writer 가 없음을 고정한다), 사용자만 쓴다.
결과를 적으면 자기강화가 된다 — 폴백 포트가 기록되고 그 뒤로 영원히 선호된다.

의도가 생기니 진단이 가능해졌다. 선호 포트가 bind 되지 않는데 `/health` 에 아무도
응답하지 않으면 그건 양보할 peer 가 아니라 **떠난 주인의 포트를 커널이 붙들고 있는
것**이다. 이제 최대 20초(`PREFERRED_PORT_RECLAIM_MS`) 폴링하며 기다렸다가 잡고,
그래도 안 되면 폴백하되 어떤 포트를 원했고 왜 못 잡았는지 남긴다.

부수적으로 드러난 결함 셋:

- **`daemon restart` 가 posture 를 잃었다.** 9120 을 맹목 probe 했으므로 데몬이 폴백
  포트에 있으면 posture 를 못 읽었고, "posture 없음" 은 "개방 posture" 와 구별되지
  않는다 — enterprise 설정이 조용히 풀리는 경로다. 이제 **실제 포트에서 읽고 stop,
  선호 포트로 start** 한다.
- **"물어본 포트" 판정이 항상 참이었다.** commander 의 `-p` 기본값이 `"9120"` 이라
  `if (opts.port)` 는 언제나 truthy 였고, 그 아래 "폴백 포트로 시작한다" 분기는 도달
  불가능한 죽은 코드였다. 기본값을 제거해 부재와 명시를 구별한다.
- **`daemon status` 가 남의 데몬을 자기 것으로 보고했다.** 자기 레지스트리에 데몬이
  없으면 9120 을 맹목 probe 하는데, 한 머신에 두 번째 AgentDeck 이 있으면 그쪽이
  답한다. "이 데몬은" 으로 시작하는 주장은 레지스트리에서 해석된 포트로만 한다.

포트 창 고갈 메시지도 §1.5 대로 고쳤다. 예전 문구 "Stop an existing session first" 는
공유 머신에서 실행 불가능한 조언이다 — 다른 OS 사용자의 포트는 이 레지스트리에
보이지 않고 bind 거부로만 나타난다. 이제 자기 세션이 쥔 포트와 레지스트리 밖 포트를
따로 세고, 자기 것이 0이면 세션을 멈추라는 말을 하지 않는다.

### 검증

운영 데몬(9120)을 건드리지 않고 `--port-window 9200-9209` + 분리된 `AGENTDECK_DATA_DIR`
로 일회용 데몬을 띄워 실측했다 — #211 이 만든 그 격리 창의 첫 실사용이다.

| 시나리오 | 결과 |
|---|---|
| 포트 비어 있음 | 9200 bind, `Preferred port 9200 (AGENTDECK_DAEMON_PORT)` 로그 |
| 8초 점유 후 해제 | 20초 예산 안에서 대기 → 해제 **144ms 뒤** 9200 bind ("came free — bound it instead of falling back") |
| 45초 계속 점유 | 20.1초 대기 후 폴백 9201, 선호 포트·이유·복구 방법 로그 |

중간에 결과가 한 번 엇갈렸는데(홀더가 살아있는데 "came free"), 이전 셀의 잔여
프로세스 오염이었다. 홀더 생존 여부를 3초마다 `lsof` 로 같이 찍는 계측을 붙여
재실행하니 재현되지 않았다 — 계측을 먼저 믿을 만하게 만들지 않았으면 없는 버그를
쫓을 뻔했다.

`daemon status` 의 폴백 안내와 `daemon port` 저장/조회/삭제도 실제 CLI 로 확인했다.

### 남은 것

`daemon restart` 없이 **실행 중에** 선호 포트를 되찾는 것(라이브 리스너 이전)은 하지
않았다. 포트는 bind 시점에 mDNS TXT, UDP 비컨 payload, adb reverse 매핑, `daemon.json`,
`BridgeCore` 로 퍼지므로 이전은 그 전부를 옮기는 일이고, 지금 얻는 것보다 깨질 표면이
넓다. 폴백은 이제 (a) 대부분 일어나지 않고, (b) 일어나면 보이고, (c) restart 한 번으로
풀린다.
