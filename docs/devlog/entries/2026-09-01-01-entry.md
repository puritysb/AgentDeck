# 2026-09-01 — 페어링은 기기가 아니라 운영자가 하고, 포커스된 세션은 자기 자신과 매칭돼 크리처를 잃고 있었다

### 문제

세 기기가 "안 붙는다"로 보였는데 원인이 셋 다 달랐다. Pantone6 는 자격증명이
없어 초당 노크 중이었고(3주치 로그에만 쌓임), Crema S 는 앱이 멈춰 있었고,
Lenovo 는 adb 트랜스포트가 사라져 있었다. 증상은 하나인데 원인이 셋이라
한 곳만 보면 매번 틀린 결론이 났다.

그 바닥에는 공통 구조가 있었다. 페어링의 세 경로 — QR, 6자리 코드, 32자리
토큰 — 는 전부 **기기에게** 무언가를 요구하는데, 정작 페어링이 필요한 기기는
카메라도 키보드도 없는 e-ink 리더다. 6자리 코드조차 mDNS 발견에 걸려 있어,
멀티캐스트가 막힌 망에서는 대상 기기에게만 닿지 않는다.

별건으로, 포커스된 세션의 크리처가 렌더되지 않았다. 타임라인은 정상이라
"연결은 되는데 크리처만 없는" 헷갈리는 모양이었다.

### 해결

**승인 방식**: 데몬은 이미 필요한 걸 다 알고 있었다 — 인증 안 된 LAN 피어를
핸드셰이크에서 거절하고 주소를 로그에 남긴다. 그걸 화면에 올렸다
(`WAITING TO CONNECT` + `/pair/knocks|approve|revoke|dismiss`). 기기는 아무것도
하지 않는다. 실측: 승인 후 10초 내 연결, 기기 조작 0회.

**개별 승인**: 신원이 IP 면 NAT 뒤에서 한 대 승인이 전체 승인이 된다.
클라이언트가 핸드셰이크에 설치별 랜덤 id(`x-agentdeck-device`)를 싣고 데몬이
그걸로 키잉한다. 실기기 2대 교차 검증 — 승인된 id 가 .53 과 .50 양쪽에서
통과하고, 다른 id 와 헤더 없는 다이얼은 거절, 회수하면 다시 거절.

**크리처**: `isDaemonLike` 가 "형제 중 내 agentType 과 같은 게 있나"를 물었는데
`siblingSessions` 는 자기 자신을 포함한다(형제 루프마다 id 로 건너뛰는 코드가
그 증거). 술어가 `agentType != null` 로 붕괴해 primary 크리처 4갈래가 전부
막혔고, 형제 루프는 자기를 건너뛰므로 양쪽에서 빠졌다. 같은 식이 TUI·macOS
에도 있어 셋 다 좁혔다.

### 핵심 설계 결정

- **주소 폴백은 선택이 아니다.** 현장의 모든 기기가 device-id 헤더보다 앞서
  나갔으므로, 없애면 업그레이드가 곧 플릿 전체 장애다. 대신 UI 가 두 종류를
  구분해 표시한다 — 주소 스코프만 DHCP 변경에 만료되므로.
- **승인은 증명이 아니다.** 평문 `ws://` 이므로 device id 는 수동 관찰자에게
  노출된다 — 지금도 모든 기기가 `?token=` 을 그렇게 나른다. 얻는 건 기밀성이
  아니라 입도와 폐기 가능성이다. 위조 불가 신원은 평문 아닌 채널의
  challenge-response 가 필요하고, 그건 별개 작업이다.
- **저장된 승인은 마이그레이션한다.** 스키마가 바뀌었다고 디코드 실패로 두면
  "아무도 승인되지 않음"으로 읽혀 이미 승인한 기기가 조용히 전부 끊긴다 —
  tmp+rename 이 막으려는 것과 같은 결과가 디스크가 아니라 스키마로 들어온다.
- **fixture 가 프로덕션에 없는 모양을 만들면 회귀가 영원히 숨는다.** 크리처
  테스트는 `siblingSessions` 를 비운 채 primary 를 만들었는데, 데몬은
  `sessions_list` 에 포커스된 세션을 포함해 전부 보낸다. 와이어대로 구성한
  테스트 3개를 먼저 실패시키고 고쳤다.
- **같은 식이 여러 표면에 있으면 같이 좁힌다.** Android(크리처 소실),
  TUI(옥토퍼스 누락), macOS(무증상) 셋 다 같은 실수였다. 한쪽만 고치면 남은
  둘이 드리프트로 남는다.
