# 2026-10-28 — The App Store app aborted right after reclaiming 9120: a hook check wrote `@Published` from the daemon actor

During the npm 1.9.5 three-mode soak, the delivered App Store build **1.9.2 (9401)** was launched while 9120 was still held after a Node daemon stop. It fell back to 9121 at 11:57:26Z, reclaimed 9120 at 11:59:34Z, and died with SIGABRT at 11:59:35.7Z (`AgentDeck-2026-10-28-205941.ips`, macOS 27.0.1).

**The crash.** The triggered thread was `com.apple.root.user-initiated-qos.cooperative`, not main. From the bottom up it ran: a Swift task → app frames → `Published.subscript.setter` → `ObservableObjectPublisher.send` → SwiftUI `AppGraph.graphDidChange` → `AppMenuBarExtrasController.updateMenuBarExtras` → `-[NSStatusItem setVisible:]` → `NSAssertionHandler`. The App scene observes `AppPreferences` (`@StateObject preferences`), so any `@Published` write on that object re-evaluates the `MenuBarExtra` on whatever thread made the write. AppKit asserts that a status item is touched on main.

**Which write.** The Store binary is stripped and the CI artifact for run 39964340470 carries no dSYM, so the app frames could not be symbolicated. The app's own `swift-daemon.log` shows the last line before the abort was step 11 of `DaemonServer.startServices` after the reclaim: `[Hooks] Already installed, no changes needed`. That branch sets `AppPreferences.shared.hooksInstalled = true`. `DaemonServer` is `@DaemonActor`. `HookInstaller.installIfNeeded()` was not actor-annotated, so the call compiled and ran on the daemon's executor. A `@Published` setter publishes even when the value is unchanged. Step 11b, `CodexConfigInstaller.installIfNeeded`, had already been made `@MainActor` and wrapped in `MainActor.run`. The Claude installer was the one left behind.

**It is a race, not a deterministic abort.** The same write ran at the first startup on 9121 (11:57:26Z) without a crash. In row 3 of the soak the same 9401 process reclaimed 9120 at 12:36:44Z, ran the same step and survived. One abort in three observed passes is a measurement, not a rate. The trigger is any `startServices` with Claude hook consent accepted. The reclaim after a fallback is just the most common way to get a second one. 9801 (in review on this date) and master carry the identical call.

**Fix.** `HookInstaller.installIfNeeded`, `uninstall` and `uninstallAndRevoke` are `@MainActor`, so Swift 6 refuses a synchronous call from another actor. Step 11 hops with `MainActor.run`, exactly like 11b.

**Not swept here.** `AgentStateHolder`, `TimelineStore`, `DisplaySyncService`, `BridgeConnection`, `BridgeDiscovery`, `LocalSessionDiscovery` and `AppPreferences` itself are `ObservableObject, @unchecked Sendable` with no actor annotation. The compiler will not stop a daemon-actor write to any of them. Making `AppPreferences` `@MainActor` is the structural fix, but it touches every reader of a preference from the daemon and was not done in this patch.
