# 2026-09-10 — 하루에 123번 "깨어난" 데몬: 늦은 타이머는 수면이 아니다

#308 유도 실험 중 데몬이 `/health`에 답을 안 하고 앱이 승격↔복귀를 5분에 3번 반복하는 걸 잡았다.
처음엔 wake 직후 복구 폭풍으로 보였는데, `pmset -g log`에는 **오늘 sleep/wake 이벤트가 0건**이고
`daemon-stderr.log`에는 `System wake detected — recovering devices`가 **123건**, 피크엔 1~4분마다.
로드 애버리지 13~17.

원인은 `bridge-core.ts`의 wake 감지기: 5초 `setInterval`이 직전 틱보다 15초 이상 늦게 도착하면
"수면에서 깼다"로 읽었다. 이벤트 루프가 굶으면 정확히 그 모양이 난다. 그리고 그 판정이 돌리는
복구(mDNS 재발행, 보드 20대 pairing 재무장, BLE 워커 재시작, usage 재조회)가 다음 틱을 굶겨서
**감지기가 자기 자신을 먹였다.** 복구 중엔 `/health`가 답을 못 하니 앱이 "9120 사라짐"으로 읽고
9121/9122로 승격, 1분 뒤 다시 클라이언트 — #305/#306 의 기계가 설계대로 돌면서 플랩만 남겼다.

증거 순서: `sample`은 메인 스레드가 HTTP 핸들러 안 JS에서 89% CPU → 4초 뒤 CPU 프로파일은 86%
idle인데 `/status`·`/health` 모두 무응답(핸들러가 뭔가를 await) → 인스펙터마저 타임아웃(완전 블록).
버스트다. 새 데몬(오늘 머지 빌드)도 5분 만에 같은 증상 → 코드 회귀가 아니라 환경(부하).

수정: **드리프트**. 실제 suspend에서는 wall clock은 뛰고 `CLOCK_MONOTONIC`(Darwin/Linux)은 안 뛴다;
부하에서는 둘이 같이 간다. `classifyClockTick`이 `wake | lag | normal` 을 순수 함수로 판정하고 lag은
로그만 남긴다. Windows는 monotonic이 sleep 중에도 흐르므로 gap 규칙을 유지하고 약한 계측임을 적었다.
변이 확인: 드리프트 비교를 gap-only로 되돌리면 "같이 간 30초=lag" 테스트가 빨개진다.

부하의 원인 자체(AgentDeck 앱 37%·WindowServer 33%·iTerm 23%)는 별건이고 데몬 밖이다.

#308 은 정책을 `ask=on-miss`로 바꿔도(오너 허가) 승인이 뜨지 않았다 — `security=full`이면 `ask`가
소용없다. `security=allowlist`로 바꿔야 하는데 데몬이 위 상태라 중단하고 원복했다(`ask=off` 확인).
