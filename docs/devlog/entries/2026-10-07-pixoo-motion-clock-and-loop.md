# 2026-10-07 — Pixoo64 motion: wall-clock simulation and an opt-in device loop

The owner reported that the usage strip looked right but that creature and aquarium motion on the Pixoo64 looked slow and unnatural. Read-only measurement on the running Node daemon showed `animationMode: "single-frame"`, `failures: 0`, and 14 pushes in 40 s at about 2.7–3.1 s each (the 2.5 s active cadence plus the upload). `Channel/GetAllConf` answered in 32–41 ms and ping lost no packets, so WiFi was not the limit. Two problems in the renderer caused the slow look:

- **Integrated motion followed the call rate, not the clock.** The tetra school, bubbles and data particles moved one 100 ms tick per `renderFrame()` call. The device renders once per push, so the school and bubbles ran at about 1/25–1/30 of their designed speed and looked frozen. An open 10 fps `/pixoo` preview stepped the same shared state and sped it up again. The renderer's own comment said motion should not depend on "who/how often calls renderFrame()"; the oscillators met that rule but the integrators did not. Each render now replays the ticks that have elapsed since the last render, capped at 30 (`consumeSimulationTicks`, mirrored in Swift `PixooRenderer`).
- **Oscillators were sampled far below their period.** The creature bob (2.2 s period), sparkle orbit (2.9 s) and seaweed were sampled once every ~2.8 s, so each push landed at an effectively random phase and the motion looked jittery. A single frame cannot fix this at a safe request rate. Smooth motion needs the device to play a loop.

**Multi-frame upload.** The 2026-06/07 attempts that caused REST timeout and 60–87.5% ping loss sent every frame concatenated into one `PicData` at `PicOffset: 0`, with `PicNum: N`. The Divoom API expects one request per frame instead: the same `PicID` and `PicNum` on each, `PicOffset` set to the frame index, and one frame per `PicData`. `pushFrames` now uploads that way, sequentially, 120 ms apart, and aborts on the first failure (`buildSendHttpGifCommands`). Each body is the same size as a proven single-frame push. A single-frame push is unchanged.

**The loop is opt-in and has not been validated on hardware.** Setting `"animation": "loop"` on a `pixooDevices` entry bakes 8 unique frames, rendered 200 ms apart, into a 14-frame palindrome that plays at 200 ms per frame. That is about 5 fps on the panel, compared with about 0.35 fps from single-frame pushes. Because the loop is a palindrome it closes by construction, so it meets the baked-loop rule. The school and bubbles stay frozen within one loop and advance between uploads. The loop is re-uploaded on a state change (3 s floor) and every 10 s. A failed upload switches that device to single frames for 15 minutes. The default stays single-frame, because the earlier failure was measured on this panel and the corrected protocol has not been pushed to it yet. The Swift daemon stays single-frame and gets only the clock fix.

Verification: `pnpm build`, `pnpm typecheck`, `pnpm test`, `bridge/src/__tests__/pixoo-motion.test.ts` (tick replay and cap, per-frame request shape, palindrome closure, opt-in default, cooldown), and a Swift `IDotMatrixProtocolTests` case for the clock. Preview frames were rendered outside the repository. Before enabling the loop by default, check on hardware that a loop upload keeps `failures: 0`, loses no pings, and does not show a loading screen.
