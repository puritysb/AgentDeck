# 2026-08-19 — 세 토폴로지는 상태여야 한다: 불리언 두 개로는 teardown 과 승격이 구별되지 않는다 (#230, #231)

### 문제

"Swift 데몬 단독 / CLI 데몬 단독 / 둘 동시" 세 경우 모두에서 기능이 완결적으로
동작하는지 테스트 셋을 감사했다. 토폴로지**별** 동작은 탄탄했다 — 토큰 수렴, 인계
협상, 포트 우선순위, 포스처 축, `/health` 와이어 파리티가 양쪽에 다 있었다.
비어 있던 건 토폴로지 **사이의 전이**였다.

`isUsingExternalDaemon` 은 UI 6곳을 게이팅하고 `didSet` 부수효과까지 달고 있는데
테스트가 0건이었고, 쓰기 지점이 10곳이었다. 그중 하나가 `stop()`:

```swift
isRunning = false
isUsingExternalDaemon = false   // didSet: oldValue && !new ⇒ "소유자로 승격"
```

클라이언트 모드에서 종료할 때도 승격과 **똑같은 값**을 쓰므로
`onPromotedToOwner` → `clearRelayedUsageState()` 가 발화해 Claude 5H/7D, Codex
rate limits, 구독, Antigravity 상태를 지웠다. `restart()` 가 `stop()` 을 부르고
설정의 포트/포스처 변경이 `restart()` 를 쓰므로, **외부 Node 데몬에 붙은 상태에서
설정만 건드려도 usage 게이지가 전멸**했다.

같은 날 두 번째 사례가 릴레이 경로에서 나왔다. Tier 1 나이 게이트가

```swift
if let fetchedAt = json["fetchedAt"] as? Int, fetchedAt > 0 { …5분 게이트… }
```

한 줄로 세 가지 일을 했고, 조건 실패 시 **블록 전체가 건너뛰어져** 5분 창을 잃고
`usage["fetchedAt"]` 도 안 채워졌다. 호출자가 `Date()` 를 찍어 나이 미상 값이
"방금 가져옴"이 되었고, 그건 `usageStaleTTL` 이 영원히 은퇴시킬 수 없는 유일한
읽기다. 이 분기는 Node 가 모든 결과에서 시계를 밀던 동안 도달 불가였는데,
Node 가 "실패한 fetch 에서는 시계를 안 민다"로 고쳐지자 `{숫자, fetchedAt: 0}`
쌍이 처음 생기며 살아났다.

### 해결

**#230** — `DaemonOwnership` 이 세 상태(`.none/.selfOwned/.external`)와 세 가지
변경 사유(`.tookOwnership/.becameClient/.toreDown`)를 이름 붙인다. `promotes()` 는
external→owner 엣지에서만 참이다. 10개 쓰기 지점이 전부 `changeOwnership(_:)` 을
지나고, 발행 프로퍼티는 파생값으로 남겨 뷰 바인딩은 그대로다. 테스트 10개는
**전이 시퀀스**를 구동한다 — 이 결함은 쌍으로는 안 보이고 `client → 설정 restart
→ client` 흐름에서만 드러난다.

**#231** — `UsageRelay.classify` 가 스탬프의 답을 `.usable/.tooOld/.unknownAge`
로 나눈다. `else { lastApiFetchTime = Date() }` 두 분기는 시계를 그대로 두고
`apiUsageStale` 을 세운다.

**#230 부수** — `timeline.json` 계약이 한 방향으로만 고정돼 있었다. 두 데몬이
번갈아 소유하는 유일한 파일이라 인계는 곧 "한 구현이 다른 구현이 쓴 걸 읽는" 일인데,
Node 는 양방향을 다 검증하고 Swift 는 자기 파일만 왕복했다. 반대 방향 5케이스 추가.

### 핵심 설계 결정

**엣지는 "플래그가 어떤 값이 됐다"가 아니라 "무엇에서 무엇으로 갔다"다.** 값 하나가
두 상황을 뜻하면 호출자는 구분할 수 없다. 오늘 같은 계열이 세 건 나왔다 — teardown
대 승격, 실패한 읽기 대 신선한 읽기, 스탬프 없음 대 있음. 고치는 수는 셋 다 같다:
**나이나 결과를 값에 실어라**(`DaemonOwnershipChange`, `{data, fresh}`, 생산자의
`fetchedAt` 을 재스탬프 없이 전달). 찾기 어려운 이유는 틀린 버전이 항상 전체적으로
보이기 때문이다 — 모든 분기가 뭔가를 돌려주고 모든 대입이 일어난다. 빠진 건
케이스가 아니라 **구분**이다.

**`.unknownAge` 를 `.tooOld` 에 합치지 않는다.** `0` 을 타임스탬프로 읽으면
1970(=우연히 ancient)이라 증상은 같아 보이지만, 생산자가 말하는 건 "한 번도 안
가져왔다"이지 "오래 전에 가져왔다"가 아니다. 합치면 다음 사람이 `0` 이 실제
케이스였다는 걸 알 방법이 없다. 저장소가 `capturedAt` 에 대해 이미 세운 규칙과 같다.

**"현재 경로에서 도달 불가"는 코드가 아니라 다른 컴포넌트의 현재 동작에 대한
주장이다.** 그 컴포넌트가 바뀌면 조용히 만료된다 — 실제로 몇 시간 만에 만료됐다.
방어 분기는 그 자체로 옳아야 한다.

**fixture 는 실제 파일에서 복사한다.** 디코더의 필드 목록을 보고 지어낸 fixture 는
절대 실패하지 않으므로 포맷 갭이 green 스위트를 그대로 통과한다. 교차 데몬 테스트의
fixture 는 실제 `~/.agentdeck/timeline.json` 에서 그대로 가져왔다.

**남은 부채**: `DaemonService.init()` 이 `start()` 를 호출해 포트를 바인드하므로
서비스 자체에 테스트 seam 이 없다(테스트에서 9120 을 잡거나 실행 중인 진짜 데몬에
붙는다). 그래서 테스트는 추출한 `DaemonOwnership` 을 구동한다. 라이프사이클을 직접
테스트해야 하면 그 initializer 부터 쪼개야 한다.
