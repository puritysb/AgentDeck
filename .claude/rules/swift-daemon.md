# Swift daemon and macOS app
<!-- Moved verbatim from the root map (then CLAUDE.md, 2026-09-10; AGENTS.md since 2026-09-29). Rule bodies are the SSOT for their domain; the root map keeps only the index. -->
Rules for the in-process Swift daemon (`@DaemonActor`), the SwiftUI app lifecycle, and Foundation traps. The
App Store invariants are in [apple-release.md](apple-release.md); daemon lifecycle shared with Node is in
[daemon-lifecycle.md](daemon-lifecycle.md).

## Isolation and windows

- **Swift daemon isolation**: the macOS in-process daemon runs on **`@DaemonActor`** (`apple/AgentDeck/Daemon/Core/DaemonActor.swift`), NOT `@MainActor` — it is hosted in the GUI app, and sharing the main executor let a busy render loop starve it. New rule: a type holding daemon state is `@DaemonActor`; UI types stay `@MainActor` and are reached with `await`. **Never write a `@convention(c)` callback inline inside an isolated method** — it inherits that isolation statically, a function pointer cannot carry it, and Swift compiles in an executor assertion that traps at runtime (this killed the app via the IOKit power callback). Declare such callbacks at file scope. Swift 6 mode verifies data races but cannot see this. See [docs/architecture.md § Swift daemon isolation](../../docs/architecture.md)
- **`NSApp.windows` is not a list of the app's windows, and SwiftUI always shows the first `Window` scene.** `NSApp.windows` also contains the panel backing `MenuBarExtra`'s `.window` style, status-item windows and AppKit internals, none of which carry a scene identifier — so a rule phrased as a COUNT ("are any windows open?") never reaches zero and silently never fires. Phrase it as an **allow-list of scene ids** (`DockVisibilityPolicy.trackedWindowIDs`, which must list every `Window(id:)` in `AgentDeckApp.body`). A miniaturized window still counts as open (`isVisible` is false while miniaturized, and treating it as closed strands its Dock tile), while a *closed* SwiftUI `Window` scene stays in `NSApp.windows` with `isVisible == false` — the identifier alone cannot tell closed from open. Separately, **`.defaultLaunchBehavior(.suppressed)` does not apply to the first `Window` scene**: with no saved application state the Dashboard's NSWindow is created and visible anyway, which is why `openDashboardOnLaunch` did nothing for its whole life and why the preference is honoured by CLOSING the window macOS opened rather than declining to open it. Consequence for anything that must run once per launch: it cannot live in the Dashboard's `.task`, which never runs for a menu-bar-only user — `configureDaemonConnection()` rides the `MenuBarExtra` label instead. Ref: `apple/AgentDeck/App/DockVisibilityController.swift`, `apple/AgentDeckTests/DockVisibilityPolicyTests.swift` (measured 2026-08-18).

## Self-restart, handover and teardown

- **A self-issued restart must be scheduled, never called inline, and must not be the only safety net.** `DaemonService.start()` guards re-entry with `isStarting` and clears it in its Task's `defer`, so any `start()` reached from *inside* that Task (the `alreadyRunning` catch → `connectToExternalDaemon`) is silently swallowed — no log, no retry. Always re-enter via `Task { @MainActor [weak self] in self?.start() }` so the defer runs first; three call sites already did, one didn't, and that one left the app daemonless for 22h (2026-08-07). The deeper rule is what made it unrecoverable: the same branch also set `port = 0`, and `checkDaemonHealth` starts with `guard currentPort > 0` — so the failed hand-off *also* neutered the watchdog that existed to catch it. **Code that schedules a retry and code that clears state must not share a failure mode**; a guard that can drop a request silently needs a log line at minimum. **The same pair bit again on a different branch** (#305, 2026-09-10): `connectToExternalDaemon`'s port-resolution failure was the one exit in that function with no rescheduled `start()`, and it too set `port = 0` — 23 h daemonless AND clientless. It fired TWICE that day and survived the first only by luck — a concurrent `Daemon listener bind failed` re-entered `retryOrFallback` — so the branch is reached routinely and is terminal whenever nothing else happens to be retrying. It is reached from the in-process server's own `onShutdown` handler, which calls `connectToExternalDaemon()` with NO port at the one moment the registry is guaranteed empty (our `daemon.json` row going away, the incoming CLI daemon not bound yet — it is waiting out our teardown plus the ~14 s NECP hold), so `resolveExternalDaemonPort` ends known › registry › **canonical port**: a wrong guess self-heals through the stale-registry retry, nil could not. Node's four Swift-eviction sites now go through one `evictSwiftDaemon` preferring **`/stand-down`** over `/shutdown` — the difference is that stand-down TELLS the app which port to become a client of — and `stopDaemon` takes a `handover` flag saying a daemon is coming BACK on this port (restart, install convergence), which is what licenses stand-down there; plain `daemon stop` keeps `/shutdown`, because there "become a client" is a lie and the app would re-promote after its yield window, stopping nothing. Second half of that wedge, fixed by the same change: `AgentStateHolder.preferredLocalBridgeUrl` is written ONLY by `daemonService.onReady`, so a DaemonService that never reaches a terminal state leaves the pin on the app's own dead port and the state holder's ladder cannot find the CLI daemon either. Diagnostic signature: process alive but its log stops dead at one timestamp, `CLOSED` sockets to the daemon port that ACCUMULATE and are never replaced, frozen `nettop -P -x` byte counters across more than one health tick, and `sample <pid> 3` with zero daemon/websocket/reconnect symbols — CPU is a red herring, the terrarium canvas keeps it at ~36% either way. Related: `isPortBindable` (raw BSD socket) can report free while NWListener still fails EADDRINUSE (NECP), so observed bind failures are remembered with a TTL (`failedBindPortsAt`) and outrank the probe — clearing that memory on stand-down is what made reclaim thrash. Ref: `apple/AgentDeck/Daemon/DaemonService.swift`, `apple/AgentDeckTests/DaemonPortFallbackTests.swift`
- **`server = nil` is not a teardown, and a transition may not write state about a daemon that replaced the one it was called for.** `connectToExternalDaemon` probes over the network with timeouts (the patient probe waits out the ~14 s NECP hold) and is reached from inside `start()`'s own Task, so `start()` can complete a bind, assign `self.server` and wire every module while it is suspended — after which its exits described a daemon that no longer existed and dropped the live one. A started `NWListener` is retained by Network.framework until it is **cancelled**, and its `newConnectionHandler` holds the server weakly, so the orphan kept `*:9121 (LISTEN)` for the life of the process and accepted connections it then answered for nobody (six `CLOSE_WAIT` sockets overnight) — on a port inside the session-bridge range 9121-9139. Two rules, and the first is the fix: every exit re-checks `inProcessDaemonEpoch` (bumped only where `start()` takes ownership) and **abandons** the transition when a newer daemon owns the port; and every exit that clears in-process state goes through `releaseInProcessDaemon()`, which shuts the server down first. The client-handover exit is guarded too — becoming a client while a live in-process daemon holds a port is the same lie. Not a regression from #305: its fix is what let the promotion cycle run to completion, which is how this became visible. `WebSocketServer.start` additionally cancels any listener it replaces, since `stop()` only ever cancels the current one. (#306, measured 2026-09-09/10 — DEVELOPMENT_LOG.)
- **A transition is not a value, and a value that means two things cannot be told apart by its reader.** Three defects of one shape landed together (2026-08-19). `DaemonService` carried the machine's daemon topology — **no daemon / in-process Swift / external Node with this app as its client** — as two independent booleans and inferred the *promotion* edge from a `didSet` across ten write sites; `stop()` is one of them, so tearing down while in client mode wrote the same `false` a promotion writes, fired `clearRelayedUsageState()` and blanked every usage gauge — and since `restart()` calls `stop()` and Settings uses `restart()` for a port or posture change, editing either setting while attached to a Node daemon wiped them all. On the Node side every failure branch of `fetchUsageFromApi` returned `fileCache?.data ?? null`, making a failed read indistinguishable from a live one. And Tier 1's age gate (`if let fetchedAt = …, fetchedAt > 0`) skipped its whole block when the stamp was absent or `0`, losing the window *and* leaving the payload unstamped, after which the caller wrote `Date()` on it. **Put the outcome or the age on the value** (`DaemonOwnershipChange`, `{data, fresh}`, the producer's `fetchedAt` carried through rather than restamped) instead of leaving the reader to infer it from the value's shape — the wrong version always looks total, because every branch returns something and every assignment happens; what is missing is a distinction, not a case. Two corollaries: **"unknown" is its own answer** (`.unknownAge` must not fold into `.tooOld` even though a `0` stamp reads as 1970 and gets skipped by accident — the producer is saying "never fetched", not "fetched long ago"); and **"unreachable on current paths" is a claim about another component's present behavior, not about the code** — that `Date()` branch was genuinely dead until the Node daemon stopped advancing its clock on a failed apply, so a defensive branch has to be correct on its own terms. SSOT `apple/AgentDeck/Daemon/Core/DaemonOwnership.swift`, `UsageRelayFreshness.swift`; gates `DaemonTopologyTests` (drives transition *sequences* — the teardown bug is invisible as a pair and only shows as `client → settings restart → client`), `UsageRelayFreshnessTests`. Seam debt: `DaemonService.init()` calls `start()` and binds a port, so the service has no test seam — split that initializer first if the lifecycle ever needs direct coverage.

## Foundation and async traps

- **An ObjC exception is not a Swift error, and `try?` does not catch it.** `JSONSerialization.data(withJSONObject:)` *raises* `NSInvalidArgumentException` for anything that is not a valid top-level JSON container — so `try? JSONSerialization.data(withJSONObject: someAny)` reads as safe and is a `terminate`. A trajectory event whose `input` was a bare String aborted the whole app from a background APME eval task, taking the daemon and every device connection with it (2026-08-06). Any Foundation API documented to *raise* needs a **precondition check**, not a `try?`: `guard JSONSerialization.isValidJSONObject(x)` first (it validates recursively, so it also covers a `[String: Any]` whose leaves are not JSON). Applies wherever untyped `Any`/`[String: Any]` from hooks, gateway payloads or the timeline is serialized — `ApmeScorers`, `ApmeCollector`, `[String: Any].jsonData`; `compactDebugValue` in `DaemonServer.swift` is the pattern to copy
- **External peer async I/O**: 모든 RPC/WS/HTTP `await` 에 timeout 강제 — peer silence (silent drop, dead socket, network glitch) 를 first-class signal 로 처리해야 함 (synthetic error code emit + UI status emit + retry/fallback escalation). race condition 가드는 secondary; timeout 이 먼저. Reference 구현: `apple/AgentDeck/Daemon/Gateway/OpenClawAdapter.swift` 의 `connectRPCResponseTimeoutNanoseconds` + `completeRPCTimeout` + `handleConnectTimeout` 패턴
- **A progress indicator binds to bounded work, and the bound is structural**: a spinner may only reflect an attempt that is guaranteed to end. Never drive one from a subscription that is *designed* never to finish — `BridgeDiscovery.isSearching` reports the long-lived Bonjour browser (kept alive so a Mac appearing later is still found), and rendering it as progress is what got iPhone/iPad 1.0.2 (3901) rejected under App Review Guideline 2.1(a). Splitting the signal is only half the fix: the bounded flag then has many exits (discovery hit, saved-URL fallback, the reconnect ladder, an explicit user stop) and any one that forgets to clear it restores the same symptom — a socket-level `disconnect()` knows nothing about the waterfall above it. So funnel the flag through `begin*()`/`end*()` and arm **one deadline per run** that clears it whatever stage is in flight (it must not tear down the socket — live work keeps its own `connecting` phase and can still succeed). Two corollaries: every stop must land on a **recoverable terminal state**, and a visible retry must never no-op on a leftover stage guard, so `retry*()` (ignores the guard) is a separate entry point from `start*()` (respects it). Testing the phase-resolution function is not a regression gate — it mirrors its inputs and stays green with the flag stuck true; drive the real state machine with an injected deadline instead. Ref: `apple/AgentDeck/State/AgentStateHolder.swift` (`beginForegroundSearch`/`endForegroundSearch`/`stopConnectionAttempts`/`retryConnectionWaterfall`), `apple/AgentDeckTests/ConnectionOverlayTests.swift`.
