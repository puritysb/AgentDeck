# ESP32 firmware, flashing and serial ownership
<!-- Moved verbatim from the root map (then CLAUDE.md, 2026-09-10; AGENTS.md since 2026-09-29). Rule bodies are the SSOT for their domain; the root map keeps only the index. -->
Release images, the two flashers (`/flash/` and `agentdeck esp32 flash`), post-write reset, the serial-suspend
lease, and serial teardown. Provisioning/OTA/client contract live in [esp32/AGENTS.md](../../esp32/AGENTS.md)
and [docs/esp32.md](../../docs/esp32.md). Heap discipline is the `esp32-heap-discipline` skill.

## Board map

- **esp32/** — PlatformIO Arduino firmware (LVGL touch displays + WS2812B matrix + **TRMNL 7.5"** e-ink). **TRMNL 7.5"** is a Seeed TRMNL 7.5" OG DIY Kit (XIAO ESP32-S3 Plus + 800×480 UC8179 e-ink), always USB-powered, driven by custom AgentDeck firmware (PlatformIO env `trmnl_75`, WiFi/WS to the daemon like other ESP32 boards). The allocation-free responsive e-ink geometry SSOT is `esp32/src/ui/eink/eink_dashboard_layout.h`; TRMNL 7.5" consumes it directly, `scripts/sync-xteink-eink-dashboard.sh` mirrors it into the external `crosspoint-agentdeck` X3/X4 fork (whose GfxRenderer remains hardware-specific), and `Trmnl75Preview.swift` pins it. Its `Density` bands key off the **short edge only** — orientation is the separate `Layout::portrait` field, so a panel can be `Compact` in either orientation (TRMNL 7.5" 800×480 and XTeink X4 480×800 both are). Firmware is **hardware-verified and ships via WiFi OTA** (`agentdeck esp32-ota trmnl_75`). It is the Seeed kit reflashed, not a TRMNL client: the commercial BYOS HTTP-pull integration was removed, and a stock panel on upstream firmware is unsupported. Shipped as "InkDeck" through 1.2.1; `inkdeck` stays an accepted board alias because a board in the field reports what it was flashed as (`LEGACY_BOARD_IDS`). See [docs/devices.md](../../docs/devices.md#trmnl-75-e-ink-custom-firmware)

## Release image and flashing

- **An ESP32 release ships a merged factory image, and its header is verified against the SSOT before it is published.** `scripts/esp32-merge-firmware.mjs` emits `agentdeck-<board>-merged.bin` written at `0x0` on **every** chip, so no consumer branches on chip family — classic boards keep their bootloader at 0x1000 inside the image behind `0xFF` padding the ROM never reads. Loose bootloader/partitions/app assets cannot bring a board up: `boot_app0.bin` (0xe000) lives in the Arduino framework package rather than `.pio/build/` so a copy step never picks it up (stale otadata then boots the previous slot), and the bootloader offset is chip-specific across three values (`esp32` 0x1000, `esp32p4` **0x2000**, everything else 0x0). Because `merge-bin` patches the flash parameters into its own output, the header can only be checked by reading it back **at the bootloader offset** — `image-info` at 0x0 on a classic merged image lands on padding and fails `invalid magic number: 0xff`. `scripts/generate-firmware-manifest.mjs` publishes `manifest.json` with sha256/size computed **from the artifacts** and fails the release when any SSOT board is missing files; the old failure mode was the opposite — a board shipping nothing while every step stayed green. **Release tooling is pinned, and the pin comes from the registry CI installs from, never from a local probe.** esptool is `5.2.0` (v4→v5 renamed `merge_bin`/`--flash_size`); PlatformIO installs its own esptool EDITABLE into `~/.platformio/penv`, so `pip show` answers a version PyPI never published — that is where the pin came from that failed at tag time with `No matching distribution found for esptool==5.1.2`. Same rule, different tool: `npx --yes esbuild` in a pnpm workspace resolves a transitive copy, skips installing, finds no bin and falls through to `esbuild: not found` (pinning the version does not help — the "already installed?" check matches either way), so package scripts fetch through `pnpm dlx <pkg>@<version>`. Reproduce in a fresh clone (`pnpm install --frozen-lockfile`, `pnpm build`, run the script) before touching either pin. (`esp32-v1.0.7`, `ulanzi-v1.0.4` — DEVELOPMENT_LOG.)
- **A refusal to flash has no override, and it is written once for both flashers.** The two entry points — `/flash/` (`tools/web-flasher/`) and `agentdeck esp32 flash <board>` — do not share their esptool-js driving code (Web Serial vs a `serialport` shim), so the piece that must not drift is the **decision**: `esp32PreflightVerdict` (`shared/src/esp32-boards.ts`) refuses a chip-family mismatch or an image declaring more flash than the part reports, with deliberately no `--force` and no "flash anyway" button — the recovery tool for a bricked board is the tool that refused. Five polarity rules live in that one function. **`webFlash` means "offered in the browser", never "may be written"** — it takes a `surface: 'browser' | 'cli'`, because `esp32_c6_147` has no OTA slot and USB is its only update path, so a CLI inheriting the browser's list would leave it unupdatable by anything. The **size check is directional** (declared ≤ detected): TRMNL 7.5" is physically 16MB with an 8MB BSP field, so an equality test fails the one board doing the correct thing. An unreadable flash id **stays unknown** — `detectFlashSize()` silently answers `"4MB"` when it cannot decode the id, so trusting it turns "I could not look" into a confident wrong number that then gates the write. `imageGeometry` (from the release manifest, resolved separately by `--tag`) is compared too, and that one is **strict equality, not directional**: two sources describing the same board that disagree cannot say which is true, and it is the only size check left when the flash id is unreadable. Its cost is a release-ordering constraint (RELEASING.md), not a defect. And **`eraseAll` is stub-only** in esptool-js, so on a `--no-stub` board it was silently dropped after showing an `erase` phase and `MD5 verified`, handing back a board still carrying the previous owner's credentials — both surfaces refuse rather than skip. Three runtime traps: esptool-js's published ESM has extensionless relative imports Node cannot resolve, so Node consumers go through `bridge/src/esptool-js-node.ts` → `esptool-js/bundle.js`; `calculateMD5Hash` receives the buffer **after** esptool-js patches the flash-params header; and **every teardown await here is bounded** — `Transport.disconnect()` spins in `waitForUnlock()` with no deadline and `Transport.write()` has no `try/finally`, and that teardown sits inside the `finally` the CLI waits on before releasing the daemon's serial lease.
- **Writing the bytes is not installing the firmware, and `esptool-js` will not reset the board for you.** Its non-USB-OTG hard reset is, in full, `sleep(100); setRTS(false)` — a RELEASE with no ASSERT, which works only when the preceding step left EN asserted (`--before default-reset` does; a finished `writeFlash` does not). The chip is left parked in the flasher stub, so the firmware never runs and the post-write `device_info` read-back cannot succeed however long it waits. Both flashers reset through `ESP32_POST_WRITE_RESET_SEQUENCE` (`D0|R1|W100|R0`, `shared/src/esp32-boards.ts`) rather than `after('hard_reset')`. **`D0` is load-bearing**: pulsing EN without first driving IO0 high leaves the CH340 boards in download mode, indistinguishable from a board that failed to boot — and the two adapter classes take different strategies inside esptool-js (`UsbJtagSerialReset` for `0x303a/0x1001`, `ClassicReset` otherwise), so a sequence verified on one is not evidence for the other. Two corollaries. **`stub` and `esptoolFlags` describe different tools** — `stub` drives esptool-js (browser + CLI), `esptoolFlags` mirrors `platformio.ini` for esptool.py, the board-matrix gate cross-checks only the latter pair, and they may legitimately disagree as long as the board's note says why. And **connecting is not writing**: `ttgo_t_display` was `webFlash: true` on evidence that it CONNECTS while pinned `--no-stub` made it unwritable by either surface, so `webFlashVerified` must record a completed write, not a handshake. **"Stubless writing is unsolved" is the wrong frame**: of the remaining `stub: false` boards, two inherited that pin from unrelated commits and have never been USB-attached (unknown, not failing), and the third fails at SYNC, which precedes stub loading in both tools. **A tool's guess about which direction failed is not a measurement** — esptool infers "the serial TX path seems to be down" from a failed round trip on a board whose ROM banner arrives over that very UART. Two instrument traps yield confident wrong answers here: node-serialport's `set()` is `{...defaults, ...options}` with `dtr/rts` defaulting to TRUE, so a partial `set({dtr:false})` asserts RTS, holds EN low and "proves" a silent ROM (borrow `NodeWebSerialPort.setSignals`, never call `set()` directly); and `drain()` times out on this adapter whether or not anything is wrong. Also: only esptool.py's `UnixTightReset` reaches `ips_10`'s download mode, so no built-in esptool-js strategy can get there — `CustomReset` can (`D0|R0|D1|R1|D0|W100|D1|R0|W50|D0`), where the PREAMBLE is load-bearing and atomicity is not. (Measured 2026-08-23 — DEVELOPMENT_LOG.)
- **A serial-suspend lease is a FILE, and it expires when it is read.** Every serial open toggles DTR/RTS and resets the board, so the daemon must let go during a flash — and the daemon that stole the port in the recorded failure was the **respawned** one, which an in-process pause cannot span. `POST /esp32/serial/suspend` (behind the normal auth gate — same-machine is already authenticated, so no standing unauthenticated route is added) writes `~/.agentdeck/esp32-flash-lease.json` and calls `releaseESP32SerialPorts()`: refusing to *open* is only half the job, since a port the daemon already holds still blocks the flasher and two readers on one macOS TTY steal each other's bytes rather than failing cleanly. Expiry is enforced in `readLease()`, **never by a timer** — a timer firing late on a sleeping laptop extends the suspension past what was promised, while a read-time check self-heals when the flasher is killed mid-write. **Honest gap**: the sandboxed Swift daemon cannot read `~/.agentdeck`, so the CLI also runs an `lsof` pre-check (allow-list polarity — an unknown holder is foreign and refuses the start) and always verifies after writing. That pre-check has **three answers, not two**: `lsof` exits non-zero both when nothing holds the file AND when it is missing, times out or hits EPERM, so collapsing those into "free" launders "I could not look" into "nobody is holding it" — the same trap `esp32FlashIdIsUsable` avoids on the flash-size axis, inverted to the permissive direction. **Suspending must also invalidate opens already in flight**: `pollForDevices` holds a port in `openingPorts` across `await openPort()` while the release only sees `connections`, so a suspend arriving mid-open reports `released: 0` and the open then resolves into a live connection whose heartbeat writes JSON into the TTY esptool is writing firmware to. A generation counter bumped on release and re-checked after the await discards it — the same rule as `OpenAttemptToken` in the Swift `ESP32Serial`. MD5 proves the bytes landed, not that the board boots them, so the flasher reopens at 115200 for `device_info` — and **`ulanzi_tc001` skips that by name**, because its CH340 TX is broken in hardware and the check would report a good flash as a failure.

## Serial teardown (Swift)

- **Teardown must invalidate async work it cannot await.** `ESP32Serial.beginOpenPort` opens ports on a `Task.detached`; `stop()` cancels the poll/heartbeat tasks but has no handle on that one. Leaving `openingPorts` populated let an open land *after* `Serial bridge stopped` and start a read loop on a dead module — and the loop holds its `FileHandle` strongly, so `closeOnDealloc` can never fire while it spins. Each daemon restart cycle stranded another reader generation; the app ended up with 34 live read loops holding duplicate FDs on the same 6 ports the Node daemon also owned (two readers on one TTY steal each other's bytes). Teardown invalidates every `OpenAttemptToken` and clears the map, plus an `isStopped` gate. Log signature: `ESP32 opened:` lines immediately after `Serial bridge stopped`
