# Observed sessions, hooks and PERM
<!-- Moved verbatim from the root map (then CLAUDE.md, 2026-09-10; AGENTS.md since 2026-09-29). Rule bodies are the SSOT for their domain; the root map keeps only the index. -->
How each coding agent's session reaches the daemon (Claude/Codex/OpenCode hooks, Kiro transcripts), what a PERM
claim may rest on, how subagents are counted, and the two id forms of an observed session. Hook installer snippet
is mirrored byte-identically in `hooks/src/install.ts`, `setup/src/setup.ts` and `HookInstaller.swift`.

## Hook format and installers

- **Hook format (CRITICAL)**: Claude Code v2.1+ requires 3-level nesting: `{ matcher: "", hooks: [{ type: "command", command: "..." }] }`. The old flat format silently fails. **Every installer targets the user-global `~/.claude/settings.json`** — that plus the two per-project files are the only paths Claude Code watches, so `~/.claude/settings.local.json` (which `localSettings` resolves against the git root / cwd, not `$HOME`) is a dead file at user scope. `installHooks()` writes it; `migrateHooksIfNeeded()` relocates pre-move installs **and rebuilds any hook whose `curl` is still unbounded** (`hasUnboundedHookCurl`), because the file is co-owned with the macOS app and an older app build can overwrite a fixed command set. Codex uses lifecycle hooks in `~/.codex/config.toml` (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `Interrupt`) via `installCodexHooksIfNeeded()`; `PermissionRequest` and `Interrupt` must be **trusted in Codex after installation** — writing the TOML alone does not activate a new hook (CLI 0.149.0 silently omits `Interrupt`; 0.151.0 supports both, timeout ≤3s). Consolidate same-layer user hooks into official `[[hooks.<Event>]]` arrays; the installers preserve and merge those but reject incompatible regular `[hooks]` tables. Kiro v3 uses AgentDeck-owned `~/.kiro/hooks/agentdeck-lifecycle.json`, structurally identical to `buildKiroHookFile()`, every command fire-and-forget even for `PreToolUse`/`Stop`. Scripts use bounded `curl` and `|| true`. Fire-and-forget events **must** keep `--connect-timeout 0.2 --max-time 0.8` (and `--connect-timeout 0.2` on the `/health` probe): Claude gives all SessionEnd hooks one ~1.5s abort budget, so an unbounded POST to a *restarting* daemon (socket open, no reply) is killed and surfaces as `Hook cancelled`. Only Claude's `PreToolUse` (60s long-poll) and `Stop` (10s) are request-response. Every Claude hook curl also sends `-H "X-AgentDeck-Pid: $PPID"` — the hook shell's parent is the agent process and the payload carries no pid, so this is the only consent-free session→process link (the sandboxed daemon cannot read `~/.claude/sessions/<pid>.json`), and it is what attributes a `claude -p` worker to the session whose Bash launched it. Migration 10 rebuilds hooks that lack it. The Claude snippet is mirrored byte-identically in 3 places — `hooks/src/install.ts` (canonical), `setup/src/setup.ts` (inlined because `@agentdeck/setup` bootstraps the workspace), `apple/.../HookInstaller.swift` — change all three together. The bridge keeps no copy; it imports `migrateHooksIfNeeded` from `@agentdeck/hooks` (its former fork silently downgraded PreToolUse/Stop to fire-and-forget).

## Per-agent observation

- **Codex observation**: `agentdeck daemon install` installs/migrates Codex lifecycle hooks in `~/.codex/config.toml`; run `codex` normally. Deprecated `agentdeck codex` still refreshes them before launching its PTY bridge during the compatibility window.
- **Codex Desktop's ambient-suggestions threads fire the user-global hooks, and only their prompt text says so.** When the app refreshes `~/.codex/ambient-suggestions/<project-hash>/ambient-suggestions.json` it runs two internal prompts ("Generate 0 to 3 hyperpersonalized suggestions…" and a "safety and compliance" review) on throw-away threads: no rollout file, no row in Codex's own `threads` table, hook `cwd` `/`. Both daemons minted a `codex-cli` session row, a `chat_start`/`chat_response` pair and a two-second APME turn per refresh (27 turns 2026-07-06 → 2026-09-11, 10 in one night). The hook payload carries no background flag and `cwd: "/"` alone would also match a user who opened Codex at the root, so the thread is classified on its `codex_user_prompt_submit` (`shared/codex-ambient-vectors.json`, replayed by both suites), every later hook on that id is dropped for 30 min of silence, and the `codex_session_start` that preceded the prompt by ~90 ms is retracted (session row forgotten, its still-empty APME run deleted). Real batch work driven by another agent through `codex exec` (thread_source `exec`) is not ambient and stays. `bridge/src/codex-ambient-hooks.ts`, Swift `CodexAmbientHookRules`.
- **Codex's memory-consolidation agent is the same class of background thread, but its cwd identifies it on the first hook.** Codex runs a `memory_consolidate_global` job (`~/.codex/memories_1.sqlite`) as an ephemeral thread whose cwd is its own memory store, `$CODEX_HOME/memories` — no rollout, no `threads` row, and the user-global hooks still fire, so both daemons showed a WORKING Codex creature named "memories" (2026-09-27; the job's `started_at` and the row's `startedAt` were 5 s apart). Because `codex_session_start` already carries the cwd, the thread is dropped before anything is created — nothing to retract. The rule is component-wise (`…/.codex/memories[/…]` or `$CODEX_HOME/memories`), so a user project merely named `memories` is untouched; vectors are `cwdVectors` in the same shared file. The passive observer and the hook-row fallback apply the same predicate as a second line.
- **A dropped Codex background thread must also be dropped from OTel.** The same threads export spans; with their hooks gone no hook row claims them, so the OTel fallback synthesized a cwd-less `Codex` project row (2026-09-29, memory-consolidation and ambient safety threads). Node `CodexOtelTracker.isBackgroundThread` consults `CodexAmbientSessions` and `forget()` retracts a row whose spans beat the identifying hook; Swift `sessionIdForCodexOtelThread` refuses ids in `codexAmbientThreads`. The generator prompt opens with a Markdown heading (`# Overview`) — vectors are copied verbatim from the hook payload, never from a timeline `raw` field that strips it.
- **OpenCode observation**: `agentdeck opencode` / `agentdeck daemon install` install the AgentDeck observer plugin (`~/.config/opencode/plugins/agentdeck.js`) so standalone `opencode` runs report `opencode_*` lifecycle hooks to the daemon — same observed-session timeline pipeline as direct `claude`/`codex` (`classifyObservedHookEvent` in `bridge/src/daemon-server.ts`). The Swift daemon ingests `opencode_*` too: `opencode:<id>` session rows + chat_start/tool_exec/chat_response timeline rows in `DaemonServer.handleHookEvent`, converging with the opt-in SSE observer on the same session key. Both daemons normalize Claude/Codex/OpenCode lifecycle names into the agent-neutral APME boundary vocabulary; Codex response text comes from the rollout tail (`bridge/src/codex-rollout-response.ts`).
- **Kiro observation is passive-first**: users run native `kiro-cli` / `kiro-cli --v3` or Kiro IDE as usual; never add an `agentdeck kiro` managed PTY. The Node daemon correlates processes with Kiro's native stores in `bridge/src/kiro-session.ts` / `passive-observer.ts` — v2 uses macOS app-data `kiro-cli/data.sqlite3` (`conversations_v2`), v3 writes `KIRO_HOME/sessions/<workspace-hash>/<session>/session.json` + `messages.jsonl`. Read SQLite with a read-only/query-only handle and never inspect auth/telemetry tables. `installKiroHooksIfNeeded()` installs AgentDeck's standalone v1 hook file (telemetry-only, never a steering decision), but **installing them buys nothing for CLI chat**: measured 2026-08-17 on kiro-cli 2.18.1, Kiro loads the hooks and then a real `kiro-cli chat` turn fires none of them (marker files proved it; a hand-POSTed hook produced a timeline row normally, so the receiving side was never the problem). That surface belongs to the Kiro IDE agent. **Kiro is therefore transcript-observed on BOTH tiers** — `bridge/src/kiro-transcript-timeline.ts` + `kiro-timeline-feed.ts` (Node), `LocalKiroObserver` + `KiroTimelineFeed` (Swift). The feed admits only the latest turn on first sighting and new rows thereafter, and those bounded rows feed APME too. Two consequences: a Kiro session appears seconds late (polled, `SCAN_INTERVAL_MS`), and state fidelity depends on the record format: nested v3 `payload.type` turn boundaries prove `processing`/`idle`; legacy transcripts use prompt/tool/final-assistant boundaries from the shared generated policy. File mtime determines roster recency, never turn state. Swift parses one bounded snapshot inside the folder-access scope and shares it with the roster and timeline. The sandboxed app reaches `~/.kiro` only through a user-granted security-scoped bookmark (`AppPreferences.withKiroDirectoryAccess`); with no grant it observes nothing rather than guessing. `agentdeck diag kiro [--json]` is the daemon-free, issue-shareable probe — keep its output content-free with report-scoped opaque keys. The Kiro creature uses the pinned `design/brand/kiro.svg`; preserve its geometry and the provenance boundary in `design/RESOURCES.md`.

**Hermes process presence does not renew working activity.** Only idle CLI conversations retain their presence through a live-PID sweep; unconfirmed work still ages out through the existing silence TTL without a successful-completion claim. After an authoritative `hermes_stop`, delayed tool callbacks cannot reopen the turn; a new explicit opening event is required. Node `HermesSessions` and Swift `HermesObserverGate` enforce the same admission boundary.

## PERM and permission prediction

- **PERM is a claim that a human is being waited for, and each agent proves it differently — never by prediction where a real signal exists.** Per-agent sources: Claude Code's `Notification` with `notification_type: permission_prompt` (display-only) and the observed-session PreToolUse **hold** (device Allow/Deny, 25 s); Codex's `PermissionRequest` hook, which fires only when Codex is about to ask (display-only — the rollout carries no approval event, so a session blocked on `approval_policy = "on-request"` used to read `processing` until the 10-minute stale-turn fallback) plus `Interrupt` (Ctrl+C closes the turn `interrupted`); OpenCode's `permission.asked` via the observer plugin (answerable `ocperm:` requestId in BOTH daemons — `bridge/src/hook-opencode-sessions.ts`); OpenClaw's `exec.approval.requested` (Gateway-blocked, with expiry/abandon). Kiro and Antigravity have no permission source and never show PERM. **A PERM must also be able to END, and for OpenClaw nothing says so.** An approval carries TWO lifetimes and both daemons only ever knew the longer one: the record's `expiresAtMs` is `DEFAULT_EXEC_APPROVAL_TIMEOUT_MS` (30 min), while the agent run waiting on it gives up far sooner — measured 2026-09-09 as a 908,788 ms `exec.approval.waitDecision`, after which the Gateway refused the follow-up with `agent runtime authority is no longer active` and dropped the record, emitting NO `exec.approval.resolved`. The deck offered an unanswerable prompt for the remaining 15 minutes, and the user's press came back `unknown or expired approval id` — which the catch branch treated as retryable and re-broadcast, re-arming a button that could only fail again. Two rules follow. **A resolve failure is two answers, not one**: the Gateway naming the approval unknown/expired/already-resolved IS the answer (abandon), while a transport failure or RPC timeout is no information (keep it, let the user press again) — the predicate is `isApprovalGoneError` in `shared/src/openclaw-approval.ts`, a mirror of the Gateway's OWN `isApprovalStaleError` (structured `code`/`details.reason` first, its legacy message regexes second), generated into Swift and pinned by `shared/openclaw-approval-error-vectors.json` that both suites replay. And **a displayed approval is reconciled against `exec.approval.list` while it is up** (30 s), because that is the only signal on the dropped path; only a READABLE answer lacking the id closes it, since an unparseable or failed list is not "gone" — the same polarity as every other probe here, and the one that cannot discard a live approval the agent is still blocked on. The Swift daemon had it worse than Node: no expiry, no abandon, not even a clear on disconnect, so its ghost PERM was permanent — it now abandons on all four (gone-error, reconcile, record expiry, disconnect) and the daemon clears its cached prompt on a new `gateway_approval_abandoned` event. **The Claude PreToolUse hold is the one place PERM is predicted, so its predictor is a single generated SSOT**: `shared/src/claude-permission-rules.ts` (→ `pnpm generate-claude-permission-rules`, vitest byte gate + `shared/claude-permission-vectors.json` replayed by both suites). It exists because the two hand copies drifted into the SAME defect — both understood only the legacy `Bash(cmd:*)` spelling while the permission dialog writes `Bash(cmd *)`, so every allowlisted call in an `acceptEdits`/`default` session was held the full 25 s and the deck showed a PERM the terminal never asked. The rules follow the Claude docs: `*` matches any text including spaces; a trailing ` *` also matches the bare command; the legacy `:*` keeps BOTH readings (` *` alias and raw prefix — over-matching only costs a missed hold); compound commands split on `&& || ; | |& &` and EVERY subcommand must be covered; the built-in read-only set (`ls cat git status …`) never prompts; `acceptEdits` also auto-approves `mkdir touch rm rmdir mv cp sed`; wrappers and env assignments are stripped; `auto`/`plan`/`dontAsk`/`bypassPermissions` never hold. **A missed hold costs nothing** (the terminal prompts as before); a false hold costs a lie plus a stall — so every uncertainty resolves to "don't hold".

## Identity, subagents and prompts

- **Three identity axes, and only one of them is the harness.** `agentType` names the CLI/app driving the session (hook set, transcript format, steering path, creature), `modelName` names the weights, and `modelProvider` names whose endpoint served them. A `claude-glm` session is Claude Code — same binary, same hooks, same transcript — with `ANTHROPIC_BASE_URL` pointed at z.ai, so it arrives correctly as `agentType: 'claude-code'` / `modelName: 'glm-5.3'` and minting a `claude-glm` **agentType** would be wrong twice: it conflates the harness with the endpoint, and (per the unknown-agent rule in [devices-and-wire.md](devices-and-wire.md#wire-semantics)) every surface's agent handling is an allow-list, so a value no client predates renders as nothing at all. What was missing is the one-bit fact neither field states alone — *this Claude is not talking to Anthropic* — which rides `offHarnessProvider` (`shared/src/model-provider.ts`, → `pnpm generate-model-provider`). It is non-null **only when both sides are known and disagree**: two unknowns must never combine into a claim, and the multi-provider harnesses (OpenClaw, OpenCode, Antigravity, Kiro) have no native provider precisely so they never wear an "off-harness" badge for doing what they are for
- **A hook's harness is read from its payload, not from the endpoint it reached — and never from its model.** Codex speaks Claude's lifecycle vocabulary (`hook_event_name: "Stop"`, `session_id`, `transcript_path`, `last_assistant_message`) and can run a Claude-shaped hook command, so both daemons ingested any unprefixed POST (`/hooks/Stop`, Swift's `/hook`) as Claude Code: Swift resurrected a `claude-code` row on the Codex thread and stamped its `gpt-*` model on it, and Node labelled the Codex turn's `chat_start`/`chat_response` `claude-code` (#490, App Store 1.8.0 audit 2026-10-09; reproduced over HTTP with verbatim codex-cli 0.160.1 payloads). `shared/src/hook-harness.ts` (→ `pnpm generate-hook-harness`, `CodexHookHarness.generated.swift`, vectors `shared/hook-harness-vectors.json` replayed by both suites) routes an unprefixed hook whose payload carries Codex-only evidence — a Codex thread key, the notify type `agent-turn-complete`, a rollout `transcript_path`, or a `turn_id` with no transcript path at all (an ephemeral Codex run; every Claude hook names its transcript, and Claude's `MessageDisplay` hook carries a `turn_id` too, so `turn_id` alone is never evidence) — to the `codex_*` event it is, drops a Codex payload with no Codex route, and fingerprints one Codex event instance (event + thread + turn/tool/source) so the twin from a second hook command is ingested once (`CodexHookReplayGuard` / `CodexHookReplayMemory`, 10 s). A payload without its discriminator is not deduplicated. Swift answers a re-routed `PreToolUse`/`Stop` with an empty body and skips Claude steering, so a queued deck directive can never be handed to Codex. Timeline exact dedup is per session for every row type (`deduplicateEntry`, `DaemonTimelineStore.add`, `shared/timeline-ci-dedup-vectors.json`): two real sessions answering the same words are two rows, the same session in either id form is one. The `X-AgentDeck-Pid` header, `cwd`, or a model/provider never decide the harness.
- **A subagent census is counted at the hook, never read back out of the timeline — and a parent's `state` is not the whole story.** A parent whose turn closed is genuinely `idle` while its children keep working, so `SessionInfo.subagents` (`{active, peak, completed}`) is a SECOND axis beside `state`, not a correction to it; `SubagentTimelineTracker` owns it (Node) with a `subagentCensus` mirror in `DaemonServer` (Swift). Deriving it from the rows it emits reads ~zero in exactly the fan-out it describes, because those rows are lossy **by design** in two ways that both had to be fixed: content dedup collapsed a simultaneous fan-out to one row (siblings of one workflow share an `agent_type` and therefore a byte-identical `raw`, in the same millisecond), so subagent rows bypass dedup keyed by `subagentId`; and `evictOne` shed `tool_exec` first, making the dispatch row the first casualty in precisely the sessions that produce the most tool rows, so `subagentId`-bearing `tool_exec` is exempt. (Measured on a real workflow session: 72 completions, peak 8 concurrent, **zero** dispatch rows surviving in the buffer.) Starts fold into ONE upserted row per burst (`Subagent ×8 dispatched`); stops stay individual and name WHICH child finished, with its duration. Emit the census with explicit zeros once a session has had children — a field that vanishes when the last child exits latches its count under retain-on-absent merging. The fallback text is `ended · no summary`, never `Completed`, which next to eleven siblings still running read as "the work is done". Children never become `SessionInfo` rows: they are not separately steerable and would flood a deck sized for sessions. **The census is also the only honest producer for APME child evidence.** Child hooks are consumed before ordinary parent ingestion, so both daemons hand start/completion evidence to the active parent task only; it writes `sample_events.kind='subagent'` and merges `SampleModelConfig.subagents` instead of letting later model/usage hooks overwrite it. Both `/apme/graph` builders project one child node with a `delegated` edge. No active parent task means no guessed edge. **A harness also divides work WITHOUT a SubagentStart, and each shape leaves evidence the daemon can read without guessing** (`bridge/src/coordination-evidence.ts` → `RelationEvent` + `SessionInfo.coordination`): a `claude -p` worker launched from a background Bash is a separate observed session whose process ANCESTRY reaches the parent's pid (`spawned`); a Claude Code `SendMessage` is a tool call on the sender and a `<cross-session-message from="uds:/…/<pid>.sock">` envelope in the receiver's prompt, where the socket basename is the sender's pid (`messaged`); and a `run_in_background` job is a process whose argv names the session's scratchpad directory (`waiting_on`). The tick is its own 5 s timer, not `onRefreshed` (a job appearing changes the process table, not the observed set). Both daemons run it — Swift's `CoordinationTracker` over `ProcessEnumerator.processTable()` (`sysctl`, no entitlement) with the session→pid link from the hook header — and both suites replay `shared/coordination-evidence-vectors.json`. IPS10 additionally gets a STABLE card roster from either daemon (`stableCardRoster`: awaiting sessions always kept, newest fill the rest, id order, `total` → `+N`), because the state-ranked round-robin re-picked the card SET whenever the machine held more than ten sessions. **A `TaskCompleted` hook is a checklist item, never a child**: handing it to the subagent pipeline rendered six finished branches for a session that ran no children; it is an `info` annotation now (`task_completed` / `team_task_completed`). (2026-08-17, 2026-09-06 — DEVELOPMENT_LOG.)
- **A headless `codex exec` launched by an observed session is that session's child, never a session of its own — and a Codex run closes when its session leaves the roster.** `codex exec` is one real `codex` process per job with a rollout (`session_meta.originator: codex_exec`) and the user-global hooks, so a Claude Bash running `xargs -P 4 codex exec` put 49 topic-named `codex-cli` rows on every deck and opened 49 APME runs that nothing closed (2026-10-01). `bridge/src/codex-exec-children.ts` folds such a run under the observed session its process ancestry reaches: the observer drops the row and reports the child (`foldHeadlessCodexSessions`), the hook path holds a headless rollout's hooks out of every parent pipeline until its launcher is resolved (`pending`, 60 s) or judged absent (`standalone` — the user's own terminal `codex exec` stays a session), and attaching retracts the child's early hook row/APME run and moves the parent's `SubagentTimelineTracker` census exactly as a hook-declared child does; its `Stop` or process exit is the `SubagentStop`. Filtering it out instead would hide real work; keeping it as a row misnames it. Codex has no `SessionEnd`, so `sweepVanishedCodexRuns` closes a Codex run 90 s after its id is absent from observer, hook and OTel rows (the Kiro observed-vanish / OpenClaw idle analogue); the abandoned-run reaper still skips live runs and is the restart backstop only. Pending never HOLDS hooks: a run this daemon cannot attach must stay a session with a run, so its hooks flow and an attach later retracts the row, the run and its open `chat_start` (`Folded into parent`). The hook path finds the process by its `-C <cwd>` argv (canonicalized — `-C /tmp/x` reports `cwd: /private/tmp/x`) or as the only unclaimed `codex exec`, reading one fresh process table per new session when the cached one predates the run; an argv-matched pid is a guess, so a same-cwd sibling still running keeps the child open, and only the observer's `lsof`-backed pid is exact. The Swift daemon mirrors it (`CodexExecChildRegistry`, hook-only producer over `ProcessEnumerator`, run closed on Codex eviction). POSIX Codex lifecycle hooks carry `X-AgentDeck-Pid: $PPID`. The command starts with `exec sh -c` so the hook runner's shell is replaced rather than becoming an extra parent; both TypeScript and Swift installers emit the same command. Reinstallation refreshes the managed block while preserving user settings and trust records; changed commands still need Codex's normal hook trust. Windows lifecycle and notify hooks take one bounded `Win32_Process` snapshot and send the header only when ancestry reaches `codex.exe` through command-runner shells; missing, cyclic or unrelated evidence omits identity without dropping the event (#429).
- **Claude `Stop` ends a parent turn, not necessarily its session work.** Claude 2.1.198+ sends `background_tasks` snapshots on Stop/SubagentStop; iTerm2 uses these to remain working between turns. `bridge/src/claude-background-tasks.ts` owns the generated Swift rule: project an idle observed row as processing with a background-work activity only while explicit running tasks remain, without reopening APME turns or inferring subagent counts. Awaiting/offline/foreground states keep precedence. Exclude the exiting `agent_id` on SubagentStop; explicit empty/completed snapshots clear, absent/malformed snapshots are unknown and retain, session boundaries reset. This projection does not discover arbitrary detached tmux processes.
- **A Claude Code background job is the conversation; its spare and its parked window are not.** Claude 2.1.29x runs background jobs (its agent view) under its own daemon, and one conversation can sit behind three processes: a pre-warmed **spare** (`claude bg-spare --bg-spare …`, `spare: true` in `~/.claude/sessions/<pid>.json`) with its own session id and cwd but no conversation; a **PTY host** (`--bg-pty-host`) relaying the job's terminal; and the **job** itself, launched from the versioned binary (`…/claude/versions/2.1.296 --session-id <NEW> --fork-session --resume …/<OLD>.jsonl`). Moving a window's conversation to the background forks it into the job and leaves the window alive as a host shell with `parkedJobId`, emitting no more hooks. Measured 2026-10-10: the job's argv[0] never said `claude`, so the Node observer dropped the working session and showed the parked window and the spare as two idle OpenClaw rows, while the spare's startup `SessionStart` opened an empty APME run the reaper later closed `abandoned`. The Node observer now admits the versioned binary (argv[0] only), never the PTY host, and `selectClaudeConversationFiles` drops spares and a window whose job is alive in the same scan (a stale `parkedJobId` keeps its row). Both hook paths classify the hook's process by argv with the generated rule `shared/src/claude-background-jobs.ts` (→ `pnpm generate-claude-background-jobs`, `ClaudeBackgroundJobRules.generated.swift`, vectors `shared/claude-background-job-vectors.json` replayed by both suites): a spare's `SessionStart` with source `startup` is dropped before any row, timeline or run exists (a claimed spare keeps its argv, so `compact`/`clear`/`resume` starts pass, and its first prompt opens the run as usual); a job forked from `<OLD>` closes `<OLD>`'s APME run (finished, not abandoned) — on Node only when `<OLD>`'s own session file carries `parkedJobId`, since a fork alone can leave the original working — and the sandboxed Swift daemon, which cannot read the session file, retires `<OLD>`'s row only when it is idle with no open turn. Swift reads the hook's process synchronously (`ProcessEnumerator.processRow`, two sysctls): SessionStart is posted fire-and-forget, and an `await` there let the session's UserPromptSubmit overtake it, after which the resumed session_start reset the row to idle and split the turn. A fork is a job only when its parent is a PTY host, so a terminal `claude --resume X --fork-session` never retires X. An unclaimed or unfound pid is unknown and never drops or retires anything. A job is a session row, not background decoration: it is the user's conversation, listed in Claude's own agent view, and nothing on disk names a parent session to fold it under.
- **An OpenCode Task-tool child session is its parent's subagent.** OpenCode runs a `task` call as a child session with `parentID`; the observer plugin (v3) learns the parent from `session.created` or one bounded `client.session.get` (one in-flight promise per session — OpenCode does not await plugin handlers, so separate lookups resumed out of order and a prompt landing after its own stop opened a phantom turn), then posts `opencode_subagent_start`/`opencode_subagent_stop` (`session_id` = the top-level parent, `agent_id` = the child) into both daemons' subagent census instead of announcing the child as a session. A finished child stays finished (OpenCode re-emits `message.updated` after a turn settles; only a new user message in the child restarts it), or the parent's census shows it running for hours. The child's permission request is a real wait, so it is surfaced on the parent's row and resolved against the child that asked (`permissionSession`); its questions are display-only and shown on the parent too. A parent lookup that fails is unknown and keeps the old behaviour (a row).
- **A Claude `SubagentStop` is not always a dispatched worker.** Claude 2.1.261's internal fork queries (prompt suggestions / agent summaries) enter the query loop without `SubagentStart` and still emit `SubagentStop` with an explicitly empty `agent_type`. Live captures produced `wait for it…` and `<no suggestion>` as fake worker completions. Both daemons consume these empty-type stops when no active child matches, without a timeline row, census increment or APME event. Typed orphan stops, absent legacy types and known children still count; never synthesize starts to balance a stop count. `TaskCompleted` is also a one-sided task event, so aggregate APME started/completed counts are not a hook-loss ratio. Ordinary Agent calls were verified marker → HTTP → tracker → APME with matching IDs. Named/background Agent calls can instead create a separate session in 2.1.261 and use `SessionStart`/`Stop`; do not invent a parent link.
- **A folded Codex project row must expose the member waiting on the user.** General activity ranking prefers processing, but that rule inside the fold hid a live `PermissionRequest` behind another processing task in the same project. `foldCodexSessionsForDisplay` and both Swift fold consumers rank awaiting members first and keep that member's ID, question, controls and tool together. A sibling's tool must never overwrite the waiting member's tool.
- **An observed session's `sessions_list` row is the SSOT for its prompt** — it has no live state channel of its own. `focus_session` is answered with the daemon's *global* `state_update` stamped with that session's `focusedSessionId`, so it passes any "is this event mine?" attribution check and, applied as a replacement snapshot, blanks the row's real `question`/`options` off the deck. Re-seed from the row instead of storing that snapshot (`plugin-ulanzi/src/state-store.ts`, `plugin/src/focused-detail-state.ts` — the same bug lived in both). A device answer to an observed prompt is only deliverable when the daemon says so via `liveAnswerable` (it can type into the session's terminal, or is holding its AskUserQuestion open — the ask-gate in `observed-steering.ts` / `ObservedSteering.swift`); `requestId` stays off the wire for a question, since it makes devices render a binary Allow/Deny over a multiple-choice prompt. A single AskUserQuestion call may carry up to four question groups — the daemon presents them **one at a time** and never flattens them into one index space, because an index only means anything within the group on screen. A press must **name the question it answers** (`select_option.question`), which is what keeps a hardware approve key (`select_option(0)` as a yes/no stand-in on hud_bar / pocket / ticker / knob `MI_APPROVE`) from committing a guess as the user's stated answer; only a surface rendering the real option list may echo (ESP32: the T-Embed knob's `MI_OPTION` alone). The echo is matched **as a truncation-tolerant prefix** (`askEchoMatches`), because a question is capped at 120 CHARACTERS but held in a 160-BYTE firmware buffer — exact match refused every answer to a Korean question while passing every English one. Two firmware traps: send the RAW daemon string, never the display copy (`sanitizeLvglText` rewrites punctuation and blanks non-Hangul CJK), and compose against `Net::OUTBOUND_MAX_LEN` since a JSON frame cut mid-string is unparseable. And a **hand-mirrored string rule must compare the same units on both sides**: Swift `String.count`/`hasPrefix` are grapheme-cluster based while TS `.length`/`startsWith` are UTF-16 code units, so the Swift mirror compares `.utf16`.
- **One session, two id forms**: devices and `sessions_list` address a passively-observed session as `observed:<agent>:<uuid>` (and devices see it **truncated to 31 chars**), while timeline rows, hook payloads and transcript filenames use the **bare uuid**. Normalize with `rawSessionId()` / `sameSession()` from `@agentdeck/shared` before comparing — never inline the regex, which is how four copies drifted into three different agent lists and a fifth site skipped stripping entirely (a spoken reply armed under one form, looked up under the other, matched nothing). Device-sent ids also need `resolveSessionIdPrefix` for the truncation

## Version compatibility

- **Version compatibility**: daemon-first users run `agentdeck diag agents [--json]`, which checks the installed Claude Code/Codex/OpenCode versions against the compatibility ranges in `bridge/package.json` without starting a PTY or daemon. Deprecated `agentdeck claude` still performs its legacy npm-registry startup check during the compatibility window and never blocks startup. `~/.agentdeck/compatibility.json` is only that wrapper's local throttle cache, not a repository manifest; removal is tracked in #273
