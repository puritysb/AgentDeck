# APME eval invariants
<!-- Moved verbatim from the root map (then CLAUDE.md, 2026-09-10; AGENTS.md since 2026-09-29). Rule bodies are the SSOT for their domain; the root map keeps only the index. -->
Rules for the APME eval module (`bridge/src/apme/`, Swift `Daemon/Apme/`): the canonical `SessionSample`, task/turn
segmentation, judge chain, transport gate and parser. The measurements behind each rule are in
[docs/apme.md](../../docs/apme.md); the incidents are in `DEVELOPMENT_LOG.md`. Every rule below is a
cross-daemon contract — Node and Swift must decide identically or the same `settings.json` scores differently
depending on which daemon holds 9120.

## Sample, tasks and turns

- **Canonical `SessionSample`** (`shared/src/sample.ts` + `sample_events` table) is the SSOT: a bounded unit with a typed trajectory (user/assistant/model/tool/subagent/state) that both the timeline and the eval derive from. Per-unit cost via `shared/src/pricing.ts` (override-loadable), Pareto-frontier recommender (`apme/pareto.ts`) surfaced via the dashboard **Recommend** tab, trajectory scorers (`apme/scorers/`).
- **Eval results are off the device timeline** (timeline = activity log only) — they flow via the `apme_eval` WS event + scorecard/SQLite. **Task rows render one-per-task**: `task_end` is data-only (spinner stop, judge upsert, reaper) and never a standalone row — the `task_start` header folds the closure in (SSOT `shared/src/timeline-task-display.ts`, mirrored Swift/Kotlin/TUI; glance surfaces exclude task rows entirely). Env `AGENTDECK_TIMELINE_PROJECTION=1` (default off) flips the device timeline to the sample projection (suppresses adapters' direct chat/tool rows).
- **Tasks segment on explicit boundaries** (`/task close`, `/clear`), `session_end`, or a **15-minute generic idle gap** armed at turn close (`AGENT_IDLE_GAP_MS`; 96% of real claude inter-turn gaps are shorter, and without it codex tasks reached the judge only via the 30-min orphan reaper — hours late or never); TodoWrite-all-completed is a non-segmenting soft hint. **The collector's state is re-adopted from the store at daemon start** (`rehydrateOpenRuns`, daemon-only) because the idle-gap timer and every session→run/task/turn edge are in-memory, so a restart otherwise stranded every mid-session run for the 2-hour reaper. The reaper stamps what it found: a task whose turns all closed is `idle_gap` (reached late), only one holding an open turn is `orphaned`, and `stop-health` reports reaped turns in their own `Reaped` column rather than folding them into session ends (which read a 29% codex loss as 11%). **Adoption at startup is provisional** — a rehydrated run counts as live to the reaper only once its session sends a hook (`rehydratedSessions` / `isLiveRun` / `releaseRun`), because a session that ended while the daemon was down has no Stop coming and no idle timer (those arm on turn close).
- **A turn closes at its Stop, and records WHICH signal closed it** (`turns.end_source`: `stop` / `synthetic_stop` / `next_prompt` / `interrupted` / `session_end` / `run_close` / `clear`) — closing at the next prompt instead put the user's typing time inside the turn's duration, and without the attribution a dropped Stop hook is byte-identical to a normal close, so its rate was unmeasurable. `agentdeck apme stop-health` reads it; pre-column rows are never backfilled. **A turn open at startup or at the next prompt is closed by the agent's OWN record, at the record's time** — Codex's rollout (`codexCompletionProbe`) and Claude's transcript (`claudeTurnCompletionSince`, located under `~/.claude/projects` by session id): `end_turn` → `synthetic_stop` with the reply, `task_complete.error` / `stop_sequence` → `aborted`, a mid-turn tail claims nothing (most `next_prompt` turns hold a completed reply or an API failure, not a dropped hook). **A reply arriving after `closeRun` still lands** (`latestClosedTurnIdForSession`, 60 s window): one-turn workers send SessionEnd 80–130 ms after Stop, ahead of the deferred transcript re-read.
- **A user cancel is not a lost hook**: ESC emits no hook at all, so no Stop was ever due — `interrupted` is its own bucket, outranks `synthetic` when both are set (a cancel can only ever arrive AS a synthetic Stop), and stays out of the loss ratio. It is detected two ways because one is not enough: the watchdog sees the marker while it is still the transcript tail, and the next-prompt close runs `readInterruptSince` for the commoner cancel-then-retype shape that buries it. The marker predicate is single-source in `bridge/src/claude-interrupt-marker.ts` (observer + watchdog + collector) and reads **text blocks only** — a `tool_result` quoting the same sentence is routine and would otherwise invent a cancel. Missed-Stop recovery is **two wirings, not one** — `claude-turn-watchdog.ts` per PTY bridge, `observed-turn-watchdogs.ts` per observed session inside the daemon (the first alone covers none of the real traffic). Recovery **re-enters the real Stop path** (the daemon self-POSTs its own `/hooks/Stop`) rather than reimplementing it, and a synthetic Stop must never drain a queue whose delivery needs a listener (`takeDirectiveForStop`).
- **A Stop hook's reply source is chosen per agent** (`hook-response-source.ts`): inline text first, else each agent's OWN reader — a Codex hook carries `transcript_path` too (its rollout), and handing it to the Claude reader left it replyless; the same payload's `model` stamps the TURN (`turns.model_id` is the scorecard source). **A verdict about the agent's work needs the agent's work**: `task-gradeability.ts` is the Node SSOT declining `no_reply` / `aborted_only` / `trivial` tasks and stamping the reason on the row; `generate-apme-display-rules` emits `TaskGradeabilityRules.generated.swift`, and both suites replay `shared/task-gradeability-vectors.json` so the App Store daemon makes the same decision.
- **The task judge backlog drain feeds ONE task per tick and only when nothing is in flight** (judge `ready` only, 30-day window, declined rows excluded), a park after two failures expires after 30 min, and an `unavailable` backend is re-probed every 5 min — a local model busy with someone else's inference at startup used to switch the drain off for the life of the process, and three concurrent requests per tick against a serial server parked every pending task with no log line. **The task it feeds is chosen park-aware** (`pickBacklogTasks` over a 200-row window, not the query's first row): the query orders `ended_at DESC` and `enqueueTask` drops a parked task SILENTLY, so a task whose judge call fails every attempt owns that head and every tick spends its one slot on it — that stranded 156 older tasks for two weeks while the day's own tasks were judged normally by the live close path. A window in which every candidate is parked says so in the log, once per park period, because silence is what let that run for two weeks.
- **A task's display title is its first user prompt, and the judge summary outranks it once it exists** (`deriveTaskTitle` SSOT `shared/src/task-title.ts`; the Swift copy is GENERATED — `pnpm generate-apme-display-rules` → `TaskTitleRules.generated.swift` — with behavior pinned by the shared vector file `shared/task-title-vectors.json` both suites replay: a markup-first prompt derives null, a slash PATH is not a slash command, all index math is code points): the intent title fills the one-line slot until judged, the outcome sentence wins after, and the `Task N` fallback stays the display SSOT's "meaningless" shape. The `/apme` default tab is a task-first **Work board** (lifecycle buckets + attention-first sort; bucket SQL is single-source in the store so filter, row flag and badge cannot disagree — attention is 7-day windowed because the unwindowed bucket measured 93% of all history). Every row exposes its project + native session as a contextual drill-down; the exact `session_id` scope gathers that session's tasks and changes ordering to recency so its work reads as one chronology, with the same entry point in Run/Task detail.

## Judge chain, transport gate and parser

- **The default judge chain is `mlx → foundationModels`, and the FM leg is a FLOOR, not a peer**: on-device FM measured 0.580 on the judge-fidelity rubric (vs 0.86–1.00 for the MLX tier) and its window is a hard, measured 4,096 tokens that refuses 4.2% of real `task_rollup` judge prompts — but dropping it as the fallback would remove evaluation outright from every machine with no MLX server. The fallback rides the DEFAULT only (`fallbackToFoundationModels`): a backend the user NAMED, offline, still skips visibly. The two daemons read one `settings.json`, so the legs must resolve it identically or the same user config scores differently depending on which daemon holds 9120, with nothing in either log saying so (#299): the MLX URL resolves `apme.judge.endpoint` then the `llm.mlx` pin on BOTH (Swift read the pin for the model only and hardcoded the URL to loopback), the MLX timeout is 90 s on both (Swift's 60 s timed out on the very prompt shape the 68.7 s measurement came from), the MLX→FM fallback is logged at normal level on both (behind Swift's debug flag the cut rate the 1.05 default is calibrated against was unmeasurable there), and a judge response is accepted on 200–299 on both, mirroring `resp.ok` — which changes nothing about the BODY gate. Both legs now send `response_format` on both daemons with the same per-request retry, and the `task_category` classifier — which selects the rubric — reads one SSOT on both (`shared/src/apme-classifier-rules.ts` → generated `ApmeClassifierRules.generated.swift`, drift-gated): prompt, label vocabulary, `max_tokens` 20, 15 s, and the try-order `mlx → foundationModels → rules`. `api`/`openai` are not members of that array, so a paid backend is structurally unreachable for classification — Swift used to route it through whatever judge backend the user configured and billed per classification. The order is NOT a ranking claim: the 2026-09-10 measurement (40 real tasks, 15 s budget) ran against an MLX server holding a 27B model and compared each leg to the RULES, which are the thing an LLM is meant to improve on, so it could not rank; `mlx` leads because it was Node's only leg and the prompts are calibrated to it, `foundationModels` follows so a Mac with no MLX server — most Macs — still gets an LLM answer. Re-measure with a normally loaded model and owner-labelled ground truth before reordering. Two consequences: anything that must decide before the call — the REVIEW tier and its diff budget — resolves the leg that will actually answer first (`resolveJudgeBackend` / `ReviewRunner.resolveBackend`), because the legs' windows differ 4×; and a prompt budget for the on-device leg is sized in MEASURED tokens, never characters (the `basic` tier's own caps used to build a 5,161-token prompt for a 4,096-token window, since the activity block is the user's own Korean prompts at ~1.15 chars/token).
- **Judge transport completion is part of verdict validity, but the rule is about the BODY, not the flag**: both daemons reject an empty content, a `choices` that is not a non-empty array, and a `finish_reason=length`, full stop. **An exemption for "its object closed, so the verdict finished" was tried and removed** (#286 item 3): brace topology cannot tell whether the model finished, so the exemption produced a defect in three consecutive adversarial review rounds — first admitting a reasoning model's `<think>` scratchpad when the real verdict was the part that got cut, then refusing complete verdicts whose trailing prose held an unmatched brace — and it had no measured beneficiary, since the one cut mode observed on this fleet is a repetition loop INSIDE the `summary` string (gemma-4-26b, running to the 800-token cap without closing) where depth never returns to zero. `parseJudgeJson` already refuses exactly the incomplete case; rejecting the complete one silently rerouted the default chain to the FM floor. The rate is visible — the park log names this failure (an earlier claim that a re-attempt clears it two times in three is **WITHDRAWN**: it came from a probe writing `task_category: unknown` where `runTaskEval` resolves it from the run, i.e. a request the daemon never sends).
- **Both daemons extract that object the same way** (first BALANCED `{…}`, Node keeping the old greedy span as a second candidate because a key that lost its opening quote desyncs any string-aware scanner and is what `repairJudgeJson` exists for): Node's greedy-only match spanned into trailing prose and called a verdict cut that Swift scored. **Which of several objects is the verdict is decided by `overall`, never by position** (`parseJudgeObject` / `ApmeRunner.selectVerdictObject`), and two spans carrying it are AMBIGUOUS and resolve to null: scanning balanced blocks makes more spans parseable, so "the first that parses" scored a local reasoning model's `<think>` scratchpad instead of its answer — a wrong score in `evals` is strictly worse than a loud skip. The vectors carry a `verdict` field (defaulting to `accepted`) separating "the transport returned it" from "the parser produced a verdict from it", because that is the only way to pin a body the gate must pass and the parser must refuse. Two known parser asymmetries the vectors CANNOT express, both in the same direction (Node scores, Swift skips): Node's greedy second candidate and `repairJudgeJson` for the lost-opening-quote defect Gemma 4 emits, which Swift has neither of — porting the repair would be a new hand mirror, so it is recorded here rather than duplicated.
- The **Anthropic `api` leg** carries the same rule under its own spelling (`stop_reason` `max_tokens` / `refusal`), sends the same `max_tokens: 8192`, resolves the same default model, and sends no `temperature` — sampling parameters are rejected outright on Opus 4.7+, so that leg 400'd for every current model and reported it as `nil`, i.e. the same shape as "no API key". Shared `apme-judge-response-vectors.json` pins the chat-completions gate and `apme-judge-api-response-vectors.json` the Anthropic one — the api leg is reached only through the SDK, so without its own vector file reverting either rule left both suites green. Serving completion rates are not judge-accuracy evidence.
- **The MLX judge leg — that leg only — sends `repetition_penalty`** (default 1.05, `apme.judge.repetitionPenalty`; exactly 1 disables and omits the field), because gemma-4-26b loops inside the `summary` string and runs to the cap without closing the object. Measured 2026-09-07/08 under two designs — three back-to-back repeats and three INTERLEAVED so each is separated by five other prompts (evicting the server's prompt cache) — with identical totals AND identical task-by-task results: **4 of 6 tasks cut → 1 of 6**, no task worse. The headline is the TASK count on purpose: greedy decoding at `temperature: 0` is specified to repeat itself given identical server state, so the repeats are the stability result and the independent unit is the task (n=6) — and that cuts both ways, since the spec says nothing about a restart and every run in the record was answered by one long-lived `mlx_vlm.server` process. **The server silently ignores unknown fields** — a made-up parameter returns 200 like a real one — so acceptance proves nothing; that this one is honoured is shown by the OUTCOMES across penalty conditions on the same prompt at `temperature: 0`. `repetition_penalty` is NOT OpenAI-standard, so on a 400/422 the ladder gives it up **before** `response_format` (the non-standard field is the likelier culprit, and losing it only raises the cut rate while losing JSON mode costs the strict-JSON request) — **per request, remembering nothing** (owner decision 2026-09-10, #299 item 1). The per-endpoint, process-lifetime memory of "this server refuses X" that used to sit here was DELETED on the repo's own criterion: it produced a HIGH/MEDIUM defect in four consecutive adversarial review rounds (blaming the wrong field, writing a field off for a prompt that was merely too long once, recording before the retry proved anything) while defending against a server never once observed — the MLX server every measurement was taken against silently accepts unknown fields. What remains costs one extra request per call against a genuinely strict server, and every mistake in this area is now a wasted request rather than a permanent, silent, process-wide mark. Both daemons run the same ladder (Node additionally re-diagnoses a context-overflow 400 by compacting the prompt; Swift never compacted and still does not), gate the SEND on `> 1`, and read only 400/422 as a rejected request. Pinned on both sides by "the second call carries the field again" tests. The openai-compatible leg deliberately does NOT send it: that adapter serves OpenRouter and any other OpenAI-compatible endpoint, several of which honour the field, so sending it would silently change sampling for a judge the user pays per call on evidence measured against one local model. The 1.05 default is a **hand mirror** (`MLX_JUDGE_REPETITION_PENALTY` / `ApmeJudgeMlx.defaultRepetitionPenalty`) with no generator — fold it into a generator when next touched.

## Identity, cost and per-key runs

- **APME identity and cost belong to the turn that produced them.** `turns.model_id` / `turns.provider` are the scorecard source; a task spanning identities is explicitly `mixed`, while `runs.model_id` / `runs.provider` retain the latest value only for legacy summary compatibility and must never drive per-turn ranking. Provider normalization lives in `shared/src/model-provider.ts` and its generated Swift/Kotlin mirrors. A numeric zero is not proof of a free call: every aggregate carries `cost_known`, unknown cost remains SQL/API `NULL`, budget recommendations exclude it, and only priced or known-local zero may rank as free. Assistant response ownership is explicit too: `chat_final` > direct response > `session_message_projection`; all producers update one stable assistant-message sample slot so a later 8K projection can never replace a full final response (nor create a duplicate event).
- **An OpenClaw run is bounded by its key's idleness, because nothing else will close it.** Every other agent's run ends on `session_end`; an OpenClaw run is opened lazily per session KEY (`openclawRunForSessionKey`) and was only ever closed when the Gateway disconnected. A key that did one turn and went quiet — a cron job, a model-eval run, the nightly `dreaming-narrative` pair OpenClaw itself prunes as orphans — kept its run open for as long as the Gateway stayed up, and the abandoned-run reaper could not reach it either: the run is still in the collector's in-memory map, so `isLiveRun` protects it (measured 2026-09-07: two runs open 16 h with their tasks long since closed as `idle_gap`, while every other OpenClaw run had closed at ~1800 s). The daemon's APME tick now closes a per-key run whose tasks have all closed and whose last activity is older than `AGENT_IDLE_GAP_MS`, and drops the key — not a loss, since the next event on that key re-opens lazily, which is the documented behaviour.
- **An index added for one query is a plan change for every other query on that table, and `better-sqlite3` runs on the daemon's main thread.** The prune command's `idx_sevents_kind_ts (kind, ts)` (#302) was the best index SQLite could see for the Work board's per-task `tool_count` subquery (`WHERE task_id = ? AND kind = 'tool'`), so from the moment that index existed the planner walked every `kind='tool'` row once per task — ~200 M row visits of multi-KB payload rows, **137.8 s for one page** on 2026-09-10, on a page the macOS app polls every 15 s. Synchronous SQLite means the event loop was gone for the duration: `/health` unanswered, the app promoting to a fallback port and standing down three times in five minutes, the OpenClaw link dropping on ping timeout. And the index reached the OLD daemon through the shared DB file — a CLI dry-run ran the schema DDL — so a build that never changed started running a 137 s query. The fix is the covering index the subquery actually wants (`idx_sevents_task_kind (task_id, kind)`: 257 ms), and the gate pins the PLAN (`apme-work-board-plan.test.ts`) — a timing test passes on a small fixture whatever the plan. Two operating rules: run `EXPLAIN QUERY PLAN` for the table's other hot queries before landing a new index, and when the daemon stops answering while its CPU is high, read the SQL before the JS — `sample <pid>` shows `sqlite3VdbeExec` under the JS frames, and a `Database.prototype.prepare` wrapper injected through the inspector names the statement and its duration (procedure in the 2026-09-10 devlog entry).
