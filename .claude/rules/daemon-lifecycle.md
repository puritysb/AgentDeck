# Daemon lifecycle, network posture and pairing
<!-- Moved verbatim from CLAUDE.md (2026-09-10). Rule bodies are the SSOT for their domain; CLAUDE.md keeps only the map. -->
Who owns port 9120, how a daemon starts/stops/restarts under its supervisor, what an unauthenticated LAN peer may
reach, how a credential travels to a device, and how two daemons converge on one token. Reference:
[docs/daemon.md](../../docs/daemon.md). The Swift-specific restart/teardown rules are in
[swift-daemon.md](swift-daemon.md).

## Persistence and hub

- **Timeline persistence is daemon-owned**: the daemon is the only process that writes `timeline.json` (`BridgeTimelineStore.enablePersistence()` on the Node side, `DaemonTimelineStore.flush()` on the Swift side), through tmp+rename, enabled only after the startup rehydrate. Session bridges share `BridgeTimelineStore` but must never enable it — concurrent bridges would interleave partial histories. The Stream Deck plugin used to be the sole writer, which left CLI-only users with no persistence at all; it no longer touches the file. Both daemons share one plain-JSON-array format so either can resume from the other's file
- **`timeline.json` is owned by whichever daemon is bound, in turn — so its format contract is bidirectional.** A handover means one implementation rehydrating what the other wrote, and a format gap does not raise: `[DaemonTimelineEntry].self` decodes to nil and the timeline silently starts empty. Both directions are gated (`bridge/src/__tests__/timeline-persistence.test.ts`, `apple/AgentDeckTests/TimelineCrossDaemonFormatTests.swift`); the Swift side only round-tripped its own file until 2026-08-19. Cross-daemon fixtures are **copied verbatim from a real `~/.agentdeck/timeline.json`**, never composed from the decoder's field list — a fixture built from what the reader expects cannot fail, which is exactly how a format gap survives a green suite

## Network posture and LAN security

- **LAN surface is default-deny** (issue #145): the daemon binds `0.0.0.0` on purpose (LAN devices are the product), so the security boundary is the pairing token, enforced at one chokepoint per daemon — `bridge/src/http-auth-gate.ts` (Node) / `DaemonServer.httpAccessResponse` + WS-upgrade 401 (Swift). An unauthenticated LAN peer reaches exactly one **standing** route: a minimal `GET /health` with **no `pairingToken`, no modules, no state**. Never add a standing unauthenticated route, never put the token in any discovery payload (mDNS TXT or UDP broadcast), never log a token-bearing pairing URL during startup, and never serve the token to a non-local peer *unless the operator is holding a pairing window open at that moment* — clients get it via QR/manual pairing, a **pairing code** (below), serial provisioning (`wifi_provision.authToken`), or `--daemon-token`/`AGENTDECK_DAEMON_TOKEN` (remote workers). `agentdeck token rotate` retires a leaked token. See [docs/daemon.md § LAN security model](../../docs/daemon.md)
- **A network posture is a single resolved fact, and "off" must be derived, not listed.** `AGENTDECK_LOOPBACK_ONLY=1` used to pick the bind address and nothing else, so a loopback-only daemon still advertised `_agentdeck._tcp`, beaconed UDP every 2s, swept the /24 for Pixoo devices and scanned BLE — for a service nobody on that segment could reach. Two axes, resolved once at startup by `resolveDaemonPosture()` (`bridge/src/network-posture.ts`) so the bind, the module set and the startup log cannot disagree: **`--local`** = no device modules (serial included), still binds `0.0.0.0` so a paired companion works; **`--loopback`** (≡ the env var) = bind `127.0.0.1` and emit nothing, but **keep the USB channels** — serial AND ADB reverse, because a board on a cable is not a network peer and cable-carried `adb reverse` terminates on the host's own loopback. That USB test is enforced, not assumed: `isNetworkAdbTransport` excludes `adb connect` / wireless debugging under loopback, which would carry the tunnel over the LAN (`BridgeContext.loopbackOnly` → `adb-reverse.ts`). Do not fold the two axes into one flag — some sites want hardware on a lab subnet with discovery off. The "everything off" record is `allModulesOff()` (`bridge/src/modules/types.ts`), **derived from `MODULE_NAMES`** with a vitest gate against `createDefaultModules()`: `initModules` reads an absent key as `'auto'`, so every hand-listed record silently switched newer modules ON — `--local` spawned the iDotMatrix Python BLE client, and so did the default session-bridge record. Write restricted branches as `{ ...allModulesOff(), <what this posture permits> }` so a module added later fails safe. **A posture that only applies when typed by hand is not a posture**: `daemon install --enterprise` bakes the flags into the LaunchAgent / Scheduled Task / systemd argv (the one channel all three writers share — Task Scheduler has no environment element), `daemon start`'s fork forwards them, and `daemon restart` reads the running daemon's posture off `/health` rather than silently downgrading it. Related default flip: **Pixoo auto-discovery is off unless explicitly `true`** (on by default meant every daemon start POSTed to `app.divoom-gz.com` and probed all 254 hosts of the /24; `agentdeck pixoo scan --no-cloud` is where a sweep belongs), mirrored in `PixooModule.swift` where an unreadable settings file must also mean off. The Swift daemon carries the same two axes via `AppPreferences` → `DaemonPosture`, module registration gated deny-by-default in `startDeviceModules`. Not covered: the shared-*machine* case — [docs/ENTERPRISE-ROADMAP.md](../../docs/ENTERPRISE-ROADMAP.md) §1, [docs/daemon.md § Enterprise and shared-network posture](../../docs/daemon.md)

## Pairing and credentials

- **The one credential path for a device with no camera and no cable is an operator-held pairing window** (`agentdeck pair`). QR needs a camera, serial needs USB, an e-ink reader has neither — and `adb reverse` dies on reboot, after which a returning reader hammers an endpoint that closes it 4001 with nothing on screen its user can act on. Rules, because this is the only place a token reaches an unauthenticated peer: the window **does not exist until the operator opens it on the host**, so with no window `POST /pair` is refused by the same default-deny branch as any unknown path — never answer it differently when closed, or the endpoint becomes an oracle for "is someone pairing right now". Expiry is enforced **on read, not by a timer** (a timer firing late on a sleeping laptop extends the window past its promise). The guess budget is **global, not per-IP**: an attacker picks their source address, so a per-peer budget is a budget per attempt. The operator-side routes (`/pair/open|status|close`) sit *behind* the normal gate — a remote peer able to open its own window would be granting itself a credential — and `/pair/status` never carries the code. A one-device window closes on success and the operator learns the outcome by polling, so it leaves a bounded **receipt**; without one, a pairing that worked reports as "nothing paired". Rules SSOT `shared/src/pairing-code.ts` (→ `pnpm generate-pairing-code-rules`, vitest drift gate — the emitted Swift carries the whole evaluator because the HTTP status *is* the contract a client's retry policy branches on; Kotlin stays a client mirror). State: `bridge/src/pairing-window.ts` / `apple/.../PairingWindowStore.swift`
- **A code asks the DEVICE to prove something; approval asks the OPERATOR, and only the second one a camera-less reader can complete.** The pairing code is gated on discovery — a client spends it against a daemon it found over mDNS — so where multicast is filtered it is unreachable by exactly the devices it was built for. The daemon already refuses an unauthenticated LAN peer at the WebSocket handshake and logs the address; it just never told anyone (one reader knocked 116 times, then went quiet for three weeks). So the refusal becomes a prompt: `WAITING TO CONNECT` in the app's Pair a Device window, backed by `GET /pair/knocks` + `POST /pair/approve|revoke|dismiss` behind the normal gate. The device does nothing at all, which is also the stronger trust model — a code trusts whoever knows a secret, an approval trusts a peer the operator pointed at, and an attacker cannot approve themselves. **Identity is the device id when the client sends one (`x-agentdeck-device`, a random per-install 128-bit id) and the address only when it does not** — the decision happens before any frame, so `client_register` is too late, and an address is not an identity behind NAT. The address fallback is not optional: every device already in the field predates the header, so refusing them turns an upgrade into a fleet-wide outage; the UI labels which kind a grant is, because only the device-scoped one survives a DHCP lease change. Neither kind is proof — the link is plaintext `ws://` — the win is granularity and revocation, not secrecy. Persisted approvals are **migrated, never dropped**: a decode that merely fails reads as "nobody is approved" and silently un-pairs the whole fleet. **Both daemons implement it**, because either may hold 9120 and which credential paths a device has must not depend on which one won. The Node port is a deliberate near-transliteration — a rule restated in different words is a rule that can drift — with three forced differences: the hooks are **injected** into `WsServer` (`setPairingApprovalHooks`), since a session bridge shares that class and must not hold a second unowned copy of the decision; the approval folds into `isAuthorizedHttpRequest` so `gateHttpRequest` stays the pure truth table its test drives; and the routes answer in the Swift daemon's wire shape field for field (`approved` not `approvals`, `deviceId: ""` not null, epoch-ms), because the Mac app in CLIENT mode calls them against whichever daemon holds the port. `approvedAt` is read by magnitude so either encoding decodes. Client side: a refusal memory carries WHEN each endpoint refused and expires on read after a 30s holdoff (`PairingCredential.UNAUTHORIZED_REDIAL_HOLDOFF_MS`) — approval mints no token, so a permanent ban meant the grant took effect only after an app restart, while an expired refusal buys exactly one redial. State: `apple/.../PairingKnockStore.swift`, `bridge/src/pairing-knocks.ts`; ids ride the `shared/src/pairing-code.ts` SSOT.
- **Discovery names an endpoint; it never carries a credential** (issues #145, #149): since the daemon stopped advertising its pairing token over mDNS TXT, the UDP beacon, and unauthenticated `/health`, every client's "a discovered URL is dialable" assumption became false — a discovered URL is `ws://host:port` with no token. Two rules, one per failure the change caused: **compare bridges by endpoint (host+port), never by full URL string** (a full-string compare against a paired `?token=` URL never matches, so Apple read every reconnect blip as "the daemon moved", dropped `savedUrl`, and redialed unauthenticated), and **an absent credential means "no information", never "clear it"** — a known endpoint inherits the credential it is already paired with, and a tokenless URL must not overwrite a stored token-bearing one (Android persists on the handshake-early CONNECTED edge, which the daemon reaches before closing 4001). Same rule in firmware: the ESP32 adopted the now-empty mDNS token into `g_state.authToken` and wrote it through to NVS, erasing the serial-provisioned credential. SSOT per surface with mirrored cases: `apple/AgentDeck/Net/PairingCredential.swift`, `android/.../net/PairingCredential.kt` (`PairingCredentialTests` / `PairingCredentialTest` share their cases); firmware guards live at the retain site in `esp32/src/main.cpp` and the persist site in `wifi_manager.cpp`
- **One machine has one pairing token, and the daemon currently serving the port is its custodian.** Either daemon can own 9120 and they keep the credential in different files — the sandboxed app cannot read `~/.agentdeck/auth-token`, and Node must not reach into the app's container (TCC hangs). So whoever starts SECOND adopts the incumbent's token off its **loopback** `/health` (`adoptPeerToken` in `bridge/src/auth.ts`; `AuthManager.adoptPeerToken` in Swift at `connectToExternalDaemon` and on each health poll while a client). No new trust — the probe dials `127.0.0.1`, and same-machine is already fully trusted. Without it, whichever daemon won the port decided whether the paired fleet authenticated, and a handover in either direction closed every board 4001 (2026-08-08: the whole WiFi fleet was locked out for hours, silently). The superseded token moves to a bounded **accepted ring** (`auth-token-accepted`, max 4, accepted but never handed out, cleared by `token rotate`), so convergence cannot lock out a device provisioned a moment before it. Two corollaries: **a credential must survive a reboot on every board, not just the ones that persist an endpoint** — `wifiSaveAuthToken`/`wifiLoadAuthToken` are board-agnostic while `wifiSaveProvisionedBridge` stays IPS10/T-Display-Pro, since a board that forgets its token has no way back on; and **the credential re-arm must not share a gate with WiFi provisioning** — `shouldSendWifiProvision` skips any board whose radio is up, which is exactly the board that needs a new token, so `auth_provision` (credential only, no WiFi side effects, ungated by `autoProvision`) is a separate message. Serial is the authoritative credential channel precisely because it still works when authentication is what is broken. Related trap: `onESP32Message`/`setOnMessage` **replace** rather than add, so everything the serial channel drives shares one handler.
- **"Same machine" and "us" are different questions, and only the second one licenses a privilege.** `isLocalConnection` is a pure IP test, so on a shared host every same-machine privilege the daemon lifecycle takes reached every account on the box: `daemon start` copied the incumbent's token into this user's home and asked it to stand down; the daemon's startup **sweeps the port window and shut down every Swift daemon in it** (one user starting a CLI daemon killed every colleague's macOS app); Swift `reclaimCanonicalPortIfNeeded` stood its own hub down for a stranger's daemon and rendered THEIR sessions here; and a port scan registered this user's sessions with whoever answered first. One predicate answers it — `localPeerOwnership()` in `bridge/src/auth.ts`, mirrored as `LocalPeerOwnership` in Swift — with **three values, not two**. `unknown` stays permissive and never silent: refusing on unproven ownership would break the one-machine-one-token convergence, which is how a whole paired fleet stops authenticating. The Swift mirror copies the CONTRACT, not the syscall — `kill(pid, 0)`'s EPERM means "another user" for Node and mostly "the sandbox said no" for the app, so Swift compares uids via `proc_pidinfo` and lands every failure in `unknown`. The decision lives in `negotiateIncumbentDaemon` (`bridge/src/daemon-takeover.ts`) rather than inline in the CLI action, because a truth table over the predicate stays green while a call site forgets to call it. **A refusal belongs where a peer is DISCOVERED, not where it is joined**: `alreadyRunning` is what sends the Swift app into client mode and it is thrown from `DaemonServer.init`, so refusing afterwards in `connectToExternalDaemon` bounces straight back into that initializer once a second, forever. **Not closed, by construction**: a TCP socket carries no peer credentials, so any local process can read `pairingToken` from `/health`; requiring the token on the operator routes defends against nobody while risking the same-user handover. See [docs/ENTERPRISE-ROADMAP.md](../../docs/ENTERPRISE-ROADMAP.md) §1.2
- **A discovery name must be unique per network SEGMENT, not per host.** Both daemons published the mDNS instance name `AgentDeck-9120`, so an office subnet had fifty daemons fighting over one name — and the Node conflict path does not rename: it swallows "already in use on the network" as non-fatal and republishes every 5s, forever. The name is now `AgentDeck-<host>-<userTag>-<port>` from the SSOT `shared/src/mdns-identity.ts` (→ `pnpm generate-mdns-identity`, vitest drift gate) — the value of this name is entirely in being computed the same way twice, so it is the last thing that may be hand-mirrored. `user` is an FNV-1a of `uid:username` and **never the account name**, because multicast is readable by everyone on the segment. TXT `v` stays `3`: no reader validates the key SET (the ESP32 walks the record for `agent`/`project`), so additive keys need no compatibility event — bump only when an existing key changes meaning

## Lifecycle: supervisor, port intent, build identity, restart

- **Nothing that may stop answering can gate a port release.** `DaemonServer.shutdown()` awaited `ModuleManager.stopAll()` — a task group waits for ALL of its children, so one wedged module (a BLE stop parked on a reply that never came) meant the `wsServer.stop()` below it was never reached. Quit survived this because `AppDelegate` arms a 3s watchdog and force-exits; **reclaim and stand-down had no such backstop and simply hung**, stranding the daemon on fallback port 9121 for the rest of its life after announcing it was reclaiming 9120. Bound such stages with `withBudget` (`DaemonActor.swift`), which **abandons rather than cancels** — cancellation is cooperative, and a subsystem parked on a continuation that never resumes never observes it. Two corollaries: a guard cleared only by a `defer` (`isReclaimingPort`) latches forever behind a suspended await, so it must not share a failure mode with the thing it guards; and **liveness ≠ availability** — `waitForDaemonExit` proves a daemon stopped ANSWERING, never that its port is free, so a taker must also wait for a real bind (`waitForPortBindable`). The canonical port may still be unwinnable for reasons neither daemon owns: a sleeping WiFi board with bytes queued leaves its socket in `LAST_ACK` and Network.framework exposes no `SO_LINGER` to RST out of it, plus macOS holds a NECP reservation ~14s after `NWListener.cancel()` during which `lsof` shows **zero** sockets and `bind()` still returns EADDRINUSE. So the CLI states why it is taking a fallback port instead of doing it silently. Ref: `bridge/src/cli.ts`, `bridge/src/session-registry.ts`, `apple/AgentDeck/Daemon/DaemonService.swift`, `apple/AgentDeck/Daemon/Server/WebSocketServer.swift` (`acceptedConnections` — the one listener accepts plain HTTP and SSE too, and only upgraded WebSockets used to be tracked).
- **A lifecycle command goes THROUGH the supervisor that owns the daemon, because the exit status has no room for intent.** Measured 2026-09-09 on a throwaway LaunchAgent carrying the shipped `KeepAlive{SuccessfulExit:false}`: a self-SIGKILL is respawned every time (~7s, the 10s minimum-runtime throttle), a plain `exit 0` leaves `state = not running, last exit code = 0` untouched. So the two remaining symptoms of that self-SIGKILL — a `daemon stop` that does not stay stopped, and a restart whose own child wins the port and leaves the daemon unsupervised until the next login — are not fixed by exiting 0: that trades the guaranteed exit (`process.exit()` has been seen joining a macOS serial fs worker and leaving the pid behind, 2026-06-06 — a daemon that will not die holding 9120 is strictly worse) for a *deterministic* version of the second symptom, since launchd deliberately does not respawn a clean exit. Intent is spoken to the supervisor instead (`bridge/src/daemon-supervisor.ts`): `stop` / `start` / `restart` drive the unit. **macOS is the asymmetric one** — `launchctl stop` only sends SIGTERM, whose handler ends in that same self-SIGKILL, so a stop that stays stopped must be `bootout` (which is not `disable`: the plist is still installed and reloads at the next login, exactly what `systemctl --user stop` and `schtasks /End` already mean), and the cost is that `kickstart` then fails rc 113 so the start plan must `bootstrap` first. Four rules the routing must keep, all in one truth table (`routeDaemonLifecycle`) rather than at two call sites: `--foreground` is never routed (that spelling IS the unit's ExecStart); a flag the unit's fixed argv cannot express (`-p`, `-d`, `--local`, `--loopback`, `--port-window`, `--wake-word`) forks as before **and says the result is outside the unit**, since a daemon nothing will bring back is what this exists to stop being silent; a posture the unit does not carry is a mismatch that also forks, or handing a loopback-only daemon to a default-posture unit rewrites it (the enterprise downgrade the inheritance exists to prevent, so the unit file is parsed for its real posture); and the stop hits the unit whichever way the start goes, or it respawns the old daemon into the middle of the new one. `waitForRestartedDaemon`'s `isChildAlive` becomes "is the unit's job still running" — without it the floor is a hard deadline again and a start still negotiating a stand-down reports as a failure. Live 2026-09-09: `runs = 7, last exit code = 0, state = not running` beside a ppid-1 CLI child serving 9120 → one `daemon restart` converged it to `state = running, pid = <daemon>`; the stop then held for 30 s (previously ~7 s). **`daemon install` converges too**, because registering a unit and that unit owning the daemon are different facts: an already-running unsupervised daemon makes the unit's job exit 0 against the incumbent guard, and install used to report success over `state = not running`. `classifySupervision` is the truth table, and only ONE of its five states acts — `foreign` and `unknown` act on nothing by rule, since the remedy for `unsupervised` is stopping a daemon and laundering "I could not look" into that verdict stops a healthy one on no evidence; `supervised` and `no-daemon` are reported, because an install that changed nothing and an install that could not start a daemon are different outcomes. It reads the state over an 8 s settle window rather than once: right after a load the job is `state = running` whether it is about to serve the port or about to exit 0 against an incumbent, so a single reading answers the wrong question — only `unsupervised` (which cannot un-happen on its own) short-circuits. A posture difference is applied, since install is the command that DECLARES the unit, and printed, since it must not be applied silently.
- **On Windows the autostart action is a LAUNCHER, so the task's status stops being the daemon's liveness.** Task Scheduler attaches a console to an interactive-token action and offers no way to suppress it, so a task whose action was `daemon start --foreground` — the spelling that made the task process *be* the daemon, for RestartOnFailure's benefit — left a terminal window and a taskbar button on the desktop for the daemon's entire life. Measured on Windows 11 26200 with Windows Terminal as the default terminal app, 2026-09-14: a long-lived `node.exe` action produced a visible `WindowsTerminal` window (enumerated with `EnumWindows`, titled with the action's command line) while the node process itself reported `MainWindowHandle = 0` — the window belongs to the terminal host, which also hosts the user's other consoles, so hiding or closing it is not available either. Three candidate fixes were tested and rejected: `<Hidden>true</Hidden>` hides the task in the Task Scheduler UI and not the window (a new window still appeared); `conhost --headless` did not run the action at all; and an `S4U` principal, the documented no-window route, fails `schtasks /Create` with "Access is denied" without elevation this installer does not have — and would return the daemon to a non-interactive session, which is why a Windows Service was rejected in the first place. So the action is `daemon autostart` (`bridge/src/cli.ts`): it spawns `daemon start --foreground` with `detached` + `windowsHide` (DETACHED_PROCESS | CREATE_NO_WINDOW — no console at all, not a hidden one) and exits within a few hundred ms, before the terminal handoff paints anything. No visible window 0.7 s or 5 s after `schtasks /Run`, detached daemon serving. The second half of the rule is the cost, and it is the same three-answer discipline as every other probe here: `Status: Ready` is now the steady state of a HEALTHY machine and carries no information about the daemon, so reading it as `false` is what makes `classifySupervision` say `unsupervised` and stop a daemon nothing is wrong with. So the DAEMON answers it: the launcher passes `AGENTDECK_SUPERVISOR=schtasks`, the daemon stamps `startedBy` into `daemon.json` **past its successful bind**, and `composeSchtasksRunning` reads that stamp whenever the status says `Ready` (`schtasksOwnsRegisteredDaemon`; `readDaemonInfo` already prunes a dead pid, so a stamp that comes back describes a live daemon and needs no pid comparison). **The launcher must not make the claim itself** — the first shape of this signal had it record the pid it spawned, and that failed live on 2026-09-14: installing over an already-running unsupervised daemon, the launcher's daemon hit the incumbent guard and stayed alive for a second or two while conceding, so "the pid the task started is alive" was true while the incumbent held 9120; the install printed `Daemon running under the scheduled task (PID <incumbent>)` and converged nothing, reopening this very hole from a new side. A daemon that loses the race exits before the stamp, so the stamp cannot lie about who is serving; an absent stamp (hand-started daemon, Swift daemon, pre-stamp build) reads as not supervised, never as unknown. The stamp inherits `daemon.json`'s one weakness, and it is bounded: a departing daemon can delete the file *after* its successor wrote it, so for a few seconds mid-handover there is no record (observed live 2026-09-15). That missing/unreadable record must read `unknown`, preserving the answering daemon; only a readable record without a stamp proves `unsupervised`. `ensureDaemonInfo`'s self-heal rewrites it from the record the live daemon built at startup — stamp included — which is why the stamp must live in that same object and not be computed at read time. `Running` and an unreadable status still answer on their own, which is what keeps a pre-upgrade task whose action still IS the daemon classified correctly. **And an install must end a running instance before `/Run`**: `MultipleInstancesPolicy=IgnoreNew` makes `/Run` against an instance of the PREVIOUS action a silent rc-0 no-op, so the upgrade registered the launcher, never ran it, and left the console-window daemon serving behind an install that reported success (measured the same day). Two losses to state plainly rather than paper over: `RestartOnFailure` now covers only a launcher that cannot spawn (the launcher waits for the child’s `spawn`/`error` event and exits nonzero on failure; a crashed daemon returns at the next logon or by hand), and `schtasks /End` no longer stops the daemon — `stopDaemon` was already ending the task *and* POSTing `/shutdown`, and it is the second one that does the work. Ref: `bridge/src/windows-service.ts` (evidence in the header), `bridge/src/daemon-supervisor.ts`, [docs/daemon.md § Autostart](../../docs/daemon.md), [docs/windows.md](../../docs/windows.md)
- **A console-less daemon means every child spawn needs `windowsHide` — the daemon has no console left to lend them.** This is the price of the launcher above, and it was invisible until it was paid: while the task's action WAS the daemon, the daemon held a console, its console-subsystem children inherited that console, and none of them drew anything. A DETACHED daemon has no console, so each such child gets a BRAND NEW one — and a new console comes with a window on the desktop unless the spawn passes `windowsHide` (CREATE_NO_WINDOW). Reported from a real desktop the same day the launcher shipped: an empty `C:\Windows\system32\taskkill.exe` window appearing every five minutes, from the Codex rate-limit probe's cleanup kill (`codex-rate-limits-live.ts` — `codex.cmd` runs under `shell`, so the child is cmd.exe and the real server is its grandchild, which is why a `taskkill /T` exists at all). Measured two-arm from a console-less detached parent, 12 spawns each: without `windowsHide` **138 window sightings**, with it **0**. The `adb reverse` poll had the same gap. Three things make a call safe, and the gate `bridge/src/__tests__/windows-child-window.test.ts` accepts exactly those: it passes `windowsHide`; or it runs a binary with no Windows counterpart (`launchctl`, `osascript`, `sysctl`, … — the spawn fails ENOENT and draws nothing); or it carries an inline `windows-hide-exempt:` comment saying why, for what a regex cannot see (a command in a variable, a POSIX-only branch, a CLI path that by definition already has a terminal). The gate reads only calls reached through a real `child_process` import — two BLE managers define their own local `spawnSync` helper — and blanks comments first, because its own first run reported a `spawn()` out of a sentence about EBADARCH. `node-pty` is not in scope: ConPTY draws no window.
- **A daemon's intent is persisted; its outcome never is.** `daemon.json` records the port a daemon actually bound and every client resolves through it. The port it *wanted* is a different fact, and until it existed a daemon bumped to a fallback had no way to know it was on the wrong port — so a 14-second kernel hold on 9120 became permanent. `bridge/src/daemon-port.ts` resolves that intent (`-p` › `AGENTDECK_DAEMON_PORT` › `settings.json daemonPort` › 9120, mirroring `AppPreferences.daemonPort`) and **only the user writes it** (`agentdeck daemon port <n>`); writing the outcome there instead is self-reinforcing, since the fallback port would then be preferred forever after. With an intent, a preferred port that cannot bind and answers no `/health` warrants bounded retries, not a claimed kernel diagnosis — #370 exceeded the old 20s margin — so the daemon retries (`preferredPortReclaimBudgetMs`, real listener retries, 90s cap on macOS and 20s elsewhere) and only then falls back, saying which port it wanted and why. Two consequences that are easy to get backwards: **`daemon restart` must read posture from the port the daemon is ON and restart on the port it PREFERS** (probing the canonical port blindly found nothing whenever the daemon had fallen back, and "no posture" is indistinguishable from "open posture" — a silent enterprise downgrade); and **anything asserting a fact about "this daemon" may only use a registry-resolved port**, never the blind default-port probe, which on a machine running a second AgentDeck answers with a stranger's daemon. The persisted port needs no argv baking — the autostart unit runs `daemon start --foreground` with no `-p` and the daemon re-resolves, which is exactly why the posture flags (a fact that exists only on a command line) must be baked and this one must not.
- **A running daemon carries the identity of the build it started with, because `dist/cli.js` is overwritten in place.** On a source checkout `agentdeck` is a shim onto `bridge/dist/cli.js`, so a daemon started before a rebuild keeps executing bytes that no longer exist on disk while reporting the same pid, port and package version as one started after it — `daemon start` answered "already running" and exited 0 about code the user had just replaced (2026-08-24: a daemon from 04:19 still held 9120 at 19:20). `/health.build` is a 12-char **content** digest of `bridge/dist` + `shared/dist` + `hooks/dist` (`bridge/src/daemon-build-identity.ts`), and three properties are load-bearing. It is content, not mtime: `tsc` rewrites every output on every run, so an mtime stamp would restart a healthy daemon for a rebuild that changed nothing. The daemon **captures it once at startup and never recomputes** — a daemon that recomputed would report the newest build on disk the moment someone rebuilt, i.e. exactly the state the field exists to detect. And eviction requires **both** digests to be known and differ: a daemon predating the field sends none, and evicting on no information turns every start into a restart, autostart units included (`--no-upgrade` opts out; the ownership gate still outranks freshness). The CLI keeps the build itself current — `daemon start` / `daemon restart` on a checkout build stale packages and then **re-exec**, because a process that loaded the old `cli.js` and then dynamically imports the new `daemon-server.js` is a mixture nobody chose. Its staleness pre-filter is trusted **one way only**: "no source is newer than its build" safely skips the compiler, while the other direction over-reports (a composite project like `shared` rewrites nothing when a rebase or `touch` moves an mtime), so the real decision is the build digest before vs after. Never build on the autostart path (no terminal ⇒ warn only): a failed build there becomes a `KeepAlive` respawn loop. See [docs/daemon.md § 어떤 빌드가 포트를 잡고 있는가](../../docs/daemon.md)
- **A restart is verified by the identity of the daemon that came up, never by the pid this command forked.** The daemon ends `/shutdown` by SIGKILLing itself (`exitProcessNow`), and a self-signalled death is not a successful exit — so launchd's `KeepAlive{SuccessfulExit:false}`, systemd's `Restart=on-failure` and the Scheduled Task's RestartOnFailure all respawn it within a few seconds. On any machine that ran `daemon install` the respawn routinely beats `daemon restart`'s own child to the port; the child then hits `daemon start`'s incumbent guard, exits 0, and a wait keyed on its pid can only time out. That printed `restart FAILED — no daemon with PID <n> is answering` over a daemon that was serving the new build the whole time (2026-09-08, twice; reproduced live 2026-09-09 as PID 27022 winning against child 27028), and the user's natural retry then stops a healthy daemon. `waitForRestartedDaemon` therefore asks three questions in order: is a daemon answering on a candidate port, is its pid **not** the pid we stopped (the old test's real purpose — a port probe alone is satisfied by the daemon the stop failed to remove), and is it serving the build on this disk. The build check exists because "a daemon restarted" and "your code is live" are different claims and only a supervisor can split them — the unit launches whatever `agentdeck` resolves to at ITS path, which may be another install — so a known mismatch fails loudly while an **unknown** build on either side is not a mismatch at all.
- **A late timer is not a sleep.** The Node daemon's wake detector read any 5 s tick landing more than 15 s late as a system wake and ran the whole device-recovery storm (mDNS republish, pairing re-arm on every ESP32 board, BLE workers restarted, usage refetch). Under load that is what a starved event loop produces with no sleep at all — 2026-09-10, load average 13–17, `pmset -g log` showing ZERO sleep events, **123 false wakes in a day**, one every one to four minutes at the peak — and each storm starved the next tick, so the detector fed itself, and left `/health` unanswered long enough for the macOS app to promote to a fallback port and stand down again, three times in five minutes. The wake signal is the DRIFT between the wall clock and the monotonic clock (`classifyClockTick`, `bridge/src/bridge-core.ts`): across a real suspend the wall clock jumps while `CLOCK_MONOTONIC` does not (Darwin, Linux); under load both advance together, which is `lag` and is logged as such. Windows' monotonic clock counts through sleep, so there the gap rule stays and is documented as the weaker instrument. Same family as the flash-id and `lsof` probes: a signal that cannot tell "the event happened" from "I was too busy to look" must not be allowed to fire the expensive branch.
