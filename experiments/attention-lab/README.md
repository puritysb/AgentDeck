# Attention Lab — isolated UX hypothesis

이 문서는 합성 데이터의 **브라우저 A/B/C 비교**를 설명합니다.
실제 세션을 읽는 후속 SwiftUI 관찰 창과 제품 메뉴바의 opt-in 패널은
[Native attention observation](native/README.md)을 참고하세요. 두 실행 경로는 분리되어 있습니다.

기존 제품을 교체하지 않고 **테라리움의 존재감, 사람이 필요한 순간, 되돌아올 맥락**의 관계를 비교하는 로컬 프로토타입입니다. 제작 시점의 기준 커밋은 `7ff90b27`입니다.

## 실행

Node.js 22 이상이면 설치 없이 실행합니다. 루트 dev 명령이나 실제 브릿지를 실행하지 않습니다.

```sh
cd experiments/attention-lab
npm start
```

기본 주소: http://127.0.0.1:4317. 포트 충돌 시 `AGENTDECK_LAB_PORT=4318 npm start`처럼 이 프로세스만 바꿉니다. 종료는 실행 터미널에서 Ctrl+C.

```sh
npm run check
npm test
```

## 비교할 가설

| 안                 | 데스크톱 표현                         | 검토할 질문                                       |
| ------------------ | ------------------------------------- | ------------------------------------------------- |
| A · Habitat        | 큰 공간 표현 + 별도 attention/context | 공간이 인지에 도움이 되는가, 장식에 가까운가?     |
| B · Work list      | 고정 순서 세션 목록 + context         | 공간 없이도 중요한 변화를 빠르게 찾는가?          |
| C · Quiet overview | 얕은 존재감 + 목록 + context          | 평소에는 조용하고, 개입할 때는 충분히 구체적인가? |

E-ink는 읽기 중심·모노크롬 표현으로, 키 데크는 15키의 고정 대상 배치로 같은 상태를 투영합니다. E-ink의 B/C는 의도적으로 수렴하고, 키 데크는 세 안이 같은 투영을 씁니다. 모든 화면에 서로 다른 스킨을 강요하지 않는 가설입니다. 실제 기기의 해상도·키 매핑·입력 지원·새로고침 특성을 구현한 것은 아닙니다.

기존 화면 참고는 저장소의 **과거 macOS 캡처**입니다. 실시간 화면이나 동일 fixture의 대조군이 아닙니다. A 역시 기존 테라리움의 정확한 재현이 아니라 공간 중심 배치의 근사입니다. 예쁜 이미지 선택이 아닌 정보 배치와 상호작용 검토용입니다.

## 10분 리뷰 순서

1. 5세션·평상시에서 A/B/C 전환: 다른 일을 하다 돌아왔을 때 파악할 정보가 충분한가?
2. Documentation을 선택한 뒤 동시 대기: 새 요청이 눈에 들어오되 읽던 맥락과 세션 위치는 유지되는가?
3. 승인 대기와 답변 가능 비교: 표시 전용 요청을 여기서 승인할 수 있다고 오해하지 않는가?
4. `API Client · api에 직접 승인 API가 생긴다면` 켜기: 기존 패널이 응답 가능한 패널로 확장된다. 이는 **가상 capability**이지 현재 Codex API 지원을 뜻하지 않는다.
5. 연결 끊김과 요청 만료: 마지막 대기와 현재 유효한 대기를 구분하는가? 응답은 차단되는가?
6. 응답 도착: 에이전트의 보고를 검증된 완료로 읽지 않는가?
7. 1/12세션, E-ink/키 데크 전환: 동일 프로젝트명·여러 대기·좁은 공간에서 대상이 명확한가?

각 안에 대해 개입 대상 찾기 시간, 잘못된 대상/불가능한 응답 선택, 원래 맥락 복귀 횟수, 읽기를 방해한 변화, 다시 사용하고 싶은 표면을 기록합니다. 수치와 선호도는 아직 수집하지 않았습니다. `순서대로 재생`은 사용자가 켠 동안만 6초 간격으로 fixture를 바꾸며 마지막 시나리오에서 멈춥니다. 연속된 실제 실행 기록이 아닙니다.

## 에이전트 발전을 흡수하는 최소 실험

안정적으로 유지할 것은 **대상·관측한 상태·요청·출처·응답 가능 여부**입니다. `model.mjs`의 `canAnswer`를 세 표면이 공유합니다. 하네스가 직접 응답 기능을 제공한다는 가정을 켜면 새로운 전용 화면을 만들지 않고 같은 요청 패널이 확장됩니다. 미지의 요청 종류는 응답 가능으로 추정하지 않습니다.

이것은 범용 capability protocol의 완성본이 아닙니다. 실제 통합에서는 하네스별 권한/유효성 확인, idempotency, 취소·재연결, 요청 identity, provenance, 네이티브 경로를 검증해야 합니다. 모든 에이전트를 최저 공통 기능으로 묶거나 각 하네스의 전체 UI를 복제하려는 목적이 아닙니다. 하네스가 좋아져 제품의 중복 코드가 줄어드는 것도 성공입니다.

## 격리와 제한

- 합성 프로젝트·세션·이벤트만 사용합니다. 실제 agent, daemon, bridge, WebSocket, credentials에 연결하지 않습니다.
- 응답 버튼은 메모리 안의 fixture만 수정합니다. 새로고침하면 사라집니다. 파일·브랜치·실제 작업에는 영향을 주지 않습니다.
- 서버는 loopback에만 바인딩하고 명시한 정적 파일만 제공합니다. POST는 거부하며 브라우저 CSP는 네트워크 연결을 차단합니다. 외부 서비스에 공개하지 마세요.
- 제품 코드, 루트 패키지/lockfile, native 앱, 배포 설정은 수정하지 않습니다. 기존 디자인 토큰·폰트·공식 마크를 읽기 전용으로 재사용합니다.
- 자동 테스트는 대상/요청 ID, 선택 유지, capability 제한, 오프라인/만료, 중복 응답, asset allowlist를 검증합니다. 실제 하드웨어 사용성·접근성 인증·운영 통합 검증은 아닙니다.

다음 결정은 이 실험을 곧바로 병합하는 것이 아니라 **실제 사용자 관찰로 A/B/C 가설을 좁힌 뒤, 기존 제품 내부의 opt-in 읽기 전용 패널로 옮길지** 정하는 것입니다.

## 이번 구현에서 확인한 범위

- 문법 검사와 자동 테스트 11개 통과.
- Chrome에서 A/B/C, 승인 capability 전환과 모의 응답, 동시 대기 중 선택 유지, 오프라인/만료의 응답 차단, 초기화, 참고 화면 모달을 확인했습니다.
- 12세션·390px 폭에서 데스크톱/E-ink/키 데크 모두 문서 가로 넘침이 없고 선택형 응답 2개가 유지되는 것을 확인했습니다. 좁은 화면은 맥락을 목록 앞에 두며, 사용자의 명시적 세션 선택 때만 맥락으로 스크롤합니다.
- 브라우저 검증 시 console error 없음. 이 기록은 수동 smoke test이며, 지속 실행되는 브라우저 회귀 테스트나 실사용자 평가가 아닙니다.
