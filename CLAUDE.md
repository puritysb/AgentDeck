# AgentDeck

Stream Deck+ controller for AI coding agents — a bidirectional local control system.

## Monorepo

- **bridge/** — Node.js server: Daemon hub + Session Bridge (PTY, hook HTTP, state machine). `src/apme/` — APME eval module (SQLite store, collector, deterministic+LLM judge runner, category-aware rubrics, turn-level mid-session eval, Pareto recommender, daemon HTTP API). Full detail — including the measurements behind each rule below — is in [docs/apme.md](docs/apme.md); the incidents are in `DEVELOPMENT_LOG.md`. The invariants:
  - **Canonical `SessionSample`** (`shared/src/sample.ts` + `sample_events` table) is the SSOT: a bounded unit with a typed trajectory (user/assistant/model/tool/subagent/state) that both the timeline and the eval derive from. Per-unit cost via `shared/src/pricing.ts` (override-loadable), Pareto-frontier recommender (`apme/pareto.ts`) surfaced via the dashboard **Recommend** tab, trajectory scorers (`apme/scorers/`).
  - **Eval results are off the device timeline** (timeline = activity log only) — they flow via the `apme_eval` WS event + scorecard/SQLite. **Task rows render one-per-task**: `task_end` is data-only (spinner stop, judge upsert, reaper) and never a standalone row — the `task_start` header folds the closure in (SSOT `shared/src/timeline-task-display.ts`, mirrored Swift/Kotlin/TUI; glance surfaces exclude task rows entirely). Env `AGENTDECK_TIMELINE_PROJECTION=1` (default off) flips the device timeline to the sample projection (suppresses adapters' direct chat/tool rows).
  - **Tasks segment on explicit boundaries** (`/task close`, `/clear`), `session_end`, or a **15-minute generic idle gap** armed at turn close (`AGENT_IDLE_GAP_MS`; 96% of real claude inter-turn gaps are shorter, and without it codex tasks reached the judge only via the 30-min orphan reaper — hours late or never); TodoWrite-all-completed is a non-segmenting soft hint. **The collector's state is re-adopted from the store at daemon start** (`rehydrateOpenRuns`, daemon-only) because the idle-gap timer and every session→run/task/turn edge are in-memory, so a restart otherwise stranded every mid-session run for the 2-hour reaper. The reaper stamps what it found: a task whose turns all closed is `idle_gap` (reached late), only one holding an open turn is `orphaned`, and `stop-health` reports reaped turns in their own `Reaped` column rather than folding them into session ends (which read a 29% codex loss as 11%). **Adoption at startup is provisional** — a rehydrated run counts as live to the reaper only once its session sends a hook (`rehydratedSessions` / `isLiveRun` / `releaseRun`), because a session that ended while the daemon was down has no Stop coming and no idle timer (those arm on turn close).
  - **A turn closes at its Stop, and records WHICH signal closed it** (`turns.end_source`: `stop` / `synthetic_stop` / `next_prompt` / `interrupted` / `session_end` / `run_close` / `clear`) — closing at the next prompt instead put the user's typing time inside the turn's duration, and without the attribution a dropped Stop hook is byte-identical to a normal close, so its rate was unmeasurable. `agentdeck apme stop-health` reads it; pre-column rows are never backfilled. **A turn open at startup or at the next prompt is closed by the agent's OWN record, at the record's time** — Codex's rollout (`codexCompletionProbe`) and Claude's transcript (`claudeTurnCompletionSince`, located under `~/.claude/projects` by session id): `end_turn` → `synthetic_stop` with the reply, `task_complete.error` / `stop_sequence` → `aborted`, a mid-turn tail claims nothing (most `next_prompt` turns hold a completed reply or an API failure, not a dropped hook). **A reply arriving after `closeRun` still lands** (`latestClosedTurnIdForSession`, 60 s window): one-turn workers send SessionEnd 80–130 ms after Stop, ahead of the deferred transcript re-read.
  - **A user cancel is not a lost hook**: ESC emits no hook at all, so no Stop was ever due — `interrupted` is its own bucket, outranks `synthetic` when both are set (a cancel can only ever arrive AS a synthetic Stop), and stays out of the loss ratio. It is detected two ways because one is not enough: the watchdog sees the marker while it is still the transcript tail, and the next-prompt close runs `readInterruptSince` for the commoner cancel-then-retype shape that buries it. The marker predicate is single-source in `bridge/src/claude-interrupt-marker.ts` (observer + watchdog + collector) and reads **text blocks only** — a `tool_result` quoting the same sentence is routine and would otherwise invent a cancel. Missed-Stop recovery is **two wirings, not one** — `claude-turn-watchdog.ts` per PTY bridge, `observed-turn-watchdogs.ts` per observed session inside the daemon (the first alone covers none of the real traffic). Recovery **re-enters the real Stop path** (the daemon self-POSTs its own `/hooks/Stop`) rather than reimplementing it, and a synthetic Stop must never drain a queue whose delivery needs a listener (`takeDirectiveForStop`).
  - **A Stop hook's reply source is chosen per agent** (`hook-response-source.ts`): inline text first, else each agent's OWN reader — a Codex hook carries `transcript_path` too (its rollout), and handing it to the Claude reader left it replyless; the same payload's `model` stamps the TURN (`turns.model_id` is the scorecard source). **A verdict about the agent's work needs the agent's work**: `task-gradeability.ts` is the Node SSOT declining `no_reply` / `aborted_only` / `trivial` tasks and stamping the reason on the row; `generate-apme-display-rules` emits `TaskGradeabilityRules.generated.swift`, and both suites replay `shared/task-gradeability-vectors.json` so the App Store daemon makes the same decision.
  - **The task judge backlog drain feeds ONE task per tick and only when nothing is in flight** (judge `ready` only, 30-day window, declined rows excluded), a park after two failures expires after 30 min, and an `unavailable` backend is re-probed every 5 min — a local model busy with someone else's inference at startup used to switch the drain off for the life of the process, and three concurrent requests per tick against a serial server parked every pending task with no log line. **The task it feeds is chosen park-aware** (`pickBacklogTasks` over a 200-row window, not the query's first row): the query orders `ended_at DESC` and `enqueueTask` drops a parked task SILENTLY, so a task whose judge call fails every attempt owns that head and every tick spends its one slot on it — that stranded 156 older tasks for two weeks while the day's own tasks were judged normally by the live close path. A window in which every candidate is parked says so in the log, once per park period, because silence is what let that run for two weeks.
  - **A task's display title is its first user prompt, and the judge summary outranks it once it exists** (`deriveTaskTitle` SSOT `shared/src/task-title.ts`; the Swift copy is GENERATED — `pnpm generate-apme-display-rules` → `TaskTitleRules.generated.swift` — with behavior pinned by the shared vector file `shared/task-title-vectors.json` both suites replay: a markup-first prompt derives null, a slash PATH is not a slash command, all index math is code points): the intent title fills the one-line slot until judged, the outcome sentence wins after, and the `Task N` fallback stays the display SSOT's "meaningless" shape. The `/apme` default tab is a task-first **Work board** (lifecycle buckets + attention-first sort; bucket SQL is single-source in the store so filter, row flag and badge cannot disagree — attention is 7-day windowed because the unwindowed bucket measured 93% of all history). Every row exposes its project + native session as a contextual drill-down; the exact `session_id` scope gathers that session's tasks and changes ordering to recency so its work reads as one chronology, with the same entry point in Run/Task detail.
  - **The default judge chain is `mlx → foundationModels`, and the FM leg is a FLOOR, not a peer**: on-device FM measured 0.580 on the judge-fidelity rubric (vs 0.86–1.00 for the MLX tier) and its window is a hard, measured 4,096 tokens that refuses 4.2% of real `task_rollup` judge prompts — but dropping it as the fallback would remove evaluation outright from every machine with no MLX server. The fallback rides the DEFAULT only (`fallbackToFoundationModels`): a backend the user NAMED, offline, still skips visibly. The two daemons read one `settings.json`, so the legs must resolve it identically or the same user config scores differently depending on which daemon holds 9120, with nothing in either log saying so (#299): the MLX URL resolves `apme.judge.endpoint` then the `llm.mlx` pin on BOTH (Swift read the pin for the model only and hardcoded the URL to loopback), the MLX timeout is 90 s on both (Swift's 60 s timed out on the very prompt shape the 68.7 s measurement came from), the MLX→FM fallback is logged at normal level on both (behind Swift's debug flag the cut rate the 1.05 default is calibrated against was unmeasurable there), and a judge response is accepted on 200–299 on both, mirroring `resp.ok` — which changes nothing about the BODY gate. Still divergent: Swift has no `response_format` ladder at all, and the two `task_category` classifiers differ in backend, `max_tokens`, timeout and fallback, which selects a different rubric. Two consequences: anything that must decide before the call — the REVIEW tier and its diff budget — resolves the leg that will actually answer first (`resolveJudgeBackend` / `ReviewRunner.resolveBackend`), because the legs' windows differ 4×; and a prompt budget for the on-device leg is sized in MEASURED tokens, never characters (the `basic` tier's own caps used to build a 5,161-token prompt for a 4,096-token window, since the activity block is the user's own Korean prompts at ~1.15 chars/token).
  - **Judge transport completion is part of verdict validity, but the rule is about the BODY, not the flag**: both daemons reject an empty content, a `choices` that is not a non-empty array, and a `finish_reason=length`, full stop. **An exemption for "its object closed, so the verdict finished" was tried and removed** (#286 item 3): brace topology cannot tell whether the model finished, so the exemption produced a defect in three consecutive adversarial review rounds — first admitting a reasoning model's `<think>` scratchpad when the real verdict was the part that got cut, then refusing complete verdicts whose trailing prose held an unmatched brace — and it had no measured beneficiary, since the one cut mode observed on this fleet is a repetition loop INSIDE the `summary` string (gemma-4-26b, running to the 800-token cap without closing) where depth never returns to zero. `parseJudgeJson` already refuses exactly the incomplete case; rejecting the complete one silently rerouted the default chain to the FM floor. The rate is visible — the park log names this failure (an earlier claim that a re-attempt clears it two times in three is **WITHDRAWN**: it came from a probe writing `task_category: unknown` where `runTaskEval` resolves it from the run, i.e. a request the daemon never sends).
  - **Both daemons extract that object the same way** (first BALANCED `{…}`, Node keeping the old greedy span as a second candidate because a key that lost its opening quote desyncs any string-aware scanner and is what `repairJudgeJson` exists for): Node's greedy-only match spanned into trailing prose and called a verdict cut that Swift scored. **Which of several objects is the verdict is decided by `overall`, never by position** (`parseJudgeObject` / `ApmeRunner.selectVerdictObject`), and two spans carrying it are AMBIGUOUS and resolve to null: scanning balanced blocks makes more spans parseable, so "the first that parses" scored a local reasoning model's `<think>` scratchpad instead of its answer — a wrong score in `evals` is strictly worse than a loud skip. The vectors carry a `verdict` field (defaulting to `accepted`) separating "the transport returned it" from "the parser produced a verdict from it", because that is the only way to pin a body the gate must pass and the parser must refuse. Two known parser asymmetries the vectors CANNOT express, both in the same direction (Node scores, Swift skips): Node's greedy second candidate and `repairJudgeJson` for the lost-opening-quote defect Gemma 4 emits, which Swift has neither of — porting the repair would be a new hand mirror, so it is recorded here rather than duplicated.
  - The **Anthropic `api` leg** carries the same rule under its own spelling (`stop_reason` `max_tokens` / `refusal`), sends the same `max_tokens: 8192`, resolves the same default model, and sends no `temperature` — sampling parameters are rejected outright on Opus 4.7+, so that leg 400'd for every current model and reported it as `nil`, i.e. the same shape as "no API key". Shared `apme-judge-response-vectors.json` pins the chat-completions gate and `apme-judge-api-response-vectors.json` the Anthropic one — the api leg is reached only through the SDK, so without its own vector file reverting either rule left both suites green. Serving completion rates are not judge-accuracy evidence.
  - **The MLX judge leg — that leg only — sends `repetition_penalty`** (default 1.05, `apme.judge.repetitionPenalty`; exactly 1 disables and omits the field), because gemma-4-26b loops inside the `summary` string and runs to the cap without closing the object. Measured 2026-09-07/08 under two designs — three back-to-back repeats and three INTERLEAVED so each is separated by five other prompts (evicting the server's prompt cache) — with identical totals AND identical task-by-task results: **4 of 6 tasks cut → 1 of 6**, no task worse. The headline is the TASK count on purpose: greedy decoding at `temperature: 0` is specified to repeat itself given identical server state, so the repeats are the stability result and the independent unit is the task (n=6) — and that cuts both ways, since the spec says nothing about a restart and every run in the record was answered by one long-lived `mlx_vlm.server` process. **The server silently ignores unknown fields** — a made-up parameter returns 200 like a real one — so acceptance proves nothing; that this one is honoured is shown by the OUTCOMES across penalty conditions on the same prompt at `temperature: 0`. `repetition_penalty` is NOT OpenAI-standard, so it carries its own per-endpoint escape hatch and is given up **before** `response_format` — otherwise a strict server's 400 is misread by `isJsonModeRejection` as a JSON-mode refusal, costing JSON mode for the whole process AND still failing. **In the MLX ladder a field is only written off once dropping it is PROVEN to have helped**: the suppression is recorded after a retry succeeds, never when the ladder gives the field up. When BOTH fields came off before the request succeeded the evidence names neither, so the rule is to make the CHEAP mistake and blame the penalty — writing that off costs the cut rate and self-corrects on the next call, while writing off JSON mode is permanent and never re-probed. **When the PROMPT was compacted after a drop, neither field is written off at all**: that success differs from the failure in two ways and the other one — no longer overflowing the context — explains it by itself, so the field/field asymmetry does not reach it and marking an endpoint for one long prompt is not a cheap mistake. Both daemons gate the SEND on `> 1` and read only 400/422 as a rejected request. The openai-compatible leg deliberately does NOT send it: that adapter serves OpenRouter and any other OpenAI-compatible endpoint, several of which honour the field, so sending it would silently change sampling for a judge the user pays per call on evidence measured against one local model. The 1.05 default is a **hand mirror** (`MLX_JUDGE_REPETITION_PENALTY` / `ApmeJudgeMlx.defaultRepetitionPenalty`) with no generator — fold it into a generator when next touched.
- **plugin/** — Stream Deck SDK v2 plugin for macOS and Windows. Six actions: two keypad (`session-slot`, plus the opt-in Claude-limit gauge `limit-key`, which is placeable but in no bundled profile) + four SD+ encoders — E1 Volume (`utility-dial`), E2 Claude Usage (`option-dial`), E3 Codex Usage (`iterm-dial`), E4 Launcher (`launcher`). UUIDs are immutable post-distribution so several no longer match their display name; the mapping is in [docs/streamdeck-layout.md](docs/streamdeck-layout.md). - **plugin-ulanzi/** — Ulanzi Studio plugin for the D200H Deck Dock and D200X LCD keys (official UlanziDeckPlugin-SDK). One dynamic keypad action + session-centric two-level UX, sharing the `@agentdeck/shared` `buildSessionDeck` layout engine. D200X encoders are a separate, not-yet-shipped action/UX; keypad support must not imply encoder support. Connects to the daemon over WS like the SD plugin and is the **sole** Ulanzi deck driver — the Node/Swift direct-HID paths and the legacy `zkswe/` research tree are gone. The Studio handshake does not identify D200H versus D200X, so the daemon preserves the historical `d200h` health wire identity and reports connectivity from `ulanzi-plugin` WS presence. **The Marketplace bundle ships NO native binary, and that is enforced at package time, not intended.** `@resvg/resvg-js` needs one `.node` per architecture, so a single bundle that must run everywhere carried five (18.5 MB of a 20 MB plugin, four unusable on any given machine) and macOS raised "Apple could not verify". Signing was never the fix: a loose native module inside a folder Studio downloads and unpacks has no owner who can sign it for the process that loads it. `@resvg/resvg-wasm` is the same resvg version and Rust core (**pin the two in lockstep** — the identity is the whole argument), ships as one file identical on every OS/CPU, and renders byte-identically (measured over 34 tiles spanning both raster sizes, every session state and `feGaussianBlur`). Three consequences: `initWasm` is async while every tile render is sync, so `app.ts` awaits `initRaster()` **before the Studio bridge opens**, i.e. before any `onAdd` can ask for a key image; fonts became load-bearing, since the WASM build has no filesystem and therefore no `loadSystemFonts` fallback, so a bundle missing them renders every tile textless; and the packaging verify walks the **tree** for `.node`/`.dylib`/`.so`/`.dll` rather than checking package names, so a dependency that grows an optional native accelerator later cannot slip one back in. See [plugin-ulanzi/VERIFY.md](plugin-ulanzi/VERIFY.md)

## Build

**Node runtime support:** the Node bridge/tooling supports the maintained,
prebuild-verified even lines **22, 24, and 26**. Node 20 reached EOL in April
2026 and is intentionally unsupported; odd-numbered releases are not product
targets. `package.json` declares the range and `pnpm-workspace.yaml`'s `engineStrict` makes it fatal, while
`agentdeck diag native` opens an in-memory `better-sqlite3` database under the
exact executable/ABI that will run the daemon. Windows daemon autostart pins
that executable, so rerun `npx @agentdeck/setup --yes` after changing Node
installations to reinstall native bindings and re-register the Scheduled Task.

```bash
pnpm install
pnpm build                  # shared must build before bridge/plugin
pnpm generate-icons         # SVG → PNG icons (first build or after icon changes)
pnpm generate-creature-glyphs  # canonical creature SVG → ESP32 alpha-mask C header (esp32/.../creature_glyphs_generated.h)
pnpm generate-micro-glyphs  # Timebox 11×11 TS→Swift mirror + official brand SVG → Pixoo/iDotMatrix/TC001 generated alpha masks
pnpm generate-protocol      # protocol.ts → JSON Schema → Swift/Kotlin types (generated/protocol/)
pnpm generate-terrarium-rules  # terrarium-rules.ts SSOT → Swift/Kotlin/C++ generated mirrors (vitest drift gate)
```

### Apple Release (App Store / TestFlight)

Release steps, local build commands, identity/signing, CI secrets, and current App Store state live in **[RELEASING.md § Apple](RELEASING.md)**. Two invariants that apply outside a release:

- **Bundle ID** `bound.serendipity.agent.deck`. The retired `bound.serendipity.agentdeck.*` tree carries an immovable ASC build floor (1.0.6/build 8) — never target it. The Stream Deck **plugin UUID** `bound.serendipity.agentdeck` (no suffix) is a separate, immutable identifier, unrelated to the app bundle ID.
- **Versioning**: root `VERSION` is the repository baseline and compatibility-major anchor (`1.0.2`), not a minor/patch ceiling. Numeric `X.Y.Z` versions are mutually compatible exactly when `X` matches: major changes are protocol-breaking or exceptionally large coordinated migrations, minor changes add substantial backward-compatible features, and patch changes are small backward-compatible fixes. Minor and patch values may advance independently by target. Each target's internal mirrors and its own release tag must match exactly, and `pnpm verify-version` enforces repository compatibility. Apple build number and Android versionCode advance only when those targets ship. Delivery tags remain channel-prefixed (`apple-v*`, `android-v*`, `esp32-v*`, `npm-v*`, `streamdeck-v*`, `ulanzi-v*`).

### Multi-Agent Development Surface

This repo is built by switching between Claude Code, Codex, OpenCode, and Antigravity. **[docs/agent-harness.md](docs/agent-harness.md)** is the canonical map of how each agent enters the repo, what it reads, and what it auto-discovers — read it when onboarding a new agent or wondering why a skill/workflow isn't picked up.

- **Repo instructions**: `AGENTS.md` is the entry file Codex/OpenCode/Antigravity discover by convention. It requires `CLAUDE.md` first, then targeted `DEVELOPMENT_LOG.md` lookup instead of loading the full log. The active log keeps only the most recent ~2 months; older entries are archived by month under [`docs/devlog/`](docs/devlog/README.md) — grep a specific month file when you need history, never load all archives at once.
- **Repo skills (SSOT)**: canonical skills live in `.agents/skills/<name>/SKILL.md` (discovered by Codex; Claude reaches them via the pointers in `.claude/skills/`). Use them before hand-rolling commands. **`.claude/skills/*.md` are thin pointers — never put procedure content there; edit the `.agents/skills/` copy so the two agents can't drift.**
- **Workflow originals**: `.agents/workflows/` remains the canonical human-readable procedure directory; skills may route into these files. OpenCode has no skill auto-discovery — point it at these workflow files explicitly.
- **Session handoff**: use the `session-end` repo skill before `/clear`, `/new`, or handing work to another session. It summarizes current state and updates durable docs only when the change is project-significant.
- **Codex observation**: `agentdeck daemon install` installs/migrates Codex lifecycle hooks in `~/.codex/config.toml`; run `codex` normally. Deprecated `agentdeck codex` still refreshes them before launching its PTY bridge during the compatibility window.
- **OpenCode observation**: `agentdeck opencode` / `agentdeck daemon install` install the AgentDeck observer plugin (`~/.config/opencode/plugins/agentdeck.js`) so standalone `opencode` runs report `opencode_*` lifecycle hooks to the daemon — same observed-session timeline pipeline as direct `claude`/`codex` (`classifyObservedHookEvent` in `bridge/src/daemon-server.ts`). The Swift daemon ingests `opencode_*` too: `opencode:<id>` session rows + chat_start/tool_exec/chat_response timeline rows in `DaemonServer.handleHookEvent`, converging with the opt-in SSE observer on the same session key. Both daemons normalize Claude/Codex/OpenCode lifecycle names into the agent-neutral APME boundary vocabulary; Codex response text comes from the rollout tail (`bridge/src/codex-rollout-response.ts`).
- **A Gateway event you never subscribed to is indistinguishable from one the Gateway does not send — and subscribing is not the same as consuming it.** `sessions.subscribe` is a no-param RPC under `operator.read` (the scope `sessions.list` already runs under) and it is the entire admission gate for `session.message` and `session.tool`: a connection in neither subscriber set receives nothing. The Node adapter never called it, so its handlers sat wired and unreachable; the Swift adapter DID call it and then discarded every frame — a different failure and the harder one to see. The only frame arriving was `chat`, and **that frame is assistant-only**: no user prompt, no tool array, no token counts, no model. So nothing emitted a `turn_start`, and a `turn_response` with no open turn is dropped by `Collector.setTurnResponse` — **657 of 665 recorded OpenClaw runs held zero turns**, all closed at ~1800s by the orphan reaper. Three copies of one guess kept it invisible: `ChatEventPayload` declared `prompt`/`tools`/`modelId`, a fixture supplied them, and the parity test read them back — a fixture, a type and an assertion authored together from one assumption agree with each other forever. Fixtures are now **captured off a live Gateway and asserted through the real parser** (`tests/parity/gateway-frames/README.md`). Ownership after the fix, so no fact is counted twice: prompt ← `session.message`(user); tools ← `session.tool` (args AND result, under `data`, never at the top level); per-turn `provider`/`model`/`usage` ← `session.message`(assistant) as a `session_meta` span; response ← both `chat.final` and `session.message`(assistant), deliberately — a run the Gateway hides from the control UI never sends `chat.final`, and the sample layer dedups on `kind|turnIndex|hash(text)`. **`chat.final` is also OpenClaw's stop signal** and emits `turn_end` (`end_source='stop'`; a cancel emits `interrupted`).
- **An OpenClaw APME run is scoped to a session KEY, never to the Gateway connection.** One connection sees every session the agent has — the user's chat (`agent:main:main`), each cron job (`agent:main:cron:<id>`), and a fresh key per model-eval run (a suite opens six in three hours). A connection-scoped run interleaves them into one trajectory under one `model_id` and computes the idle-gap boundary across unrelated conversations, so turn ordering, per-task cost and every judge verdict describe a conversation that never happened. `openclawRunForSessionKey` opens `openclaw:<sessionKey>` lazily on that key's first event and `setApmeRunResolver` hands it to the adapter; **each key owns its own idle-gap timer**, or a heartbeat every few minutes keeps resetting the timer for a chat that ended half an hour ago and the task is never evaluated. `projectName` is the key itself, not the literal "openclaw". A frame with no key falls back to the connection-scoped run — a mis-scoped record beats no record. **A run opens on a span that can RECORD, not on a non-empty span list** (`ApmeCollector.spanCanOpenRun`, kept adjacent to `ingestSpan` because it is a claim about that dispatch): a context is built for every frame including ones that parse to zero spans, so opening it in `apmeEntryFor` manufactured the exact noise the split removes — and the list test that replaced it was the same defect one level down, since an assistant `session.message` always builds a `session_meta` and, with text, a `turn_response`, both of which the collector then discards with no turn open. The four kinds that may open a run are exactly the ones reaching `ingestHook`, which inserts a `steps` row unconditionally. The connection-scoped fallback obeys the same rule and is opened lazily on first use, its id still minted at connect so `hasDirectApmeIngestion` — which gates the bridge's timeline→span conversion — answers unchanged. Measured over the week to 2026-09-09, before the fix: 87 of 113 OpenClaw runs held zero `sample_events` and 82 held zero `steps` as well (25 per-key, 57 connection-scoped), each `_empty`-tagged and held to the 30-minute orphan reaper. Old `openclaw-<uuid>` rows are **not backfilled**; the key was never recorded, so any attribution would be invented.
- **APME identity and cost belong to the turn that produced them.** `turns.model_id` / `turns.provider` are the scorecard source; a task spanning identities is explicitly `mixed`, while `runs.model_id` / `runs.provider` retain the latest value only for legacy summary compatibility and must never drive per-turn ranking. Provider normalization lives in `shared/src/model-provider.ts` and its generated Swift/Kotlin mirrors. A numeric zero is not proof of a free call: every aggregate carries `cost_known`, unknown cost remains SQL/API `NULL`, budget recommendations exclude it, and only priced or known-local zero may rank as free. Assistant response ownership is explicit too: `chat_final` > direct response > `session_message_projection`; all producers update one stable assistant-message sample slot so a later 8K projection can never replace a full final response (nor create a duplicate event).
- **OpenClaw is Gateway-observed AND transcript-observed, and the two carry disjoint halves.** The Gateway WS stream is the live channel (`connect` / `sessions.list` / `chat.send` / `chat.abort` / `exec.approval.*` / — once subscribed — `session.message` / `session.tool`); `bridge/src/openclaw-transcript-timeline.ts` + `openclaw-timeline-feed.ts` read `~/.openclaw/agents/<agent>/sessions/<uuid>.jsonl` and emit **only `tool_exec` rows**, the complement of that stream and never a duplicate of it. **Which producer owns the timeline's tool rows differs per daemon, and that is not an oversight**: Node routes `session.tool` to APME only (its timeline rows come from the transcript feed, so routing both would double-emit), while Swift has no transcript feed — it reaches `~/.openclaw` only through a security-scoped bookmark — so there `session.tool` IS the timeline's source, read from its real `data`-nested shape. Never both at once; one daemon owns the port. Three measured bounds on the feed: only sessions written inside `ACTIVE_WINDOW_MS`; a first sighting emits **nothing** (the opposite of `KiroTimelineFeed` — seeding would inject minutes-old tool calls from finished eval runs); rows attach to the virtual `openclaw-gateway` row rather than minting sessions. **The session key rides every row's `detail`**, or a cron job and a model-eval harness both arrive as the literal "OpenClaw". Gate the feed on `gatewayConnected`, not on the store. Two rules this feed cost to learn: **a producer must be driven by a signal its own subject can move** (`OPENCLAW_FEED_INTERVAL_MS`, not `passiveSessionObserver.onRefreshed` — OpenClaw has no process row, so its turns move nothing that observer sees), and OpenClaw `tool_exec` is carved out of `evictOne` in **both** daemons (it is the only type this feed emits and the first type eviction sheds, so on a full buffer the row evicted itself on insertion; a one-sided carve-out leaves the shared `timeline.json` replay buffers diverged). The `.trajectory.jsonl` is **not** a tool log and **not** an APME enrichment axis — turn boundaries, provider/model and token usage only, all of which now arrive first-hand as `session_meta`. Its one unique field, `gen_ai.system`, has no consumer, so do not cite provider as a reason the transcript is redundant until it is wired to `shared/src/model-provider.ts`. - **A Gateway link that keeps reconnecting reads `connected` at every sample, and the reason it dropped is written only in OpenClaw's own log.** Eleven Gateway restarts in ninety minutes produced eleven `connected` lines, an OpenClaw row flipping to `gateway_not_found` and back on every surface, and nothing that said so — each cycle is indistinguishable from a healthy recovery. `bridge/src/openclaw-gateway-stability.ts` counts disconnects in a ten-minute window (three = unstable), reads the tail of `~/Library/Logs/openclaw/gateway.log` for the sentence OpenClaw prints (`another Gateway owns that state directory` outranks `restart-loop breaker tripped` outranks a routine config restart, whichever is newer), and surfaces it as `gatewayInstability` on `/health` + `/status` plus one `error` timeline row on `openclaw-gateway` — the timeline being the one channel every surface already renders, Android and e-ink included, without a protocol change. - **Kiro observation is passive-first**: users run native `kiro-cli` / `kiro-cli --v3` or Kiro IDE as usual; never add an `agentdeck kiro` managed PTY. The Node daemon correlates processes with Kiro's native stores in `bridge/src/kiro-session.ts` / `passive-observer.ts` — v2 uses macOS app-data `kiro-cli/data.sqlite3` (`conversations_v2`), v3 writes `KIRO_HOME/sessions/<workspace-hash>/<session>/session.json` + `messages.jsonl`. Read SQLite with a read-only/query-only handle and never inspect auth/telemetry tables. `installKiroHooksIfNeeded()` installs AgentDeck's standalone v1 hook file (telemetry-only, never a steering decision), but **installing them buys nothing for CLI chat**: measured 2026-08-17 on kiro-cli 2.18.1, Kiro loads the hooks and then a real `kiro-cli chat` turn fires none of them (marker files proved it; a hand-POSTed hook produced a timeline row normally, so the receiving side was never the problem). That surface belongs to the Kiro IDE agent. **Kiro is therefore transcript-observed on BOTH tiers** — `bridge/src/kiro-transcript-timeline.ts` + `kiro-timeline-feed.ts` (Node), `LocalKiroObserver` + `KiroTimelineFeed` (Swift). The feed admits only the latest turn on first sighting and new rows thereafter, and those bounded rows feed APME too. Two consequences: a Kiro session appears seconds late (polled, `SCAN_INTERVAL_MS`), and it is always reported `idle` — a transcript gains its assistant record only once the reply lands, and claiming `processing` would be inventing a state. ## CLI

The CLI command is `agentdeck` (`bridge/src/cli.ts`).

Full command list: `agentdeck --help`, or [docs/cli.md](docs/cli.md) for the annotated reference.

**Module flags**: `--local` (all device modules off), `--no-adb` (skip ADB reverse). There are no per-session `--no-mdns`/`--no-serial`/`--no-pixoo` flags — hardware modules are daemon-only and session bridges never activate them

**Session sort weight**: session commands (`claude`/`codex`/`opencode`/`monitor`) accept `--weight <n>` (integer in **-9999..9999** — `SESSION_WEIGHT_MIN/MAX` in `shared/src/session-utils.ts`, emitted to Swift/Kotlin via `pnpm generate-session-weight-rules`; default 0) — an explicit deck/tab sort override. `sortSessions` (SSOT `shared/src/session-utils.ts`, hand-mirrored in Swift `DashboardDataRules`, Kotlin `EinkFormatUtils`) orders by **weight ascending first** (negatives → unweighted/0 → positives), then the existing agentType→project→startedAt→id keys; weight also joins the Codex display-fold key so distinct pins never fold together. Comparators are three-way, never subtraction. Threads CLI → `SessionOptions.weight` → `SessionEntry.weight` (registry) → `session_push_register` + `SessionInfo.weight` (wire, sanitized at daemon boundaries) → every surface. Lets a user pin Windows Terminal / iTerm tab order onto the Stream Deck. Leaving all weights at 0 reproduces the pre-weight ordering. See [docs/cli.md → Pinning session order](docs/cli.md#pinning-session-order-with---weight).

**Env-var default args** (`bridge/src/cli.ts` — `applyGlobalEnvArgs`/`weaveAgentCommand`/`resolveAgentCommand`): `AGENTDECK_COMMANDER_ARGS` injects flags into the `agentdeck` (commander) layer — spliced into argv right after the session subcommand, **keyed on `argv[2]`** (`claude`/`codex`/`opencode`/`monitor`; any other command ignores it, even with a session word as a positional value). Env tokens land before typed flags: scalar options are overridden by retyping (last-write); boolean flags have no inverse spelling, so the per-invocation override is **`--no-env-args`**, which disables BOTH layers (the splice pre-parse, the per-agent weave in the action). `AGENTDECK_CLAUDE_ARGS` / `AGENTDECK_CODEX_ARGS` / `AGENTDECK_OPENCODE_ARGS` append to the spawned agent command, weaving onto an existing `-c` (e.g. `AGENTDECK_CLAUDE_ARGS="--remote-control"` + `-c "claude --resume X"` → `claude --resume X --remote-control`). The per-agent append rides the same platform shell path as `-c` (`pty-manager.ts`); the global var is tokenized in pure JS and never touches a shell.

**node-pty macOS helper mode** (`bridge/src/pty-manager.ts`): stable
`node-pty@1.1.0` is published with both Darwin `spawn-helper` prebuilds at mode

## Key Conventions

- **Hook format (CRITICAL)**: Claude Code v2.1+ requires 3-level nesting: `{ matcher: "", hooks: [{ type: "command", command: "..." }] }`. The old flat format silently fails. **Every installer targets the user-global `~/.claude/settings.json`** — that plus the two per-project files are the only paths Claude Code watches, so `~/.claude/settings.local.json` (which `localSettings` resolves against the git root / cwd, not `$HOME`) is a dead file at user scope. `installHooks()` writes it; `migrateHooksIfNeeded()` relocates pre-move installs **and rebuilds any hook whose `curl` is still unbounded** (`hasUnboundedHookCurl`), because the file is co-owned with the macOS app and an older app build can overwrite a fixed command set. Codex uses lifecycle hooks in `~/.codex/config.toml` (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `Interrupt`) via `installCodexHooksIfNeeded()`; `PermissionRequest` and `Interrupt` must be **trusted in Codex after installation** — writing the TOML alone does not activate a new hook (CLI 0.149.0 silently omits `Interrupt`; 0.151.0 supports both, timeout ≤3s). Consolidate same-layer user hooks into official `[[hooks.<Event>]]` arrays; the installers preserve and merge those but reject incompatible regular `[hooks]` tables. Kiro v3 uses AgentDeck-owned `~/.kiro/hooks/agentdeck-lifecycle.json`, structurally identical to `buildKiroHookFile()`, every command fire-and-forget even for `PreToolUse`/`Stop`. Scripts use bounded `curl` and `|| true`. Fire-and-forget events **must** keep `--connect-timeout 0.2 --max-time 0.8` (and `--connect-timeout 0.2` on the `/health` probe): Claude gives all SessionEnd hooks one ~1.5s abort budget, so an unbounded POST to a *restarting* daemon (socket open, no reply) is killed and surfaces as `Hook cancelled`. Only Claude's `PreToolUse` (60s long-poll) and `Stop` (10s) are request-response. Every Claude hook curl also sends `-H "X-AgentDeck-Pid: $PPID"` — the hook shell's parent is the agent process and the payload carries no pid, so this is the only consent-free session→process link (the sandboxed daemon cannot read `~/.claude/sessions/<pid>.json`), and it is what attributes a `claude -p` worker to the session whose Bash launched it. Migration 10 rebuilds hooks that lack it. The Claude snippet is mirrored byte-identically in 3 places — `hooks/src/install.ts` (canonical), `setup/src/setup.ts` (inlined because `@agentdeck/setup` bootstraps the workspace), `apple/.../HookInstaller.swift` — change all three together. The bridge keeps no copy; it imports `migrateHooksIfNeeded` from `@agentdeck/hooks` (its former fork silently downgraded PreToolUse/Stop to fire-and-forget).
- **PERM is a claim that a human is being waited for, and each agent proves it differently — never by prediction where a real signal exists.** Per-agent sources: Claude Code's `Notification` with `notification_type: permission_prompt` (display-only) and the observed-session PreToolUse **hold** (device Allow/Deny, 25 s); Codex's `PermissionRequest` hook, which fires only when Codex is about to ask (display-only — the rollout carries no approval event, so a session blocked on `approval_policy = "on-request"` used to read `processing` until the 10-minute stale-turn fallback) plus `Interrupt` (Ctrl+C closes the turn `interrupted`); OpenCode's `permission.asked` via the observer plugin (answerable `ocperm:` requestId in BOTH daemons — `bridge/src/hook-opencode-sessions.ts`); OpenClaw's `exec.approval.requested` (Gateway-blocked, with expiry/abandon). Kiro and Antigravity have no permission source and never show PERM. **The Claude PreToolUse hold is the one place PERM is predicted, so its predictor is a single generated SSOT**: `shared/src/claude-permission-rules.ts` (→ `pnpm generate-claude-permission-rules`, vitest byte gate + `shared/claude-permission-vectors.json` replayed by both suites). It exists because the two hand copies drifted into the SAME defect — both understood only the legacy `Bash(cmd:*)` spelling while the permission dialog writes `Bash(cmd *)`, so every allowlisted call in an `acceptEdits`/`default` session was held the full 25 s and the deck showed a PERM the terminal never asked. The rules follow the Claude docs: `*` matches any text including spaces; a trailing ` *` also matches the bare command; the legacy `:*` keeps BOTH readings (` *` alias and raw prefix — over-matching only costs a missed hold); compound commands split on `&& || ; | |& &` and EVERY subcommand must be covered; the built-in read-only set (`ls cat git status …`) never prompts; `acceptEdits` also auto-approves `mkdir touch rm rmdir mv cp sed`; wrappers and env assignments are stripped; `auto`/`plan`/`dontAsk`/`bypassPermissions` never hold. **A missed hold costs nothing** (the terminal prompts as before); a false hold costs a lie plus a stall — so every uncertainty resolves to "don't hold".
- **An ESP32 release ships a merged factory image, and its header is verified against the SSOT before it is published.** `scripts/esp32-merge-firmware.mjs` emits `agentdeck-<board>-merged.bin` written at `0x0` on **every** chip, so no consumer branches on chip family — classic boards keep their bootloader at 0x1000 inside the image behind `0xFF` padding the ROM never reads. Loose bootloader/partitions/app assets cannot bring a board up: `boot_app0.bin` (0xe000) lives in the Arduino framework package rather than `.pio/build/` so a copy step never picks it up (stale otadata then boots the previous slot), and the bootloader offset is chip-specific across three values (`esp32` 0x1000, `esp32p4` **0x2000**, everything else 0x0). Because `merge-bin` patches the flash parameters into its own output, the header can only be checked by reading it back **at the bootloader offset** — `image-info` at 0x0 on a classic merged image lands on padding and fails `invalid magic number: 0xff`. `scripts/generate-firmware-manifest.mjs` publishes `manifest.json` with sha256/size computed **from the artifacts** and fails the release when any SSOT board is missing files; the old failure mode was the opposite — a board shipping nothing while every step stayed green. **Release tooling is pinned, and the pin comes from the registry CI installs from, never from a local probe.** esptool is `5.2.0` (v4→v5 renamed `merge_bin`/`--flash_size`); PlatformIO installs its own esptool EDITABLE into `~/.platformio/penv`, so `pip show` answers a version PyPI never published — that is where the pin came from that failed at tag time with `No matching distribution found for esptool==5.1.2`. Same rule, different tool: `npx --yes esbuild` in a pnpm workspace resolves a transitive copy, skips installing, finds no bin and falls through to `esbuild: not found` (pinning the version does not help — the "already installed?" check matches either way), so package scripts fetch through `pnpm dlx <pkg>@<version>`. Reproduce in a fresh clone (`pnpm install --frozen-lockfile`, `pnpm build`, run the script) before touching either pin. (`esp32-v1.0.7`, `ulanzi-v1.0.4` — DEVELOPMENT_LOG.)
- **A refusal to flash has no override, and it is written once for both flashers.** The two entry points — `/flash/` (`tools/web-flasher/`) and `agentdeck esp32 flash <board>` — do not share their esptool-js driving code (Web Serial vs a `serialport` shim), so the piece that must not drift is the **decision**: `esp32PreflightVerdict` (`shared/src/esp32-boards.ts`) refuses a chip-family mismatch or an image declaring more flash than the part reports, with deliberately no `--force` and no "flash anyway" button — the recovery tool for a bricked board is the tool that refused. Five polarity rules live in that one function. **`webFlash` means "offered in the browser", never "may be written"** — it takes a `surface: 'browser' | 'cli'`, because `esp32_c6_147` has no OTA slot and USB is its only update path, so a CLI inheriting the browser's list would leave it unupdatable by anything. The **size check is directional** (declared ≤ detected): TRMNL 7.5" is physically 16MB with an 8MB BSP field, so an equality test fails the one board doing the correct thing. An unreadable flash id **stays unknown** — `detectFlashSize()` silently answers `"4MB"` when it cannot decode the id, so trusting it turns "I could not look" into a confident wrong number that then gates the write. `imageGeometry` (from the release manifest, resolved separately by `--tag`) is compared too, and that one is **strict equality, not directional**: two sources describing the same board that disagree cannot say which is true, and it is the only size check left when the flash id is unreadable. Its cost is a release-ordering constraint (RELEASING.md), not a defect. And **`eraseAll` is stub-only** in esptool-js, so on a `--no-stub` board it was silently dropped after showing an `erase` phase and `MD5 verified`, handing back a board still carrying the previous owner's credentials — both surfaces refuse rather than skip. Three runtime traps: esptool-js's published ESM has extensionless relative imports Node cannot resolve, so Node consumers go through `bridge/src/esptool-js-node.ts` → `esptool-js/bundle.js`; `calculateMD5Hash` receives the buffer **after** esptool-js patches the flash-params header; and **every teardown await here is bounded** — `Transport.disconnect()` spins in `waitForUnlock()` with no deadline and `Transport.write()` has no `try/finally`, and that teardown sits inside the `finally` the CLI waits on before releasing the daemon's serial lease.
- **Writing the bytes is not installing the firmware, and `esptool-js` will not reset the board for you.** Its non-USB-OTG hard reset is, in full, `sleep(100); setRTS(false)` — a RELEASE with no ASSERT, which works only when the preceding step left EN asserted (`--before default-reset` does; a finished `writeFlash` does not). The chip is left parked in the flasher stub, so the firmware never runs and the post-write `device_info` read-back cannot succeed however long it waits. Both flashers reset through `ESP32_POST_WRITE_RESET_SEQUENCE` (`D0|R1|W100|R0`, `shared/src/esp32-boards.ts`) rather than `after('hard_reset')`. **`D0` is load-bearing**: pulsing EN without first driving IO0 high leaves the CH340 boards in download mode, indistinguishable from a board that failed to boot — and the two adapter classes take different strategies inside esptool-js (`UsbJtagSerialReset` for `0x303a/0x1001`, `ClassicReset` otherwise), so a sequence verified on one is not evidence for the other. Two corollaries. **`stub` and `esptoolFlags` describe different tools** — `stub` drives esptool-js (browser + CLI), `esptoolFlags` mirrors `platformio.ini` for esptool.py, the board-matrix gate cross-checks only the latter pair, and they may legitimately disagree as long as the board's note says why. And **connecting is not writing**: `ttgo_t_display` was `webFlash: true` on evidence that it CONNECTS while pinned `--no-stub` made it unwritable by either surface, so `webFlashVerified` must record a completed write, not a handshake. **"Stubless writing is unsolved" is the wrong frame**: of the remaining `stub: false` boards, two inherited that pin from unrelated commits and have never been USB-attached (unknown, not failing), and the third fails at SYNC, which precedes stub loading in both tools. **A tool's guess about which direction failed is not a measurement** — esptool infers "the serial TX path seems to be down" from a failed round trip on a board whose ROM banner arrives over that very UART. Two instrument traps yield confident wrong answers here: node-serialport's `set()` is `{...defaults, ...options}` with `dtr/rts` defaulting to TRUE, so a partial `set({dtr:false})` asserts RTS, holds EN low and "proves" a silent ROM (borrow `NodeWebSerialPort.setSignals`, never call `set()` directly); and `drain()` times out on this adapter whether or not anything is wrong. Also: only esptool.py's `UnixTightReset` reaches `ips_10`'s download mode, so no built-in esptool-js strategy can get there — `CustomReset` can (`D0|R0|D1|R1|D0|W100|D1|R0|W50|D0`), where the PREAMBLE is load-bearing and atomicity is not. (Measured 2026-08-23 — DEVELOPMENT_LOG.)
- **A serial-suspend lease is a FILE, and it expires when it is read.** Every serial open toggles DTR/RTS and resets the board, so the daemon must let go during a flash — and the daemon that stole the port in the recorded failure was the **respawned** one, which an in-process pause cannot span. `POST /esp32/serial/suspend` (behind the normal auth gate — same-machine is already authenticated, so no standing unauthenticated route is added) writes `~/.agentdeck/esp32-flash-lease.json` and calls `releaseESP32SerialPorts()`: refusing to *open* is only half the job, since a port the daemon already holds still blocks the flasher and two readers on one macOS TTY steal each other's bytes rather than failing cleanly. Expiry is enforced in `readLease()`, **never by a timer** — a timer firing late on a sleeping laptop extends the suspension past what was promised, while a read-time check self-heals when the flasher is killed mid-write. **Honest gap**: the sandboxed Swift daemon cannot read `~/.agentdeck`, so the CLI also runs an `lsof` pre-check (allow-list polarity — an unknown holder is foreign and refuses the start) and always verifies after writing. That pre-check has **three answers, not two**: `lsof` exits non-zero both when nothing holds the file AND when it is missing, times out or hits EPERM, so collapsing those into "free" launders "I could not look" into "nobody is holding it" — the same trap `esp32FlashIdIsUsable` avoids on the flash-size axis, inverted to the permissive direction. **Suspending must also invalidate opens already in flight**: `pollForDevices` holds a port in `openingPorts` across `await openPort()` while the release only sees `connections`, so a suspend arriving mid-open reports `released: 0` and the open then resolves into a live connection whose heartbeat writes JSON into the TTY esptool is writing firmware to. A generation counter bumped on release and re-checked after the await discards it — the same rule as `OpenAttemptToken` in the Swift `ESP32Serial`. MD5 proves the bytes landed, not that the board boots them, so the flasher reopens at 115200 for `device_info` — and **`ulanzi_tc001` skips that by name**, because its CH340 TX is broken in hardware and the check would report a good flash as a failure.

- **A network posture is a single resolved fact, and "off" must be derived, not listed.** `AGENTDECK_LOOPBACK_ONLY=1` used to pick the bind address and nothing else, so a loopback-only daemon still advertised `_agentdeck._tcp`, beaconed UDP every 2s, swept the /24 for Pixoo devices and scanned BLE — for a service nobody on that segment could reach. - **The one credential path for a device with no camera and no cable is an operator-held pairing window** (`agentdeck pair`). QR needs a camera, serial needs USB, an e-ink reader has neither — and `adb reverse` dies on reboot, after which a returning reader hammers an endpoint that closes it 4001 with nothing on screen its user can act on. Rules, because this is the only place a token reaches an unauthenticated peer: the window **does not exist until the operator opens it on the host**, so with no window `POST /pair` is refused by the same default-deny branch as any unknown path — never answer it differently when closed, or the endpoint becomes an oracle for "is someone pairing right now". Expiry is enforced **on read, not by a timer** (a timer firing late on a sleeping laptop extends the window past its promise). The guess budget is **global, not per-IP**: an attacker picks their source address, so a per-peer budget is a budget per attempt. The operator-side routes (`/pair/open|status|close`) sit *behind* the normal gate — a remote peer able to open its own window would be granting itself a credential — and `/pair/status` never carries the code. A one-device window closes on success and the operator learns the outcome by polling, so it leaves a bounded **receipt**; without one, a pairing that worked reports as "nothing paired". Rules SSOT `shared/src/pairing-code.ts` (→ `pnpm generate-pairing-code-rules`, vitest drift gate — the emitted Swift carries the whole evaluator because the HTTP status *is* the contract a client's retry policy branches on; Kotlin stays a client mirror). State: `bridge/src/pairing-window.ts` / `apple/.../PairingWindowStore.swift`
- **A code asks the DEVICE to prove something; approval asks the OPERATOR, and only the second one a camera-less reader can complete.** The pairing code is gated on discovery — a client spends it against a daemon it found over mDNS — so where multicast is filtered it is unreachable by exactly the devices it was built for. The daemon already refuses an unauthenticated LAN peer at the WebSocket handshake and logs the address; it just never told anyone (one reader knocked 116 times, then went quiet for three weeks). So the refusal becomes a prompt: `WAITING TO CONNECT` in the app's Pair a Device window, backed by `GET /pair/knocks` + `POST /pair/approve|revoke|dismiss` behind the normal gate. The device does nothing at all, which is also the stronger trust model — a code trusts whoever knows a secret, an approval trusts a peer the operator pointed at, and an attacker cannot approve themselves. **Identity is the device id when the client sends one (`x-agentdeck-device`, a random per-install 128-bit id) and the address only when it does not** — the decision happens before any frame, so `client_register` is too late, and an address is not an identity behind NAT. The address fallback is not optional: every device already in the field predates the header, so refusing them turns an upgrade into a fleet-wide outage; the UI labels which kind a grant is, because only the device-scoped one survives a DHCP lease change. Neither kind is proof — the link is plaintext `ws://` — the win is granularity and revocation, not secrecy. Persisted approvals are **migrated, never dropped**: a decode that merely fails reads as "nobody is approved" and silently un-pairs the whole fleet. **Both daemons implement it**, because either may hold 9120 and which credential paths a device has must not depend on which one won. The Node port is a deliberate near-transliteration — a rule restated in different words is a rule that can drift — with three forced differences: the hooks are **injected** into `WsServer` (`setPairingApprovalHooks`), since a session bridge shares that class and must not hold a second unowned copy of the decision; the approval folds into `isAuthorizedHttpRequest` so `gateHttpRequest` stays the pure truth table its test drives; and the routes answer in the Swift daemon's wire shape field for field (`approved` not `approvals`, `deviceId: ""` not null, epoch-ms), because the Mac app in CLIENT mode calls them against whichever daemon holds the port. `approvedAt` is read by magnitude so either encoding decodes. Client side: a refusal memory carries WHEN each endpoint refused and expires on read after a 30s holdoff (`PairingCredential.UNAUTHORIZED_REDIAL_HOLDOFF_MS`) — approval mints no token, so a permanent ban meant the grant took effect only after an app restart, while an expired refusal buys exactly one redial. State: `apple/.../PairingKnockStore.swift`, `bridge/src/pairing-knocks.ts`; ids ride the `shared/src/pairing-code.ts` SSOT.
- **Discovery names an endpoint; it never carries a credential** (issues #145, #149): since the daemon stopped advertising its pairing token over mDNS TXT, the UDP beacon, and unauthenticated `/health`, every client's "a discovered URL is dialable" assumption became false — a discovered URL is `ws://host:port` with no token. Two rules, one per failure the change caused: **compare bridges by endpoint (host+port), never by full URL string** (a full-string compare against a paired `?token=` URL never matches, so Apple read every reconnect blip as "the daemon moved", dropped `savedUrl`, and redialed unauthenticated), and **an absent credential means "no information", never "clear it"** — a known endpoint inherits the credential it is already paired with, and a tokenless URL must not overwrite a stored token-bearing one (Android persists on the handshake-early CONNECTED edge, which the daemon reaches before closing 4001). Same rule in firmware: the ESP32 adopted the now-empty mDNS token into `g_state.authToken` and wrote it through to NVS, erasing the serial-provisioned credential. SSOT per surface with mirrored cases: `apple/AgentDeck/Net/PairingCredential.swift`, `android/.../net/PairingCredential.kt` (`PairingCredentialTests` / `PairingCredentialTest` share their cases); firmware guards live at the retain site in `esp32/src/main.cpp` and the persist site in `wifi_manager.cpp`
- **One machine has one pairing token, and the daemon currently serving the port is its custodian.** Either daemon can own 9120 and they keep the credential in different files — the sandboxed app cannot read `~/.agentdeck/auth-token`, and Node must not reach into the app's container (TCC hangs). So whoever starts SECOND adopts the incumbent's token off its **loopback** `/health` (`adoptPeerToken` in `bridge/src/auth.ts`; `AuthManager.adoptPeerToken` in Swift at `connectToExternalDaemon` and on each health poll while a client). No new trust — the probe dials `127.0.0.1`, and same-machine is already fully trusted. Without it, whichever daemon won the port decided whether the paired fleet authenticated, and a handover in either direction closed every board 4001 (2026-08-08: the whole WiFi fleet was locked out for hours, silently). The superseded token moves to a bounded **accepted ring** (`auth-token-accepted`, max 4, accepted but never handed out, cleared by `token rotate`), so convergence cannot lock out a device provisioned a moment before it. Two corollaries: **a credential must survive a reboot on every board, not just the ones that persist an endpoint** — `wifiSaveAuthToken`/`wifiLoadAuthToken` are board-agnostic while `wifiSaveProvisionedBridge` stays IPS10/T-Display-Pro, since a board that forgets its token has no way back on; and **the credential re-arm must not share a gate with WiFi provisioning** — `shouldSendWifiProvision` skips any board whose radio is up, which is exactly the board that needs a new token, so `auth_provision` (credential only, no WiFi side effects, ungated by `autoProvision`) is a separate message. Serial is the authoritative credential channel precisely because it still works when authentication is what is broken. Related trap: `onESP32Message`/`setOnMessage` **replace** rather than add, so everything the serial channel drives shares one handler.
- **"Same machine" and "us" are different questions, and only the second one licenses a privilege.** `isLocalConnection` is a pure IP test, so on a shared host every same-machine privilege the daemon lifecycle takes reached every account on the box: `daemon start` copied the incumbent's token into this user's home and asked it to stand down; the daemon's startup **sweeps the port window and shut down every Swift daemon in it** (one user starting a CLI daemon killed every colleague's macOS app); Swift `reclaimCanonicalPortIfNeeded` stood its own hub down for a stranger's daemon and rendered THEIR sessions here; and a port scan registered this user's sessions with whoever answered first. One predicate answers it — `localPeerOwnership()` in `bridge/src/auth.ts`, mirrored as `LocalPeerOwnership` in Swift — with **three values, not two**. `unknown` stays permissive and never silent: refusing on unproven ownership would break the one-machine-one-token convergence, which is how a whole paired fleet stops authenticating. The Swift mirror copies the CONTRACT, not the syscall — `kill(pid, 0)`'s EPERM means "another user" for Node and mostly "the sandbox said no" for the app, so Swift compares uids via `proc_pidinfo` and lands every failure in `unknown`. The decision lives in `negotiateIncumbentDaemon` (`bridge/src/daemon-takeover.ts`) rather than inline in the CLI action, because a truth table over the predicate stays green while a call site forgets to call it. **A refusal belongs where a peer is DISCOVERED, not where it is joined**: `alreadyRunning` is what sends the Swift app into client mode and it is thrown from `DaemonServer.init`, so refusing afterwards in `connectToExternalDaemon` bounces straight back into that initializer once a second, forever. **Not closed, by construction**: a TCP socket carries no peer credentials, so any local process can read `pairingToken` from `/health`; requiring the token on the operator routes defends against nobody while risking the same-user handover. See [docs/ENTERPRISE-ROADMAP.md](docs/ENTERPRISE-ROADMAP.md) §1.2

- **A self-issued restart must be scheduled, never called inline, and must not be the only safety net.** `DaemonService.start()` guards re-entry with `isStarting` and clears it in its Task's `defer`, so any `start()` reached from *inside* that Task (the `alreadyRunning` catch → `connectToExternalDaemon`) is silently swallowed — no log, no retry. The deeper rule is what made it unrecoverable: the same branch also set `port = 0`, and `checkDaemonHealth` starts with `guard currentPort > 0` — so the failed hand-off *also* neutered the watchdog that existed to catch it. **Code that schedules a retry and code that clears state must not share a failure mode**; a guard that can drop a request silently needs a log line at minimum. - **"The OS killed this" is not "this failed", and a dependency probe cannot see an architecture.** Both rules govern the daemon-managed Python BLE workers (`bridge/src/ble-sync-spawn.ts`, `python-ble-runtime.ts`), and each hid the other for two days (2026-08-20: 77 crash reports). A macOS **TCC Bluetooth grant for an unbundled binary is pinned to an exact path**, so a `brew upgrade` or a Claude Code auto-update silently revokes it — and an interpreter with no bundle cannot prompt, it is killed outright with SIGABRT. A backoff respawn re-rolls that kill every period forever, which is amplification, not recovery, so `createSigabrtCircuitBreaker` halts after 3 consecutive SIGABRT exits and names the fix, while any clean exit (a powered-off panel's `device not found`) resets the streak. Separately, a translated interpreter imports `bleak`/`PIL` perfectly, so `dependencyProbe` accepts exactly the Rosetta venv that must be rebuilt: architecture is read from the **Mach-O header** (thin and fat), an x86_64-only python on an arm64 Mac is refused, `ensureBleRuntime` **removes** such a venv before recreating it (re-`venv` keeps wrong-arch native wheels in site-packages), and `/opt/homebrew/bin/python3` is probed ahead of PATH `python3` because daemon-spawned shells resolve `/usr/local` first. Unknown formats (a shell wrapper, ELF, a truncated file) make **no claim** — refuse only when an x86_64 slice is present and an arm64 one is not. Diagnostic rule this came from: a `.ips` crash report is JSON from its second line, and `termination.details` states the reason in a sentence — read it before inferring anything from the stack.

- **A running daemon carries the identity of the build it started with, because `dist/cli.js` is overwritten in place.** On a source checkout `agentdeck` is a shim onto `bridge/dist/cli.js`, so a daemon started before a rebuild keeps executing bytes that no longer exist on disk while reporting the same pid, port and package version as one started after it — `daemon start` answered "already running" and exited 0 about code the user had just replaced (2026-08-24: a daemon from 04:19 still held 9120 at 19:20). `/health.build` is a 12-char **content** digest of `bridge/dist` + `shared/dist` + `hooks/dist` (`bridge/src/daemon-build-identity.ts`), and three properties are load-bearing. It is content, not mtime: `tsc` rewrites every output on every run, so an mtime stamp would restart a healthy daemon for a rebuild that changed nothing. The daemon **captures it once at startup and never recomputes** — a daemon that recomputed would report the newest build on disk the moment someone rebuilt, i.e. exactly the state the field exists to detect. And eviction requires **both** digests to be known and differ: a daemon predating the field sends none, and evicting on no information turns every start into a restart, autostart units included (`--no-upgrade` opts out; the ownership gate still outranks freshness). The CLI keeps the build itself current — `daemon start` / `daemon restart` on a checkout build stale packages and then **re-exec**, because a process that loaded the old `cli.js` and then dynamically imports the new `daemon-server.js` is a mixture nobody chose. Its staleness pre-filter is trusted **one way only**: "no source is newer than its build" safely skips the compiler, while the other direction over-reports (a composite project like `shared` rewrites nothing when a rebase or `touch` moves an mtime), so the real decision is the build digest before vs after. Never build on the autostart path (no terminal ⇒ warn only): a failed build there becomes a `KeepAlive` respawn loop. See [docs/daemon.md § 어떤 빌드가 포트를 잡고 있는가](docs/daemon.md)
- **A restart is verified by the identity of the daemon that came up, never by the pid this command forked.** The daemon ends `/shutdown` by SIGKILLing itself (`exitProcessNow`), and a self-signalled death is not a successful exit — so launchd's `KeepAlive{SuccessfulExit:false}`, systemd's `Restart=on-failure` and the Scheduled Task's RestartOnFailure all respawn it within a few seconds. On any machine that ran `daemon install` the respawn routinely beats `daemon restart`'s own child to the port; the child then hits `daemon start`'s incumbent guard, exits 0, and a wait keyed on its pid can only time out. That printed `restart FAILED — no daemon with PID <n> is answering` over a daemon that was serving the new build the whole time (2026-09-08, twice; reproduced live 2026-09-09 as PID 27022 winning against child 27028), and the user's natural retry then stops a healthy daemon. `waitForRestartedDaemon` therefore asks three questions in order: is a daemon answering on a candidate port, is its pid **not** the pid we stopped (the old test's real purpose — a port probe alone is satisfied by the daemon the stop failed to remove), and is it serving the build on this disk. The build check exists because "a daemon restarted" and "your code is live" are different claims and only a supervisor can split them — the unit launches whatever `agentdeck` resolves to at ITS path, which may be another install — so a known mismatch fails loudly while an **unknown** build on either side is not a mismatch at all. Two consequences of the respawn that are not defects of the verdict: a `daemon stop` on a supervised machine does not stay stopped, and a restart whose own child wins the port leaves the daemon **unsupervised** until the next login, because the unit's job has exited cleanly by then.
- **An ObjC exception is not a Swift error, and `try?` does not catch it.** `JSONSerialization.data(withJSONObject:)` *raises* `NSInvalidArgumentException` for anything that is not a valid top-level JSON container — so `try? JSONSerialization.data(withJSONObject: someAny)` reads as safe and is a `terminate`. A trajectory event whose `input` was a bare String aborted the whole app from a background APME eval task, taking the daemon and every device connection with it (2026-08-06). Any Foundation API documented to *raise* needs a **precondition check**, not a `try?`: `guard JSONSerialization.isValidJSONObject(x)` first (it validates recursively, so it also covers a `[String: Any]` whose leaves are not JSON). Applies wherever untyped `Any`/`[String: Any]` from hooks, gateway payloads or the timeline is serialized — `ApmeScorers`, `ApmeCollector`, `[String: Any].jsonData`; `compactDebugValue` in `DaemonServer.swift` is the pattern to copy
- **External peer async I/O**: 모든 RPC/WS/HTTP `await` 에 timeout 강제 — peer silence (silent drop, dead socket, network glitch) 를 first-class signal 로 처리해야 함 (synthetic error code emit + UI status emit + retry/fallback escalation). race condition 가드는 secondary; timeout 이 먼저. Reference 구현: `apple/AgentDeck/Daemon/Gateway/OpenClawAdapter.swift` 의 `connectRPCResponseTimeoutNanoseconds` + `completeRPCTimeout` + `handleConnectTimeout` 패턴

- **A Claude `SubagentStop` is not always a dispatched worker.** Claude 2.1.261's internal fork queries (prompt suggestions / agent summaries) enter the query loop without `SubagentStart` and still emit `SubagentStop` with an explicitly empty `agent_type`. Live captures produced `wait for it…` and `<no suggestion>` as fake worker completions. Both daemons consume these empty-type stops when no active child matches, without a timeline row, census increment or APME event. Typed orphan stops, absent legacy types and known children still count; never synthesize starts to balance a stop count. `TaskCompleted` is also a one-sided task event, so aggregate APME started/completed counts are not a hook-loss ratio. Ordinary Agent calls were verified marker → HTTP → tracker → APME with matching IDs. Named/background Agent calls can instead create a separate session in 2.1.261 and use `SessionStart`/`Stop`; do not invent a parent link.
- **A folded Codex project row must expose the member waiting on the user.** General activity ranking prefers processing, but that rule inside the fold hid a live `PermissionRequest` behind another processing task in the same project. `foldCodexSessionsForDisplay` and both Swift fold consumers rank awaiting members first and keep that member's ID, question, controls and tool together. A sibling's tool must never overwrite the waiting member's tool.

- **Claude quota authorization is distinct from session connectivity.** The Node daemon alone enables bounded recovery (`claude-usage-recovery.ts`) when a credential expires or the usage endpoint rejects it with 401. Claude Code owns refresh-token rotation and its locks; AgentDeck asks the user's CLI for one tool-free, customization-free Haiku reply (small quota cost, 25s timeout), then re-reads credentials before retrying usage. Never add this subprocess to Swift. A persisted recovery cooldown survives daemon restart (30 min, then 6 h after the third attempt); `AGENTDECK_CLAUDE_USAGE_RECOVERY=0` disables it. `tokenStatus` must explicitly emit `unknown` as well as valid/expired/missing so a previous auth error can be retracted. The app preserves this field and shows the quota failure reason independently of working session hooks. API `Retry-After` is scheduling metadata, never a replacement for the cache's successful `fetchedAt` stamp.

## Design System

**Local collaboration trial:** macOS Dashboard has an opt-in `dashboardCollaborationEnabled` lens over the existing Habitat/roster/control surfaces. It reads the selected session's canonical task sample, not inferred project membership; live child census is a separate axis from task-scoped start/stop observations. IPS10 uses stable work cards and a bounded optional census projection from both daemons (other board frames unchanged). No new steering or dependency inference. Scope, fallback and local recovery: [experiments/collaboration/README.md](experiments/collaboration/README.md).

Aquarium-tide design system. Spec: [DESIGN.md](DESIGN.md). Source of truth for color/type/spacing tokens: [design/tokens.css](design/tokens.css). **Resource map (which directory is SSOT for what, and which gate stops drift): [design/RESOURCES.md](design/RESOURCES.md)** — bound into the Pages viewer via `catalog.json`; update it in the same commit when a design-resource location or gate changes. Visual reference: [docs/design/Design System.html](docs/design/Design%20System.html). Coverage matrix + lint rules: [docs/design/Design Audit.html](docs/design/Design%20Audit.html).

`agentdeck-design-system/` is the integration and handover layer, and its scope is the **whole designed surface** — visual language, system architecture, hardware and surface specs, product policy, and validation evidence — not just tokens. `catalog.json` binds those canonical Markdown sources to the GitHub Pages viewer (`pnpm design-system:check` prints the current document, token and asset counts — read them there rather than from a number in this file), [`agentdeck-design-system/docs/handover.md`](agentdeck-design-system/docs/handover.md) defines ownership and evidence levels, and `locales/{ko,ja}/` contains reader translations. English is always canonical. Every catalog document has YAML frontmatter; translations must match the canonical `source_revision`. Validate with `pnpm design-system:check`, build with `pnpm design-system:build`, and never edit generated `dist/design-system/` content.

**Coverage gate — this is what stops doc fragmentation.** `catalog.json` carries a `coverage` block (`scan` directories + `exclusions` map). Every `docs/*.md` must be either cataloged or excluded *with a stated reason*, and `pnpm design-system:check` fails otherwise. **Adding a doc to `docs/` therefore requires a decision in the same commit**: bind it (frontmatter + catalog entry) or write down why it does not belong. Excluding is legitimate — runbooks, credential setup, exploratory studies, and untranslated rationale essays are excluded today. The Asset library is likewise indexed from the real files (brand marks, generated masks, creatures, icons, brand type, product marks, hardware photography, reference surfaces); images ≤1 MiB ship inline, larger ones become pointer cards.

**Markdown gate:** `pnpm docs:check` validates tracked and newly added Markdown local links and anchors, rejects machine-local Markdown links, and requires exactly one H1 in `README.md` and each `docs/**/*.md` file. `.github/workflows/design-system.yml` runs the same checker directly with Node.

**Token bindings** (all mirror `design/tokens.css`; CSS stays canonical — update every mirror in the same commit when CSS tokens change). Seven mirrors are gated: the four language bindings below plus three non-binding copies (`apme-dashboard` HTML, Stream Deck PI `design-tokens.css`, and the Build Health generator `scripts/generate-html-report.py`) that `verify-tokens-sync.py` also checks — the verifier's own footer prints the count, so read it there rather than trusting this sentence:
- Browser JS — `design/tokens.js` (IIFE that exposes `window.DT.{Tide,Ink,Kelp,Coral,Amber,Status,UI,Brand}`). Used by `docs/design/data.js` and Design System.html mockups
- TS — `shared/src/design-tokens.ts` (re-exported via `@agentdeck/shared`). Use for plugin renderers, bridge, hooks
- Swift — `apple/AgentDeck/UI/Common/DesignTokens.swift` (`DesignTokens.Tide.s50` etc.). Existing `StateColors` stays as legacy
- Kotlin — `android/app/src/main/kotlin/dev/agentdeck/ui/theme/DesignTokens.kt` (`DesignTokens.Tide.s50` etc.). Existing `AgentDeckColors` stays as legacy
- Sync verification: `python3 design/verify-tokens-sync.py` — diffs all seven mirrors against tokens.css and exits non-zero on drift

**Rules** (DESIGN.md §10 — enforced by `bash design/lint.sh`):
1. **No raw hex.** Use tokens (`var(--ink-900)`, `DesignTokens.Ink.s900`, etc.). Tokens are the only place hex literals live
2. **No `#fff` / `#000`.** Whites lean toward `--tide-50` sand, blacks toward `--ink-900` aquarium green
3. **Two faces only.** IBM Plex Sans (+ KR/JP) and JetBrains Mono. Never Inter / Roboto / Arial / Fraunces
4. **Status colors are semantic.** `--status-idle` / `--status-processing` / `--status-awaiting` / `--status-error`. Only **amber awaiting** animates; never animate kelp or coral
5. **Marketing vs product UI palette split.** Marketing surfaces (landing, docs, print) use the warm tokens. Product UI (menubar / e-ink / hardware / TTY) may also use the brighter `--ui-*` set. Marketing must NEVER touch `--ui-*`
6. **Brand marks are upstream — do not redraw.** `design/brand/{claudecode,codex,openclaw,opencode,antigravity,kiro}.svg` are the canonical agent marks. Brand colors (#C07058 / #6166E0 / #FF4D4D / #3a3a3a / #5F6368 / #7C3AED) are the only saturated reds/blues allowed, and each one is a `--brand-*` token in `design/tokens.css` — a mark whose colour is quoted in this rule but absent from that file is the gap that shipped Kiro and Antigravity to every renderer while the design-system page could not draw either
7. **Real assets > drawn ones.** Hardware shots and brand marks come from `assets/` and `design/brand/`. Never illustrate hardware with hand-drawn SVG; ship the diagonal-hatch placeholder pattern (`.ad-hatch` / `.ad-placeholder`) when real assets aren't ready

**Dot-matrix brand assets:** Pixoo64/iDotMatrix use the generated 24×24 alpha masks, Timebox Mini uses generated 9×9 masks, and TC001 uses generated 8×8 masks emitted by `pnpm generate-micro-glyphs` from `design/brand/*.svg`. Node, Swift, and ESP32 consumers may add device-specific color, shading, pulse, rails, and particles, but must not replace those masks with hand-drawn agent geometry. Regression tests preserve each official mark's defining negative space. Pixoo64's 64×64 usage HUD identifies Claude/Codex rows with 9×7 silhouettes sampled from those same official masks and gives both the same provider-row grammar: primary/5h and secondary/7d percentage fills plus reset countdowns; do not reintroduce letter keys or provider-specific standalone rails there.

**Migration**: existing UI uses pre-design-system palettes (`StateColors.Hex.*`, `AgentDeckColors.*`). New code reaches for `DesignTokens.*`; migration is incremental, not a sweep. Run `bash design/lint.sh` for the violation count baseline

## App Store build invariants

The macOS app ships through the App Store and must stay **self-contained** under App Review Guidelines 2.5.2 (no bundled interpreters) and 4.2.3 (no routing users to outside installs). The guardrails below are enforced in code, CI, and docs — preserve them on every change.

- **`AGENTDECK_APP_STORE` compile flag** is set on the macOS target in `apple/project.yml`. macOS == App Store; the legacy non-App-Store macOS GUI build is no longer maintained. The flag is retained as a defense-in-depth gate, but the macOS source tree itself contains no `Process()`, `/bin/sh`, `osascript`, `.command` script writer, or external-CLI probe (`security`, `sqlite3`, `adb`, `openclaw`, `whisper-cli`) — those code paths are gone. Do not reintroduce subprocess paths under any guard; route new functionality through entitlement-backed APIs or surface it as a "requires desktop bridge" capability gated on `DaemonService.isUsingExternalDaemon`.
- **No companion-install prompts.** App-Store-reachable UI (Setup card, Settings, menubar, alerts) must not tell the user to install, register, or launch a companion binary. Setup card copy is identical regardless of whether an `agentdeck` CLI exists on disk — differentiating based on external state is an App Review 4.2.3 red flag. See [apple/AgentDeck/UI/Monitor/SetupNeededCard.swift](apple/AgentDeck/UI/Monitor/SetupNeededCard.swift) for the canonical copy.
- **No session-launch UI in the App Store build.** The `Launch Session` entry point is gone from the menubar, dashboard empty-state and AgentDeckApp Window scenes — App Store builds never spawn Terminal windows, `.command` files, AppleScript prompts, or child processes. Sessions appear automatically once the user starts Claude Code / Codex / OpenCode in their own workspace and the AgentDeck hooks pick them up. `apple/AgentDeck/Daemon/Core/SessionLauncher.swift::showAppStoreLaunchInfo` remains as defense-in-depth (NSAlert-only path, no callers in shipped UI).
- **CI verifier**: `apple/scripts/verify-appstore-archive.sh` runs after the macOS archive step and fails the build if the shipped `.app` Mach-O contains any forbidden subprocess path string or any bundled executable besides the signed AgentDeck binary itself. Run it locally before releasing: `bash apple/scripts/verify-appstore-archive.sh $PATH_TO_APP`.
- **Feature matrix is canonical**: [docs/appstore-feature-matrix.md](docs/appstore-feature-matrix.md) is the one place that records which features are in the App Store build vs. only the terminal-managed daemon. New features land in the table before any implementation touches the App Store target.
- **Progressive enhancement on `isUsingExternalDaemon`**: capabilities that depend on the separately-installed Node.js daemon (Claude subscription quota gauges, ADB-tier device previews, Android/TC001 topology rows) render only when `DaemonService.isUsingExternalDaemon` is true. When false, the relevant UI sections are hidden — never replaced with a "sandbox limitation" notice — so the standalone app reads as feature-complete instead of broken.
- **A release step marked "manual" is an interactive portal, not a user-only task, and CI green is not "released."** Store submission has no API, so RELEASING.md calls it manual — that describes the missing API, not a missing capability: portals take a signed-in browser and browser automation is available here (the tools are often **deferred**, so `ToolSearch` for `mcp__claude-in-chrome__*` before concluding they are absent). Read portal state freely (Play review status, ASC builds and submission readiness, Maker/Ulanzi status); ask before pressing anything that changes external state. And keep the five states apart — CI succeeded / artifact exists / uploaded / submitted / live — reporting one you did not measure is how a build sitting in a portal gets called a release (2026-08-09). See [RELEASING.md § A release has five states](RELEASING.md)
- **A GitHub Release body is rendered from `CHANGELOG.md`, never hand-written into a workflow.** All six release workflows used to hardcode a static `body:` — the same install blurb every version — so `npm-v1.0.21` published 18 lines that never said what changed, and the round that shipped Kiro observation across five channels announced it nowhere a user could read. `scripts/release-notes.mjs` resolves a delivery tag to its CHANGELOG section and appends the channel's install text from `.github/release-notes/<channel>.md` (ESP32 passes its artifact-rendered board table via `--template`, since a table built from what actually compiled cannot be a checked-in file). Heading format is `## <YYYY-MM-DD> — <Channel> <version>`, and one heading names every channel when a round is cut across several. **There is deliberately no bare-version fallback**: the channels stopped sharing a patch number, so `## 1.0.7` was npm's on 2026-08-06 while Apple reached 1.0.7 on 2026-08-18 with unrelated content, and publishing one channel's notes under another's tag is worse than publishing none. `verify-release-version.mjs` fails on a missing entry as the **first** step of every release workflow, before anything is built, published or tagged — the procedure text alone had been in RELEASING.md the whole time and was skipped without consequence. Backfilling history is out of scope by rule: versions that shipped without notes are listed as *Known gaps* rather than reconstructed, because a plausible sentence derived from a commit log is a release note nobody measured. Gate: `scripts/__tests__/release-notes.test.ts`
- **Review notes**: [apple/APP_REVIEW_NOTES.md](apple/APP_REVIEW_NOTES.md) is the text that ships to the reviewer — its claims ("does not spawn any subprocess", "no home-relative-path entitlement", "local WebSocket only accepts same-machine + paired iOS companion") must stay factually correct. Update both the code and this doc when touching anything in that surface area.
