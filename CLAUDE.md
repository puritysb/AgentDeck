# AgentDeck

Stream Deck+ controller for AI coding agents — a bidirectional local control system.

## Monorepo

- **bridge/** — Node.js server: Daemon hub + Session Bridge (PTY, hook HTTP, state machine). `src/apme/` — APME eval module (SQLite store, collector, deterministic+LLM judge runner, category-aware rubrics, turn-level mid-session eval, Pareto recommender, daemon HTTP API). **Canonical `SessionSample`** (`shared/src/sample.ts` + `sample_events` table) is the SSOT: a bounded unit with a typed trajectory (user/assistant/model/tool/subagent/state) that both the timeline and the eval derive from. Per-unit cost via `shared/src/pricing.ts` (override-loadable), Pareto-frontier recommender (`apme/pareto.ts`) surfaced via the dashboard **Recommend** tab, trajectory scorers (`apme/scorers/`). **Eval results are off the device timeline** (timeline = activity log only) — they flow via the `apme_eval` WS event + scorecard/SQLite. **Tasks segment on explicit boundaries** (`/task close`, `/clear`), `session_end`, or a **15-minute generic idle gap** armed at turn close (`AGENT_IDLE_GAP_MS`, measured: 96% of real claude inter-turn gaps are shorter, and before it existed 100% of codex tasks reached the judge only via the 30-min orphan reaper — hours late or never); TodoWrite-all-completed is a non-segmenting soft hint. **The collector's state is re-adopted from the store at daemon start** (`rehydrateOpenRuns`, daemon-only): the idle-gap timer and every session→run/task/turn edge are in-memory, so without it a restart stranded every mid-session run for the 2-hour reaper — measured 5.5 days after the idle gap shipped, 60 of the 68 tasks the reaper closed straddled a restart, and the new boundary had closed none of them. The reaper itself now stamps what it found: a task whose turns all closed is `idle_gap` (reached late), only one holding an open turn is `orphaned`, and `stop-health` reports the reaped turns in their own `Reaped` column rather than folding them into session ends (which read a 29% codex loss as 11%). **A verdict about the agent's work needs the agent's work**: `task-gradeability.ts` is the Node SSOT declining `no_reply` / `aborted_only` / `trivial` tasks and stamping the reason on the row; `generate-apme-display-rules` emits `TaskGradeabilityRules.generated.swift`, and both suites replay `shared/task-gradeability-vectors.json` so the App Store daemon makes the same decision — before this gate, 69 of a week's 182 judged tasks held no reply and a usage-limit abort scored 0% on its own notice. **A Stop hook's reply source is chosen per agent** (`hook-response-source.ts`): inline text first, else each agent's OWN reader — a Codex hook carries `transcript_path` too (its rollout), and handing it to the Claude reader left 125 of 128 codex turns replyless; the same payload's `model` now stamps the TURN (`turns.model_id`, the scorecard source, was NULL on every hook-observed turn). The task judge backlog is drained by the daemon tick (one only when no task judge is in flight, judge `ready` only, 30-day window, declined rows excluded) — `listTasksNeedingSummary` had no caller and 1,060 closed tasks sat unjudged. **Adoption at startup is provisional** — a rehydrated run counts as live to the reaper only once its session sends a hook (`rehydratedSessions` / `isLiveRun` / `releaseRun`), because a session that ended while the daemon was down has no Stop coming and no idle timer (those arm on turn close): two such runs sat open 17 hours. **A turn open at startup or at the next prompt is closed by the agent's OWN record, at the record's time** — Codex's rollout (`codexCompletionProbe`) and Claude's transcript (`claudeTurnCompletionSince`, located under `~/.claude/projects` by session id): `end_turn` → `synthetic_stop` with the reply, `task_complete.error` / `stop_sequence` → `aborted`, a mid-turn tail claims nothing. Measured over a week, 16 of 23 codex `next_prompt` turns held a completed reply in the rollout and 2 were API failures Codex fires no Stop for — only 5 were dropped hooks. **A reply arriving after `closeRun` still lands** (`latestClosedTurnIdForSession`, 60 s window): one-turn workers send SessionEnd 80–130 ms after Stop, ahead of the deferred transcript re-read. **The task judge backlog drain feeds ONE task per tick and only when nothing is in flight**, a park after two failures expires after 30 min, and an `unavailable` backend is re-probed every 5 min — a local model busy with someone else's inference at startup used to switch the drain off for the life of the process, and three concurrent requests per tick against a serial server parked all 289 pending tasks with no log line. **The task it feeds is chosen park-aware** (`pickBacklogTasks` over a 200-row window, not the query's first row): the query orders `ended_at DESC` and `enqueueTask` drops a parked task SILENTLY, so a task whose judge call fails every attempt owns that head and every tick spends its one slot on it — measured 2026-09-06, 156 closed tasks from 2026-08-07..23 unjudged for two weeks while the day's own tasks (83 of 95) were judged normally by the live close path, the count going 217 → 156 while the head was still judgeable and then flat. A window in which every candidate is parked says so in the log, once per park period, because silence is what let that run for two weeks. **A task's display title is its first user prompt, and the judge summary outranks it once it exists** (`deriveTaskTitle` SSOT `shared/src/task-title.ts`; the Swift copy is GENERATED — `pnpm generate-apme-display-rules` → `TaskTitleRules.generated.swift` — with behavior pinned by the shared vector file `shared/task-title-vectors.json` both suites replay: a markup-first prompt derives null, a slash PATH is not a slash command, all index math is code points): the intent title fills the one-line slot until judged, the outcome sentence wins after, and the `Task N` fallback stays the display SSOT's "meaningless" shape. The `/apme` default tab is a task-first **Work board** (lifecycle buckets + attention-first sort; bucket SQL is single-source in the store so filter, row flag and badge cannot disagree — attention is 7-day windowed because the unwindowed bucket measured 93% of all history). Every row exposes its project + native session as a contextual drill-down; the exact `session_id` scope gathers that session's tasks and changes ordering to recency so its work reads as one chronology, with the same entry point in Run/Task detail. **A turn closes at its Stop, and records WHICH signal closed it** (`turns.end_source`: `stop` / `synthetic_stop` / `next_prompt` / `interrupted` / `session_end` / `run_close` / `clear`) — closing at the next prompt instead put the user's typing time inside the turn's duration, and without the attribution a dropped Stop hook is byte-identical to a normal close, so its rate was unmeasurable. `agentdeck apme stop-health` reads it; pre-column rows are never backfilled. **A user cancel is not a lost hook**: ESC emits no hook at all, so no Stop was ever due — `interrupted` is its own bucket, outranks `synthetic` when both are set (a cancel can only ever arrive AS a synthetic Stop), and stays out of the loss ratio. It is detected two ways because one is not enough: the watchdog sees the marker while it is still the transcript tail, and the next-prompt close runs `readInterruptSince` for the commoner cancel-then-retype shape that buries it. The marker predicate is single-source in `bridge/src/claude-interrupt-marker.ts` (observer + watchdog + collector) and reads **text blocks only** — a `tool_result` quoting the same sentence is routine and would otherwise invent a cancel. Missed-Stop recovery is **two wirings, not one** — `claude-turn-watchdog.ts` per PTY bridge, `observed-turn-watchdogs.ts` per observed session inside the daemon (1.0.20 shipped only the first, which covered none of the real traffic). Recovery **re-enters the real Stop path** (the daemon self-POSTs its own `/hooks/Stop`) rather than reimplementing it, and a synthetic Stop must never drain a queue whose delivery needs a listener (`takeDirectiveForStop`). **Task rows render one-per-task**: `task_end` is data-only (spinner stop, judge upsert, reaper) and never a standalone row — the `task_start` header folds the closure in (SSOT `shared/src/timeline-task-display.ts`, mirrored Swift/Kotlin/TUI; glance surfaces exclude task rows entirely). Env `AGENTDECK_TIMELINE_PROJECTION=1` (default off) flips the device timeline to the sample projection (suppresses adapters' direct chat/tool rows). **The default judge chain is `mlx → foundationModels`, and the FM leg is a FLOOR, not a peer**: on-device FM measured 0.580 on the judge-fidelity rubric (vs 0.86–1.00 for the MLX tier) and its window is a hard, measured 4,096 tokens that refuses 4.2% of real `task_rollup` judge prompts — but flipping the default without keeping FM as the fallback would have removed evaluation outright from every machine with no MLX server. The fallback rides the DEFAULT only (`fallbackToFoundationModels`): a backend the user NAMED, offline, still skips visibly. Two consequences: anything that must decide before the call — the REVIEW tier and its diff budget — resolves the leg that will actually answer first (`resolveJudgeBackend` / `ReviewRunner.resolveBackend`), because the legs' windows differ 4×; and a prompt budget for the on-device leg is sized in MEASURED tokens, never characters (the `basic` tier's own caps used to build a 5,161-token prompt for a 4,096-token window, since the activity block is the user's own Korean prompts at ~1.15 chars/token). **Judge transport completion is part of verdict validity, but the rule is about the BODY, not the flag**: both daemons reject an empty content, a `choices` that is not a non-empty array, and a `finish_reason=length`, full stop. **An exemption for "its object closed, so the verdict finished" was tried and removed** (#286 item 3, which lists "keep rejecting and alert on the rate" among its own options): brace topology cannot tell whether the model finished, so the exemption produced a defect in three consecutive adversarial review rounds — first admitting a reasoning model's `<think>` scratchpad when the real verdict was the part that got cut (exactly ONE span closes, so nothing looks ambiguous), then refusing complete verdicts whose trailing prose held an unmatched brace. It also had no measured beneficiary: the one cut mode observed on this fleet is a repetition loop INSIDE the `summary` string, where depth never returns to zero, so the exemption and the plain rule agree on every real body seen. The rate is visible — the park log names this failure, and a re-attempt clears it two times in three (measured over the 24 parked tasks, 2026-09-06) — a closed object IS the finished verdict (what the model wrote after the closing brace is not part of it) and a body cut mid-object cannot parse anyway, so `parseJudgeJson` already refuses exactly the incomplete case; rejecting the complete one silently rerouted the default chain to the FM floor. Measured: gemma-4-26b enters a repetition loop inside `summary` on some prompts and runs to the 800-token cap without closing — that is the body the rule is for. **Both daemons extract that object the same way** (first BALANCED `{…}`, Node keeping the old greedy span as a second candidate because a key that lost its opening quote desyncs any string-aware scanner and is what `repairJudgeJson` exists for): Node's greedy-only match spanned into trailing prose and called a verdict cut that Swift scored. **Which of several objects is the verdict is decided by `overall`, never by position** (`parseJudgeObject` / `ApmeRunner.selectVerdictObject`), and two spans carrying it are AMBIGUOUS and resolve to null: scanning balanced blocks makes more spans parseable, so "the first that parses" scored a local reasoning model's `<think>` scratchpad instead of its answer — a wrong score in `evals` is strictly worse than a loud skip. The vectors carry a `verdict` field (defaulting to `accepted`) separating "the transport returned it" from "the parser produced a verdict from it", because that is the only way to pin a body the gate must pass and the parser must refuse. Two known parser asymmetries the vectors CANNOT express, both pre-dating this and both in the same direction (Node scores, Swift skips): Node keeps a greedy first-`{`-to-last-`}` span as a second candidate and `repairJudgeJson` for the lost-opening-quote defect Gemma 4 emits, and Swift has neither — porting the repair would be a new hand mirror, so it is recorded here rather than duplicated. The **Anthropic `api` leg** carries the same rule under its own spelling (`stop_reason` `max_tokens` / `refusal`), sends the same `max_tokens: 8192`, resolves the same default model, and sends no `temperature` — sampling parameters are rejected outright on Opus 4.7+, so that leg 400'd for every current model and reported it as `nil`, i.e. the same shape as "no API key". Shared `apme-judge-response-vectors.json` pins the chat-completions gate and `apme-judge-api-response-vectors.json` the Anthropic one — the api leg is reached only through the SDK, so without its own vector file reverting either rule left both suites green. Serving completion rates are not judge-accuracy evidence. See [docs/apme.md](docs/apme.md)

Five actions: `session-slot` (keypad) + four SD+ encoders — E1 Volume (`utility-dial`), E2 Claude Usage (`option-dial`), E3 Codex Usage (`iterm-dial`), E4 Launcher (`launcher`). - **plugin-ulanzi/** — Ulanzi Studio plugin for the D200H Deck Dock and D200X LCD keys (official UlanziDeckPlugin-SDK). One dynamic keypad action + session-centric two-level UX, shares the `@agentdeck/shared` `buildSessionDeck` layout engine. D200X encoders are a separate, not-yet-shipped action/UX; keypad support must not imply encoder support. Connects to the daemon over WS like the SD plugin and is the **sole** Ulanzi deck driver — Node direct-HID was deleted (2026-07-08), Swift direct-HID and the legacy `zkswe/` research tree were deleted (2026-07-14). The Studio handshake does not identify D200H versus D200X, so the daemon preserves the historical `d200h` health wire identity and reports connectivity from `ulanzi-plugin` WS presence. **The Marketplace bundle ships NO native binary, and that is enforced at package time, not intended.** Through 1.0.4 the SVG rasterizer was `@resvg/resvg-js`, which needs one `.node` per architecture: a single Marketplace bundle must run everywhere, so it carried five — 18.5 MB of a 20 MB plugin, four of them unusable on any given machine — and macOS raised "Apple could not verify" on `resvgjs.darwin-arm64.node` (Ulanzi Studio team, 2026-08-25). Signing was never the fix: a loose native module inside a folder Studio downloads and unpacks has no owner who can sign it for the process that loads it — we do not build Studio, and Studio does not build our dependency. `@resvg/resvg-wasm` is the same resvg version and the same Rust core (**pin the two in lockstep** — the identity is the whole argument), ships as one file identical on every OS/CPU, and renders **byte-identically**: measured over 34 tiles spanning both raster sizes, every session state and `feGaussianBlur`, same RGBA and same PNG hash. Three consequences. `initWasm` is async while every tile render is sync, so `app.ts` awaits `initRaster()` **before the Studio bridge opens**, i.e. before any `onAdd` can ask for a key image. Fonts became load-bearing: the WASM build has no filesystem and therefore no `loadSystemFonts` fallback, so a bundle missing them renders every tile textless rather than merely differently. And the packaging verify walks the **tree** for `.node`/`.dylib`/`.so`/`.dll` rather than checking a list of package names, so a dependency that grows an optional native accelerator later cannot slip one back in. See [plugin-ulanzi/VERIFY.md](plugin-ulanzi/VERIFY.md)

## Build

**Node runtime support:** the Node bridge/tooling supports the maintained,
prebuild-verified even lines **22, 24, and 26**. Node 20 reached EOL in April
2026 and is intentionally unsupported; odd-numbered releases are not product
targets. `pnpm-workspace.yaml` enforces the engine contract, while
`agentdeck diag native` opens an in-memory `better-sqlite3` database under the
exact executable/ABI that will run the daemon. Windows daemon autostart pins
that executable, so rerun `npx @agentdeck/setup --yes` after changing Node
installations to reinstall native bindings and re-register the Scheduled Task.

```bash
pnpm install
pnpm build                  # shared must build before bridge/plugin
pnpm generate-icons         # SVG → PNG icons (first build or after icon changes)
pnpm generate-creature-glyphs  # canonical creature SVG → ESP32 alpha-mask C header (esp32/.../creature_glyphs_generated.h)
pnpm generate-micro-glyphs  # Timebox 11×11 TS→Swift mirror + official brand SVG → Pixoo/iDotMatrix/TC001 generated alpha masks
pnpm generate-protocol      # protocol.ts → JSON Schema → Swift/Kotlin types (generated/protocol/)
pnpm generate-terrarium-rules  # terrarium-rules.ts SSOT → Swift/Kotlin/C++ generated mirrors (vitest drift gate)
```

### Apple Release (App Store / TestFlight)

Release steps, local build commands, identity/signing, CI secrets, and current App Store state live in **[RELEASING.md § Apple](RELEASING.md)**. Two invariants that apply outside a release:

- **Bundle ID** `bound.serendipity.agent.deck`. The retired `bound.serendipity.agentdeck.*` tree carries an immovable ASC build floor (1.0.6/build 8) — never target it. The Stream Deck **plugin UUID** `bound.serendipity.agentdeck` (no suffix) is a separate, immutable identifier, unrelated to the app bundle ID.
- **Versioning**: root `VERSION` is the repository baseline and compatibility-major anchor (`1.0.2`), not a minor/patch ceiling. Numeric `X.Y.Z` versions are mutually compatible exactly when `X` matches: major changes are protocol-breaking or exceptionally large coordinated migrations, minor changes add substantial backward-compatible features, and patch changes are small backward-compatible fixes. Minor and patch values may advance independently by target. Each target's internal mirrors and its own release tag must match exactly, and `pnpm verify-version` enforces repository compatibility. Apple build number and Android versionCode advance only when those targets ship. Delivery tags remain channel-prefixed (`apple-v*`, `android-v*`, `esp32-v*`, `npm-v*`, `streamdeck-v*`, `ulanzi-v*`).

### Multi-Agent Development Surface

This repo is built by switching between Claude Code, Codex, OpenCode, and Antigravity. **[docs/agent-harness.md](docs/agent-harness.md)** is the canonical map of how each agent enters the repo, what it reads, and what it auto-discovers — read it when onboarding a new agent or wondering why a skill/workflow isn't picked up.

- **Repo instructions**: `AGENTS.md` is the entry file Codex/OpenCode/Antigravity discover by convention. It requires `CLAUDE.md` first, then targeted `DEVELOPMENT_LOG.md` lookup instead of loading the full log. The active log keeps only the most recent ~2 months; older entries are archived by month under [`docs/devlog/`](docs/devlog/README.md) — grep a specific month file when you need history, never load all archives at once.
- **Repo skills (SSOT)**: canonical skills live in `.agents/skills/<name>/SKILL.md` (discovered by Codex; Claude reaches them via the pointers in `.claude/skills/`). Use them before hand-rolling commands. **`.claude/skills/*.md` are thin pointers — never put procedure content there; edit the `.agents/skills/` copy so the two agents can't drift.**
- **Workflow originals**: `.agents/workflows/` remains the canonical human-readable procedure directory; skills may route into these files. OpenCode has no skill auto-discovery — point it at these workflow files explicitly.
- **Session handoff**: use the `session-end` repo skill before `/clear`, `/new`, or handing work to another session. It summarizes current state and updates durable docs only when the change is project-significant.
- **Codex observation**: `agentdeck daemon install` installs/migrates Codex lifecycle hooks in `~/.codex/config.toml`; run `codex` normally. Deprecated `agentdeck codex` still refreshes them before launching its PTY bridge during the compatibility window.
- **OpenCode observation**: `agentdeck opencode` / `agentdeck daemon install` install the AgentDeck observer plugin (`~/.config/opencode/plugins/agentdeck.js`) so standalone `opencode` runs report `opencode_*` lifecycle hooks to the daemon — same observed-session timeline pipeline as direct `claude`/`codex` (`classifyObservedHookEvent` in `bridge/src/daemon-server.ts`). The Swift daemon ingests `opencode_*` too: `opencode:<id>` session rows + chat_start/tool_exec/chat_response timeline rows in `DaemonServer.handleHookEvent`, converging with the opt-in SSE observer on the same session key. Both daemons normalize Claude/Codex/OpenCode lifecycle names into the agent-neutral APME boundary vocabulary; Codex response text comes from the rollout tail (`bridge/src/codex-rollout-response.ts`).
- **A Gateway event you never subscribed to is indistinguishable from one the Gateway does not send, and for OpenClaw that gap cost APME every turn it ever had.** `sessions.subscribe` is a no-param RPC under `operator.read` — the scope `sessions.list` already runs under — and it is the entire admission gate for `session.message` and `session.tool`: the Gateway's recipient set for both is `sessionEventSubscribers ∪ sessionMessageSubscribers`, and a connection in neither set receives nothing. the NODE adapter never called it, so its handlers for both events sat wired and unreachable — the Swift adapter DID call it and then discarded every frame it received, which is a different failure and the harder one to see, and the `chat` frame was the only thing arriving. **That frame is assistant-only** (`emitChatDelta` / `emitChatTerminal` in `openclaw/dist/server-chat-wgxNCdC3.js` build `message:{role:'assistant',…}` and nothing else) — no user prompt, no tool array, no token counts, no model. So nothing ever emitted a `turn_start`, and a `turn_response` with no open turn is dropped by `Collector.setTurnResponse` (`if (!turnId) return`): **657 of 665 recorded OpenClaw runs held zero turns**, the last turn ever recorded was 2026-08-16, and every turn that did exist came from a prompt typed through AgentDeck rather than from the OpenClaw app. The runs were then closed by the 30-minute orphan reaper, which is why nearly every one is exactly ~1800s long. Three copies of the guess had kept this invisible: `ChatEventPayload` declared `prompt`/`tools`/`modelId`, `chat-final-with-tools.json` supplied them, and the parity test read them back — a fixture, a type and an assertion authored together from one assumption agree with each other forever. Fixtures are now **captured off a live Gateway and asserted through the real parser** (`tests/parity/gateway-frames/README.md`). Ownership after the fix, so no fact is counted twice: the prompt comes from `session.message`(user), the tools from `session.tool` (which carries args AND result, under `data` — never at the top level), the per-turn `provider`/`model`/`usage` from `session.message`(assistant) as a `session_meta` span, and the response from both `chat.final` and `session.message`(assistant), which is deliberate — a run the Gateway hides from the control UI never reaches us as a `chat.final` at all, and when both arrive the sample layer dedups on `kind|turnIndex|hash(text)`. **`chat.final` is also OpenClaw's stop signal**, so it emits `turn_end` (`end_source='stop'`; a cancel emits `interrupted`): before that OpenClaw was the only agent leaving turns open under an already-closed task, so a single-turn conversation's turn carried no duration and never flushed its tool tally.
- **An OpenClaw APME run is scoped to a session KEY, never to the Gateway connection.** One connection sees every session the agent has — the chat the user is looking at (`agent:main:main`), each cron job (`agent:main:cron:<id>`), and one fresh key per model-eval run (a suite opens six in three hours). A connection-scoped run interleaves all of them into one trajectory under one `model_id`, and computes the idle-gap boundary across conversations that have nothing to do with each other, so turn ordering, per-task cost and every judge verdict derived from them describe a conversation that never happened. `openclawRunForSessionKey` (daemon) opens `openclaw:<sessionKey>` lazily on that key's first event and `setApmeRunResolver` hands it to the adapter; **each key owns its own idle-gap timer** for the same reason — a heartbeat firing every few minutes would otherwise keep resetting the timer for a user chat that ended half an hour ago, and a task that never closes is never evaluated. `projectName` is the key itself, not the literal "openclaw". A frame with no session key still falls back to the connection-scoped run: a mis-scoped record beats no record. **A key's run opens on its first ingestable span, never while building a context** — opening it in `apmeEntryFor` manufactured exactly the noise the split removes, since a context is built for every frame including ones that parse to zero spans, and a real `agent:main:main:heartbeat` key opened a run holding 0 turns / 0 steps / 0 events (the Gateway filters heartbeat message pairs out of `session.message`, so such frames are routine). **Still open**: the connection-scoped fallback run is itself opened eagerly at connect and, now that essentially every frame carries a key, is usually empty and reaped as an orphan — one row per Gateway connection, the same rate as before the split. Making it lazy means restructuring `setApmeSession`, which `hasDirectApmeIngestion` gates the bridge's timeline→span conversion on. The old `openclaw-<uuid>` rows are **not backfilled** — the session key was never recorded on them, so any attribution would be invented.
- **APME identity and cost belong to the turn that produced them.** `turns.model_id` / `turns.provider` are the scorecard source; a task spanning identities is explicitly `mixed`, while `runs.model_id` / `runs.provider` retain the latest value only for legacy summary compatibility and must never drive per-turn ranking. Provider normalization lives in `shared/src/model-provider.ts` and its generated Swift/Kotlin mirrors. A numeric zero is not proof of a free call: every aggregate carries `cost_known`, unknown cost remains SQL/API `NULL`, budget recommendations exclude it, and only priced or known-local zero may rank as free. Assistant response ownership is explicit too: `chat_final` > direct response > `session_message_projection`; all producers update one stable assistant-message sample slot so a later 8K projection can never replace a full final response (nor create a duplicate event).
- **OpenClaw is Gateway-observed AND transcript-observed, and the two carry disjoint halves.** The Gateway WS stream is the live channel (`connect` / `sessions.list` / `chat.send` / `chat.abort` / `exec.approval.*` / — once subscribed — `session.message` / `session.tool`). **Which producer owns the timeline's tool rows differs per daemon, and that is not an oversight.** Node routes `session.tool` to APME ONLY — its timeline tool rows come from the transcript feed, which predates the subscription, so routing both would double-emit. Swift has no transcript feed (it reaches `~/.openclaw` only through a security-scoped bookmark), so there `session.tool` IS the timeline's source; it emitted nothing at all until its reader was taught the real `data`-nested shape. The two daemons therefore produce the same row TYPE from different sources — never at the same time, since one owns the port — and the rows read slightly differently (`read · /path` with the session key vs `read · success`). Before the subscription the only tools that ever reached the timeline were the ones that happened to need approval, which is a biased sample rather than a log. OpenClaw writes a full per-session transcript anyway (`~/.openclaw/agents/<agent>/sessions/<uuid>.jsonl` + a typed `<uuid>.trajectory.jsonl`, indexed by `sessions.json` whose KEYS are the session keys), so `bridge/src/openclaw-transcript-timeline.ts` + `openclaw-timeline-feed.ts` read it and emit **only `tool_exec` rows** — the complement of the Gateway stream, never a duplicate of it. Three bounds, each measured: only sessions written inside `ACTIVE_WINDOW_MS` are read (the store keeps every session forever — 103 on the machine this was built against); a first sighting emits **nothing**, the opposite of `KiroTimelineFeed`, because OpenClaw has no blank-strip problem to solve and seeding would inject minutes-old tool calls from finished eval runs; and rows are attributed to the existing virtual `openclaw-gateway` row rather than minting sessions, since an eval suite opens a fresh session key per run (six in three hours). **The session key is the orienting fact and rides every row's `detail`**: `agent:main:main` (the chat the user is looking at), `agent:main:cron:<id>` and `agent:main:eval-…__r2` all arrive as the single literal "OpenClaw", which is how an approval raised by a model-eval harness looked like it came from a conversation the user could not find in the OpenClaw app (2026-08-23). The feed is gated on the SSOT presence predicate (`gatewayConnected`), not on the store — rows under a session no surface is showing are worse than no rows. **Two things had to be fixed before a single row ever reached a live strip, and both were invisible until it was measured end-to-end (2026-08-23: three consecutive OpenClaw turns, each one written to the store and read back correctly, published nothing).** First, the pump needs a driver of its own (`OPENCLAW_FEED_INTERVAL_MS`): it originally rode `passiveSessionObserver.onRefreshed`, which fires only when the observed PROCESS set changes. Every other transcript feed may ride that edge because its subject is IN that set — a Kiro turn moves its own row's `state`/`lastActivityAt` — but OpenClaw is reached over the Gateway and has no process row at all, so an OpenClaw turn moves nothing the observer can see and the pump ran only when an unrelated agent started or stopped (plus once at boot, empty cache → populated). **A producer must be driven by a signal its own subject can move.** Second, `tool_exec` is the ONLY type this feed emits and is exactly the type `evictOne` sheds first, so on a full buffer — the steady state on any busy machine — the row evicted ITSELF on insertion (`addEntry` pushes, then evicts, and it was the only plain `tool_exec` present). OpenClaw is now carved out of that rule in BOTH daemons, like the subagent dispatch rows before it, since the two take turns owning `timeline.json` and a one-sided carve-out leaves the replay buffers diverged. Both failure modes look identical from outside — a tick that emits nothing writes nothing — which is why the emit path is logged at all. Note the trajectory file is **not** a tool log: across all 484 in this store it carries only 8 event types (`session.started` / `prompt.submitted` / `model.completed` / `session.ended` and metadata), one `runId` per turn with per-turn provider/model and token usage, and **zero tool events** — turn boundaries and cost, never the steps. It is also **not needed as an APME enrichment axis**: the per-turn model and token usage it carries now arrive first-hand on `session.message`(assistant) and are ingested as `session_meta`, so reading them from a polled file too would be a second source for a column we already own — which is where drift lives. **Provider is the exception and the decision does not rest on it**: `gen_ai.system` is emitted and declared but has no consumer (`grep gen_ai.system` finds the emitter and the type, nothing else), so the endpoint that answered is currently recorded nowhere. Its destination already exists (`shared/src/model-provider.ts` with generated Swift/Kotlin mirrors); wiring it is open work, and until it is, do not cite provider as a reason the transcript is redundant. Node daemon only: the sandboxed Swift daemon reaches `~/.openclaw` only through a user-granted security-scoped bookmark, the same consent surface Kiro needs, and that is a Settings flow rather than a code port.
- **A Gateway link that keeps reconnecting reads `connected` at every sample, and the reason it dropped is written only in OpenClaw's own log.** Eleven Gateway restarts in ninety minutes (2026-09-02) produced eleven `connected` lines in the daemon log, an OpenClaw row that flipped to `gateway_not_found` and back on every surface, and nothing that said so — each cycle is indistinguishable from a healthy recovery. The cause was two OpenClaw installs (a global npm/pnpm copy beside the app-managed `~/.openclaw/tools` runtime) fighting over `~/.openclaw/state`: the launchd unit ran whichever copy last ran `gateway install`, its startup migration refused to run because the other copy held the state, KeepAlive respawned it until OpenClaw's own restart-loop breaker tripped, and a plugin install restarted it on top. `bridge/src/openclaw-gateway-stability.ts` counts disconnects in a ten-minute window (three = unstable), reads the tail of `~/Library/Logs/openclaw/gateway.log` for the sentence OpenClaw prints (`another Gateway owns that state directory` outranks `restart-loop breaker tripped` outranks a routine config restart, whichever is newer), and surfaces it as `gatewayInstability` on `/health` + `/status` and one `error` timeline row on `openclaw-gateway` — the timeline being the one channel every surface already renders, Android and e-ink included, without a protocol change. Fixtures are the real log lines, not the matcher's regexes. Operator rule that the finding points at: `openclaw` on PATH must be `~/.openclaw/bin/openclaw` (the app-installed wrapper that runs the managed node) ahead of `/opt/homebrew/bin` — a stray global CLI running `gateway install` bakes `process.execPath` into the plist and recreates the fight. Node daemon only; the sandboxed Swift daemon cannot read the Gateway log.
- **Kiro observation is passive-first**: users run native `kiro-cli` / `kiro-cli --v3` or Kiro IDE as usual; never add an `agentdeck kiro` managed PTY. The Node daemon correlates processes with Kiro's native stores in `bridge/src/kiro-session.ts` / `passive-observer.ts`: Kiro CLI 2.18.1 v2 uses macOS app-data `kiro-cli/data.sqlite3` (`conversations_v2`), while v3 writes `KIRO_HOME/sessions/<workspace-hash>/<session>/session.json` + `messages.jsonl`. Read SQLite with a read-only/query-only handle and never inspect auth/telemetry tables. Kiro CLI 2.13+ v3 accepts global `~/.kiro/hooks/*.json` and `installKiroHooksIfNeeded()` installs AgentDeck's standalone v1 file (telemetry-only `SessionStart` / `UserPromptSubmit` / tool / `Stop`, never a steering decision) — but **installing them buys nothing for CLI chat**: measured 2026-08-17 on kiro-cli 2.18.1, Kiro logs `v2 hooks loaded 5 standalone hooks` and then a real `kiro-cli chat` turn fires **none** of them (each hook was instrumented with a marker file; a live turn produced zero markers, while a hand-POSTed hook produced a timeline row normally, so the receiving side was never the problem). That surface belongs to the Kiro IDE agent. **Kiro is therefore transcript-observed on BOTH tiers**, not just Tier 2 — `bridge/src/kiro-transcript-timeline.ts` + `kiro-timeline-feed.ts` (Node) and `LocalKiroObserver` + `KiroTimelineFeed` (Swift). The feed admits only the latest turn on first sighting and new rows thereafter; those same bounded rows now feed APME so Kiro appears in unified activity without replaying old transcripts. Two consequences follow: a Kiro session appears seconds late rather than instantly (it is polled, not pushed — `SCAN_INTERVAL_MS`), and it is always reported `idle`, because a transcript gains its assistant record only once the reply lands and claiming `processing` would be inventing a state. The sandboxed app reaches `~/.kiro` only through a user-granted security-scoped bookmark (`AppPreferences.withKiroDirectoryAccess`, Settings → Integrations → Kiro CLI); with no grant it observes nothing rather than guessing. V2 remains process/store observed because the global standalone hook surface is v3-only. `agentdeck diag kiro [--json]` is the daemon-free, issue-shareable probe; keep its output content-free and use report-scoped opaque keys for cwd/session identity. The Kiro creature uses the pinned `design/brand/kiro.svg` from MIT-licensed `@lobehub/icons-static-svg@1.94.0`; preserve its exact geometry and the provenance/trademark boundary in `design/RESOURCES.md` when regenerating glyphs.

## CLI

The CLI command is `agentdeck` (`bridge/src/cli.ts`).

Full command list: `agentdeck --help`, or [docs/cli.md](docs/cli.md) for the annotated reference.

**Module flags**: `--local` (all device modules off), `--no-adb` (skip ADB reverse). There are no per-session `--no-mdns`/`--no-serial`/`--no-pixoo` flags — hardware modules are daemon-only and session bridges never activate them

**Session sort weight**: session commands (`claude`/`codex`/`opencode`/`monitor`) accept `--weight <n>` (integer in **-9999..9999** — `SESSION_WEIGHT_MIN/MAX` in `shared/src/session-utils.ts`, emitted to Swift/Kotlin via `pnpm generate-session-weight-rules`; default 0) — an explicit deck/tab sort override. `sortSessions` (SSOT `shared/src/session-utils.ts`, hand-mirrored in Swift `DashboardDataRules`, Kotlin `EinkFormatUtils`) orders by **weight ascending first** (negatives → unweighted/0 → positives), then the existing agentType→project→startedAt→id keys; weight also joins the Codex display-fold key so distinct pins never fold together. Comparators are three-way, never subtraction. Threads CLI → `SessionOptions.weight` → `SessionEntry.weight` (registry) → `session_push_register` + `SessionInfo.weight` (wire, sanitized at daemon boundaries) → every surface. Lets a user pin Windows Terminal / iTerm tab order onto the Stream Deck. Leaving all weights at 0 reproduces the pre-weight ordering. See [docs/cli.md → Pinning session order](docs/cli.md#pinning-session-order-with---weight).

**Env-var default args** (`bridge/src/cli.ts` — `applyGlobalEnvArgs`/`weaveAgentCommand`/`resolveAgentCommand`): `AGENTDECK_COMMANDER_ARGS` injects flags into the `agentdeck` (commander) layer — spliced into argv right after the session subcommand, **keyed on `argv[2]`** (`claude`/`codex`/`opencode`/`monitor`; any other command ignores it, even with a session word as a positional value). Env tokens land before typed flags: scalar options are overridden by retyping (last-write); boolean flags have no inverse spelling, so the per-invocation override is **`--no-env-args`**, which disables BOTH layers (the splice pre-parse, the per-agent weave in the action). `AGENTDECK_CLAUDE_ARGS` / `AGENTDECK_CODEX_ARGS` / `AGENTDECK_OPENCODE_ARGS` append to the spawned agent command, weaving onto an existing `-c` (e.g. `AGENTDECK_CLAUDE_ARGS="--remote-control"` + `-c "claude --resume X"` → `claude --resume X --remote-control`). The per-agent append rides the same platform shell path as `-c` (`pty-manager.ts`); the global var is tokenized in pure JS and never touches a shell.

**node-pty macOS helper mode** (`bridge/src/pty-manager.ts`): stable
`node-pty@1.1.0` is published with both Darwin `spawn-helper` prebuilds at mode
0644 (upstream microsoft/node-pty#850/#919), so the native addon imports but its
first spawn fails with the misleading generic `posix_spawnp failed`. Before the
dynamic import, `PtyManager` resolves the actual installed package and adds only
the missing execute bits to a regular helper file (prebuild first, source-build
fallback). This runtime repair intentionally covers direct bridge installs as
well as `@agentdeck/setup` and does not depend on npm/pnpm install scripts. Never
replace it with an import-only probe; the measured failure occurs only at spawn.

## Key Conventions

- **Hook format (CRITICAL)**: Claude Code v2.1+ requires 3-level nesting: `{ matcher: "", hooks: [{ type: "command", command: "..." }] }`. Old flat format silently fails. **Every installer targets the user-global `~/.claude/settings.json`** — that plus the two per-project files are the only paths Claude Code watches, so `~/.claude/settings.local.json` (which `localSettings` resolves against the git root / cwd, not `$HOME`) is a dead file at user scope. The CLI installer writes it via `installHooks()`; `migrateHooksIfNeeded()` relocates pre-move installs out of the legacy file **and rebuilds any hook whose `curl` is still unbounded** (`hasUnboundedHookCurl`) — the file is co-owned with the macOS app, so an older app build can and does overwrite a fixed command set; the App Store opt-in UI writes the user-selected `settings.json` and migrates the same legacy path. Codex uses lifecycle hooks in `~/.codex/config.toml` (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `Interrupt`) installed by `installCodexHooksIfNeeded()`. `PermissionRequest` and `Interrupt` must be trusted in Codex after installation; writing the TOML alone does not activate a new hook. Live-verified: CLI 0.149.0 supports `PermissionRequest` but silently omits `Interrupt`; 0.151.0 supports both (Interrupt timeout ≤3s). Kiro v3 uses AgentDeck-owned `~/.kiro/hooks/agentdeck-lifecycle.json`; the setup/bootstrap copy must stay structurally identical to `buildKiroHookFile()`, and every Kiro command stays fire-and-forget even for `PreToolUse`/`Stop`. Codex warns when one config layer contains both `hooks.json` and inline `[hooks]`; consolidate same-layer user hooks into official `[[hooks.<Event>]]` arrays in `config.toml`. The AgentDeck installers preserve and merge those user arrays, but still reject incompatible regular `[hooks]` tables. Scripts use bounded `curl` and `|| true` to avoid blocking when bridge is down — fire-and-forget events **must** keep `--connect-timeout 0.2 --max-time 0.8` (and `--connect-timeout 0.2` on the `/health` probe): Claude gives all SessionEnd hooks a single ~1.5s abort budget, so an unbounded POST to a *restarting* daemon (socket open, no reply) is killed and surfaces as `SessionEnd hook [...] failed: Hook cancelled`. Only Claude's `PreToolUse` (60s long-poll) and `Stop` (10s) are request-response. The Claude snippet is mirrored byte-identically in 3 places — `hooks/src/install.ts` (canonical), `setup/src/setup.ts` (inlined because `@agentdeck/setup` bootstraps the workspace and may not depend on it), `apple/.../HookInstaller.swift` — change all three together. The bridge has no copy: it imports `migrateHooksIfNeeded` from `@agentdeck/hooks` (the former `bridge/src/hook-migration.ts` fork silently downgraded PreToolUse/Stop to fire-and-forget)
- **PERM is a claim that a human is being waited for, and each agent proves it differently — never by prediction where a real signal exists.** The per-agent sources: Claude Code's `Notification` with `notification_type: permission_prompt` (display-only) and the observed-session PreToolUse **hold** (device Allow/Deny, 25 s); Codex's `PermissionRequest` hook, which fires only when Codex is about to ask (display-only — the rollout carries no approval event, so before it a Codex session blocked on `approval_policy = "on-request"` read `processing` until the 10-minute stale-turn fallback) and `Interrupt` (Ctrl+C closes the turn `interrupted`); OpenCode's `permission.asked` via the observer plugin (answerable `ocperm:` requestId in BOTH daemons — the Node daemon used to classify it for the timeline and drop it for state, `bridge/src/hook-opencode-sessions.ts`); OpenClaw's `exec.approval.requested` (Gateway-blocked, with expiry/abandon). Kiro and Antigravity have no permission source and never show PERM. **The Claude PreToolUse hold is the one place PERM is predicted, so its predictor is a single generated SSOT**: `shared/src/claude-permission-rules.ts` (→ `pnpm generate-claude-permission-rules` emits `ClaudePermissionRules.generated.swift`, vitest byte gate + `shared/claude-permission-vectors.json` replayed by both suites). It exists because the two hand copies drifted into the SAME defect: both understood only the legacy `Bash(cmd:*)` spelling, while the permission dialog writes `Bash(cmd *)` — 67 of the user's 73 Bash rules — so every allowlisted call in an `acceptEdits`/`default` session was held for the full 25 s, the deck showed a PERM the terminal never asked, and the learner's 8 s window could not learn a `curl` that took longer than that (measured 2026-09-05: awaiting→processing exactly 25.0 s, re-held on every batch). The rules follow the Claude docs: `*` matches any text including spaces, a trailing ` *` also matches the bare command, the legacy `:*` keeps BOTH its readings (` *` alias and raw prefix — over-matching only costs a missed hold), compound commands split on `&& || ; | |& &` and EVERY subcommand must be covered, the built-in read-only set (`ls cat git status …`) never prompts, `acceptEdits` also auto-approves `mkdir touch rm rmdir mv cp sed`, wrappers/env assignments are stripped. `auto`/`plan`/`dontAsk`/`bypassPermissions` never hold (the classifier's decisions live outside the settings files). A missed hold costs nothing (the terminal prompts as before); a false hold costs a lie plus a stall, so every uncertainty resolves to "don't hold"
- **An ESP32 release ships a merged factory image, and its header is verified against the SSOT before it is published.** The old asset set was bootloader/partitions/app as three loose files with instructions to write the app alone at `0x10000`, which cannot bring a board up: `boot_app0.bin` (0xe000) was never published — it is the one input that lives in the Arduino framework package rather than `.pio/build/`, so the copy step could not have picked it up — and a stale otadata therefore boots the PREVIOUS slot; the bootloader offset is chip-specific and this fleet spans **three** values (`esp32` 0x1000, `esp32p4` **0x2000**, everything else 0x0), documented nowhere; and an unstated flash size leaves a wrong header (TC001's bootloader misbehaves on the 4MB default). `scripts/esp32-merge-firmware.mjs` emits `agentdeck-<board>-merged.bin` written at `0x0` on **every** chip — classic boards keep their bootloader at 0x1000 inside the image behind `0xFF` padding the ROM never reads, so no consumer branches on chip family. Because `merge-bin` patches the flash parameters into its own output, the only way to know the header is right is to read it back **at the bootloader offset** (`image-info` on a classic merged image starts on padding and fails `invalid magic number: 0xff`). `scripts/generate-firmware-manifest.mjs` then publishes `manifest.json` with sha256/size computed **from the artifacts**, and fails the release when any SSOT board is missing files — the previous failure mode was the opposite, a board shipping nothing while every step stayed green. esptool is pinned (`5.2.0`): it renamed `merge_bin`/`--flash_size` to `merge-bin`/`--flash-size` between v4 and v5, so un-pinned it breaks a cut at tag time. **Take that number from PyPI, never from a local `pip show esptool`.** PlatformIO vendors its own esptool as the `tool-esptoolpy` package and installs it EDITABLE into `~/.platformio/penv`, so a dev machine answers `5.1.2` for a version PyPI has never published — its 5.1 line stops at 5.1.0. That is where the previous pin came from, and it failed the only way it could: at tag time, on `esp32-v1.0.7`, with `No matching distribution found for esptool==5.1.2`, i.e. the pin caused the exact failure the pin exists to prevent. Two registries, one distribution name. The local merge runs resolve bare `esptool` on PATH, which is a third thing again, so "validated on this machine" says nothing about what CI will install. **The same rule cost `ulanzi-v1.0.4` two red tags, on a different tool and a different package manager.** `scripts/package-ulanzi-plugin.sh` bundled with bare `npx --yes esbuild`, and esbuild is a declared dependency of nothing here — it is reachable only as a transitive of vite. Inside a pnpm workspace `npx` resolves that transitive copy, decides esbuild is already installed, skips installing it, then finds no bin (pnpm links no bins for transitive packages) and falls through to `sh -c esbuild`: `esbuild: not found`. A dev machine hides it forever, since something has usually left a hoisted `node_modules/.bin/esbuild` behind. Pinning the version in the npx call does NOT fix it — npx's "already installed?" check matches either way, which is what burned the second tag — so the fetch goes through `pnpm dlx <pkg>@<version>`, which has its own store and runs the platform postinstall. Reproduce before touching either pin: clone to a fresh directory, `pnpm install --frozen-lockfile`, `pnpm build`, run the script; then close it by hashing the same artifact in all three places (dev machine, clean clone, published asset)
- **A refusal to flash has no override, and it is written once for both flashers.** Getting firmware onto a board is the entry barrier to the whole ESP32 surface — every asset of `esp32-v1.0.6` was downloaded zero times — so there are now two ways in: `/flash/` (`tools/web-flasher/`, a Vite app on Pages) and `agentdeck esp32 flash <board>`. They do NOT share the esptool-js driving code (Web Serial vs a `serialport` shim), so the piece that must not drift is the **decision**: `esp32PreflightVerdict` in `shared/src/esp32-boards.ts` refuses a chip-family mismatch or an image declaring more flash than the part reports, and there is deliberately no `--force` and no "flash anyway" button — the recovery tool for a bricked board is the tool that refused. Three polarity traps live in that one function. **`webFlash` means "offered in the browser", never "may be written"** — it takes a `surface: 'browser' | 'cli'`, because `esp32_c6_147` has no OTA slot and USB is its ONLY update path, so a CLI inheriting the browser's list would leave that board unupdatable by anything. The **size check is directional** (declared ≤ detected): InkDeck is physically 16MB with an 8MB BSP field, so an equality test fails the one board doing the correct thing. And an unreadable flash id **stays unknown** — `detectFlashSize()` silently answers `"4MB"` when it cannot decode the id, so trusting it turns "no answer" into a confident wrong number that then gates the write; the surfaces say the check was unavailable rather than implying it passed. A fourth rule is about WHICH value the guard checks: the board spec is bundled with the tool while the image geometry comes from a release manifest resolved separately (`--tag`, or whichever release Pages deployed), so `imageGeometry` is compared too — otherwise a board corrected down to 4MB in master, a pinned 16MB manifest and an 8MB part combine into `4 ≤ 8` passing while a 16MB header lands on an 8MB part, the exact brick the function exists to prevent. That one is **strict equality, not directional** (unlike the size rule): the two values describe the SAME board from two sources that must agree, so a disagreement either way means they describe different boards with no way to tell which is true — and it is the ONLY size check left when the flash id is unreadable, which is a case the fleet actually has. Its cost is a release-ordering constraint, not a defect: after an SSOT flash-size edit the browser refuses that board until Pages redeploys with the matching manifest (RELEASING.md). A fifth is about a promise the library does not keep: **`eraseAll` is stub-only** (`if (this.IS_STUB === true && options.eraseAll === true)`), so on a `--no-stub` board — and `ttgo_t_display` is `webFlash: true` — ticking "erase the whole flash first (clears saved Wi-Fi and pairing token)" was silently dropped after showing an `erase` phase and `MD5 verified`, handing back a board still carrying the previous owner's credentials; both surfaces refuse rather than skip. Two runtime traps carried over from the spike: esptool-js's published ESM has **extensionless relative imports** that Node cannot resolve (`from "./util"`), so every Node consumer goes through `bridge/src/esptool-js-node.ts` → `esptool-js/bundle.js`; and `calculateMD5Hash` receives the buffer **after** esptool-js patches the flash-params header, not the image you passed. **Every teardown await here is bounded**: `Transport.disconnect()` spins in `waitForUnlock()` with no deadline and `Transport.write()` has no `try/finally`, so one rejected write (an unplugged board) locks the stream forever — and that teardown sits inside the `finally` the CLI waits on before releasing the daemon's serial lease, so inheriting its hang means no further output AND a dead serial layer for the whole lease
- **Writing the bytes is not installing the firmware, and `esptool-js` will not reset the board for you.** Its non-USB-OTG hard reset is, in full, `sleep(100); setRTS(false)` — a RELEASE with no ASSERT. That works only when the preceding step left EN asserted, which `--before default-reset` does and a finished `writeFlash` does not, so the chip is left parked in the flasher stub: the firmware never runs and the post-write `device_info` read-back cannot succeed however long it waits. Both flashers therefore reset through `ESP32_POST_WRITE_RESET_SEQUENCE` (`D0|R1|W100|R0`, `shared/src/esp32-boards.ts`) rather than `after('hard_reset')`. **`D0` is load-bearing and only one board shows it**: pulsing EN without first driving IO0 high leaves the CH340 boards in download mode, which from outside is indistinguishable from a board that failed to boot — and the two adapter classes take different strategies inside esptool-js (`UsbJtagSerialReset` for `0x303a/0x1001`, `ClassicReset` otherwise), so a sequence verified on one is not evidence for the other. Measured 2026-08-23 on three boards spanning both classes and the no-stub path. Two corollaries. **`stub` and `esptoolFlags` describe different tools** — `stub` drives esptool-js (browser + CLI), `esptoolFlags` mirrors `platformio.ini` for esptool.py, the board-matrix gate cross-checks only the latter pair, and they may legitimately disagree (ttgo does) as long as the board's note says why. And **connecting is not writing**: `ttgo_t_display` was `webFlash: true` on evidence that it CONNECTS, while pinned `--no-stub` made it unwritable by either surface — the ROM loader has no compressed flash mode, so the write died at `Failed to enter compressed flash mode`, and uncompressed died one step later at `Failed to enter Flash download mode`, both before a byte landed. A board's `webFlashVerified` must record a completed write, not a handshake. **"Stubless writing is unsolved" was the wrong frame**, measured 2026-08-23: of the three remaining `stub: false` boards, two (`ips_35`, `round_amoled`) have never been USB-attached and their `stub: false` is INHERITED from a `--no-stub` pin added inside unrelated June commits that never mention the stub — unknown, not failing, and unusable as evidence. The third (`ips_10`) fails at SYNC, which precedes stub loading in both tools, so `stub: true` cannot reach its failure at all. Its recorded evidence also quoted esptool's "The serial TX path seems to be down" as a finding, and that is wrong: the board reaches download mode and its ROM banner arrives over that very UART. **A tool's guess about which direction failed is not a measurement** — esptool infers it from a failed round trip. Two instrument traps sit on this path and both yield confident wrong answers: node-serialport's `set()` is `{...defaults, ...options}` with `dtr/rts` defaulting to TRUE, so a partial `set({dtr:false})` asserts RTS and holds EN low — a probe ending that way reads 0 bytes in every mode and "proves" a silent ROM (the product's `NodeWebSerialPort.setSignals` already knows this; a harness must borrow it rather than call `set()` itself); and `drain()` times out on this adapter whether or not anything is wrong, so reading that as "the bytes never left" invents a broken wire — the running app answers 1403 bytes through the identical path. Also: esptool-js implements only `ClassicReset`/`UsbJtagSerialReset`, and only esptool.py's `UnixTightReset` reaches `ips_10`'s download mode, so no built-in esptool-js strategy can ever get there; `CustomReset` can (`D0|R0|D1|R1|D0|W100|D1|R0|W50|D0`), where the PREAMBLE is load-bearing and atomicity is not
- **A serial-suspend lease is a FILE, and it expires when it is read.** Every serial open toggles DTR/RTS and resets the board, so the daemon has to let go during a flash — but the daemon that stole the port in the recorded failure was the **respawned** one, and an in-process pause cannot span a respawn. `POST /esp32/serial/suspend` (behind the normal auth gate — same-machine is already authenticated, so this adds no standing unauthenticated route) writes `~/.agentdeck/esp32-flash-lease.json` and calls `releaseESP32SerialPorts()`; refusing to *open* is only half the job, since a port the daemon already holds still blocks the flasher and two readers on one macOS TTY steal each other's bytes rather than failing cleanly. Expiry is enforced in `readLease()`, never by a timer — a timer firing late on a sleeping laptop extends the suspension past what was promised, while a read-time check self-heals when the flasher is killed mid-write, with nothing running. Timers stay armed so the next poll re-opens on its own. **Honest gap**: the sandboxed Swift daemon cannot read `~/.agentdeck`, so the CLI also runs an `lsof` pre-check (allow-list polarity — an unknown holder is foreign and refuses the start) and always verifies after writing. That pre-check has **three answers, not two**: `lsof` exits non-zero both when nothing holds the file AND when it is missing, times out, or hits EPERM, so collapsing those into "free" launders "I could not look" into "nobody is holding it" — the same trap `esp32FlashIdIsUsable` avoids on the flash-size axis, inverted to the permissive direction. **Suspending must also invalidate opens already in flight.** `pollForDevices` holds a port in `openingPorts` across `await openPort()` — an fd open plus an `stty` exec — while the release only sees `connections`, which that port is not in yet: a suspend arriving mid-open reports `released: 0`, the CLI logs success, and a second later the open resolves and pushes a live connection whose heartbeat then writes JSON into the same TTY esptool is writing firmware to. A generation counter bumped on release and re-checked after the await discards it — the same rule as `OpenAttemptToken` in the Swift `ESP32Serial`. MD5 proves the bytes landed, not that the board boots them, so it reopens at 115200 for `device_info` — and **`ulanzi_tc001` skips that by name**, because its CH340 TX is broken in hardware and the check would report a good flash as a failure

- **A code asks the DEVICE to prove something; approval asks the OPERATOR, and only the second one a camera-less reader can complete.** The pairing code is still gated on discovery — a client spends it against a daemon it found over mDNS — so on a segment where multicast is filtered it is unreachable by exactly the devices it was built for. The device does nothing at all, which also makes it the stronger trust model: a code trusts whoever knows a secret, an approval trusts a peer the operator pointed at, and an attacker cannot approve themselves. **Identity is the device id when the client sends one (`x-agentdeck-device`, a random per-install 128-bit id) and the address only when it does not** — the decision happens before any frame, so `client_register` is too late to supply it, and an address is not an identity behind NAT where every device shares one. Remember each socket's own `device_info` report instead. Ref: `bridge/src/device-voice-reply.ts` (`ReplySink.deviceKey` + `resolveLive`)
- **A baked animation loop must close, and only the baked surface can tell you it doesn't.** A live ticker (Stream Deck: `animFrame++` every 150ms) hides incommensurate periods forever, because it never wraps. Bake the same renderer into a looping GIF — which is what the D200H does, since Ulanzi Studio plays and loops it on the device, so a transition costs one push and steady-state motion costs nothing — and every animated value must return to its start at the same frame or the tile visibly jumps once per loop. `SESSION_SLOT_ANIM_CYCLE` (`shared/src/svg-renderers/session-slot-renderer.ts`) is that period; a new animated element must have a period that divides it (dash phase closes at `BORDER_PERIMETER / speed`, so speeds must be one value or integer multiples of it; pulses ride `PULSE_OMEGA = π / cycle`). Two corollaries from the same 2026-08-07 pass: **a renderer's output is used as identity, so it must be deterministic** — `svgFrame` minted its gradient id with `Math.random()`, which looked perfect on screen while breaking device push dedup, the "does this tile animate?" probe, and the GIF cache at once (never `Math.random()` in a renderer); and **the frame rotation that gives each key its own phase must have exactly one definition** (`frameOrderFor`) — deriving it separately for "collect the frames" and "is this tile still current?" made every phase-shifted key read as permanently stale, so its encode was cancelled and requeued forever and the symptom was merely "nothing animates". Gates: `shared/src/__tests__/session-slot-anim.test.ts`, `plugin-ulanzi/src/__tests__/anim-schedule.test.ts`, plus the `SYNC-HASH` pin in `apple/AgentDeck/Rendering/SessionSlotRenderer.swift` (the Swift Stream Deck preview mirrors the same origin; the Swift D200H preview is deliberately static and mirrors layout only)
- **An observed session's `sessions_list` row is the SSOT for its prompt** — it has no live state channel of its own. `focus_session` is answered with the daemon's *global* `state_update` stamped with that session's `focusedSessionId`, so it passes any "is this event mine?" attribution check and, applied as a replacement snapshot, blanks the row's real `question`/`options` off the deck. Re-seed from the row instead of storing that snapshot (`plugin-ulanzi/src/state-store.ts`, `plugin/src/focused-detail-state.ts` — the same bug lived in both). Related: a device answer to an observed prompt is only deliverable when the daemon says so via `liveAnswerable` (it can type into the session's terminal, or is holding its AskUserQuestion open — see the ask-gate in `observed-steering.ts` / `ObservedSteering.swift`); `requestId` stays off the wire for a question, since it makes devices render a binary Allow/Deny over a multiple-choice prompt. A single AskUserQuestion call may carry up to four question groups — the daemon presents them **one at a time** and never flattens them into one index space, because an index only means anything within the group on screen. A press must **name the question it answers** (`select_option.question`), which is exactly the line that keeps a hardware approve key — `select_option(0)` as a yes/no stand-in on hud_bar / pocket / ticker / knob `MI_APPROVE` — from committing a guess as the user's stated answer; only a surface rendering the real option list may echo (ESP32: the T-Embed knob's `MI_OPTION` alone). The echo is matched **as a truncation-tolerant prefix** (`askEchoMatches`), because a question is capped at 120 CHARACTERS but held in a 160-BYTE firmware buffer — exact match refused every answer to a Korean question while passing every English one. Two traps when echoing from firmware: send the RAW daemon string, never the display copy (`sanitizeLvglText` rewrites punctuation and blanks non-Hangul CJK), and compose against `Net::OUTBOUND_MAX_LEN` since the outbox truncates and a JSON frame cut mid-string is unparseable. And a **hand-mirrored string rule must compare the same units on both sides**: Swift `String.count`/`hasPrefix` are grapheme-cluster and canonical-equivalence based while TS `.length`/`startsWith` are UTF-16 code units, so an echo cut inside a grapheme was refused by one daemon and accepted by the other — the Swift mirror compares `.utf16`
- **One session, two id forms**: devices and `sessions_list` address a passively-observed session as `observed:<agent>:<uuid>` (and devices see it **truncated to 31 chars**), while timeline rows, hook payloads and transcript filenames use the **bare uuid**. Normalize with `rawSessionId()` / `sameSession()` from `@agentdeck/shared` before comparing — never inline the regex, which is how four copies drifted into three different agent lists and a fifth site skipped stripping entirely (a spoken reply armed under one form, looked up under the other, matched nothing). Device-sent ids also need `resolveSessionIdPrefix` for the truncation
- **A progress indicator binds to bounded work, and the bound is structural**: a spinner may only reflect an attempt that is guaranteed to end. Never drive one from a subscription that is *designed* never to finish — `BridgeDiscovery.isSearching` reports the long-lived Bonjour browser (kept alive so a Mac appearing later is still found), and rendering it as progress is what got iPhone/iPad 1.0.2 (3901) rejected under App Review Guideline 2.1(a) on 2026-08-04. Splitting the signal is only half the fix: the bounded flag then has many exits (discovery hit, saved-URL fallback, the reconnect ladder, an explicit user stop) and any one that forgets to clear it restores the same symptom — a socket-level `disconnect()` knows nothing about the waterfall above it. So funnel the flag through `begin*()`/`end*()` and arm **one deadline per run** that clears it whatever stage is in flight (it must not tear down the socket — live work keeps its own `connecting` phase and can still succeed). Two corollaries: every stop must land on a **recoverable terminal state**, and a visible retry must never no-op on a leftover stage guard, so `retry*()` (ignores the guard) is a separate entry point from `start*()` (respects it). Testing the phase-resolution function is not a regression gate — it mirrors its inputs and stays green with the flag stuck true; drive the real state machine with an injected deadline instead. Ref: `apple/AgentDeck/State/AgentStateHolder.swift` (`beginForegroundSearch`/`endForegroundSearch`/`stopConnectionAttempts`/`retryConnectionWaterfall`), `apple/AgentDeckTests/ConnectionOverlayTests.swift` (`ForegroundSearchBoundTests`)
- **Nothing that may stop answering can gate a port release.** `DaemonServer.shutdown()` awaited `ModuleManager.stopAll()` — a task group over every module's `stop()` — and a task group waits for ALL of its children, so one wedged module (a BLE stop parked on a reply that never came) meant the `wsServer.stop()` below it was never reached. Quit survived this because `AppDelegate` arms a 3s watchdog and force-exits; **reclaim and stand-down had no such backstop and simply hung**, stranding the daemon on fallback port 9121 for the rest of its life after announcing it was reclaiming 9120 (2026-08-06). Bound such stages with `withBudget` (`DaemonActor.swift`), which **abandons rather than cancels** — cancellation is cooperative and a subsystem parked on a continuation that never resumes never observes it. Two corollaries: a guard cleared only by a `defer` (`isReclaimingPort`) latches forever behind a suspended await, so it must not share a failure mode with the thing it guards; and **liveness ≠ availability** — `waitForDaemonExit` proves a daemon stopped ANSWERING, never that its port is free, so a taker must also wait for a real bind (`waitForPortBindable`). The canonical port may still be unwinnable for reasons neither daemon owns: a sleeping WiFi board with bytes queued leaves its socket in `LAST_ACK` on that port and Network.framework exposes no `SO_LINGER` to RST out of it, plus macOS holds a NECP reservation ~14s after `NWListener.cancel()` during which `lsof` shows **zero** sockets and `bind()` still returns EADDRINUSE. So the CLI states why it is taking a fallback port instead of doing it silently — a silent fallback is what left 9120 owned by nobody while `agentdeck daemon start` reported success. Ref: `bridge/src/cli.ts`, `bridge/src/session-registry.ts`, `apple/AgentDeck/Daemon/DaemonService.swift`, `apple/AgentDeck/Daemon/Server/WebSocketServer.swift` (`acceptedConnections` — the one listener accepts plain HTTP and SSE too, and only upgraded WebSockets used to be tracked)
- **A daemon's intent is persisted; its outcome never is.** `daemon.json` records the port a daemon actually bound and every client resolves through it. The port it *wanted* is a different fact, and until it existed a daemon bumped to a fallback had no way to know it was on the wrong port — so a 14-second kernel hold on 9120 became permanent, and nothing but a hand-typed `stop`/`start` moved it back. `bridge/src/daemon-port.ts` resolves that intent (`-p` › `AGENTDECK_DAEMON_PORT` › `settings.json daemonPort` › 9120, mirroring the app's `AppPreferences.daemonPort`) and **only the user writes it** — `agentdeck daemon port <n>`. Writing the outcome there instead is self-reinforcing: the fallback port would be recorded and preferred forever after. With an intent, a preferred port that is bound but answers no `/health` is diagnosable — it is the kernel still holding a departed owner's port (NECP ~14s), not a peer to concede to — so the daemon waits it out (`PREFERRED_PORT_RECLAIM_MS`, polled, 20s cap) and only then falls back, saying which port it wanted and why it could not have it. Two consequences that are easy to get backwards: **`daemon restart` must read posture from the port the daemon is ON and restart on the port it PREFERS** (probing the canonical port blindly found nothing whenever the daemon had fallen back, and "no posture" is indistinguishable from "open posture" — a silent enterprise downgrade); and **anything asserting a fact about "this daemon" may only use a registry-resolved port**, never the blind default-port probe, which on a machine running a second AgentDeck answers with a stranger's daemon. The persisted port needs no argv baking — the LaunchAgent/Task/systemd unit runs `daemon start --foreground` with no `-p` and the daemon re-resolves, which is exactly why the posture flags (a fact that exists only on a command line) must be baked and this one must not.
- **A running daemon carries the identity of the build it started with, because `dist/cli.js` is overwritten in place.** On a source checkout `agentdeck` is a shim onto `bridge/dist/cli.js`, so a daemon started before a rebuild keeps executing bytes that no longer exist on disk while reporting the same pid, port and package version as one started after it — `daemon start` answered "already running" and exited 0 about code the user had just replaced (2026-08-24: a daemon from 04:19 still held 9120 at 19:20). `/health.build` is a 12-char **content** digest of `bridge/dist` + `shared/dist` + `hooks/dist` (`bridge/src/daemon-build-identity.ts`), and three of its properties are load-bearing. It is content, not mtime: `tsc` rewrites every output on every run, so an mtime stamp would restart a healthy daemon for a rebuild that changed nothing. The daemon **captures it once at startup and never recomputes** — a daemon that recomputed would start reporting the newest build on disk the moment someone rebuilt, i.e. exactly the state the field exists to detect. And eviction requires **both** digests to be known and differ: a daemon predating the field sends none, and evicting on no information turns every start into a restart, autostart units included (`--no-upgrade` opts out; the ownership gate still outranks freshness, so another user's stale daemon is left alone). The CLI side keeps the build itself current — `daemon start` / `daemon restart` on a checkout build stale packages and then **re-exec**, because a process that loaded the old `cli.js` and then dynamically imports the new `daemon-server.js` is a mixture nobody chose. Its staleness pre-filter is trusted **one way only**: "no source is newer than its build" safely skips the compiler, while the other direction over-reports (a composite project like `shared` rewrites nothing — not even `.tsbuildinfo` — when a rebase or `touch` moves an mtime), so the real decision is the build digest before vs after. Never build on the autostart path (no terminal ⇒ warn only): a failed build there becomes a `KeepAlive` respawn loop. See [docs/daemon.md § 어떤 빌드가 포트를 잡고 있는가](docs/daemon.md)
- **An ObjC exception is not a Swift error, and `try?` does not catch it.** `JSONSerialization.data(withJSONObject:)` *raises* `NSInvalidArgumentException` for anything that is not a valid top-level JSON container — so `try? JSONSerialization.data(withJSONObject: someAny)` reads as safe and is a `terminate`. A trajectory event whose `input` was a bare String aborted the whole app from a background APME eval task, taking the daemon and every device connection with it (2026-08-06). Any Foundation API documented to *raise* needs a **precondition check**, not a `try?`: `guard JSONSerialization.isValidJSONObject(x)` first (it validates recursively, so it also covers a `[String: Any]` whose leaves are not JSON). Applies wherever untyped `Any`/`[String: Any]` from hooks, gateway payloads or the timeline is serialized — `ApmeScorers`, `ApmeCollector`, `[String: Any].jsonData`; `compactDebugValue` in `DaemonServer.swift` is the pattern to copy
- **External peer async I/O**: 모든 RPC/WS/HTTP `await` 에 timeout 강제 — peer silence (silent drop, dead socket, network glitch) 를 first-class signal 로 처리해야 함 (synthetic error code emit + UI status emit + retry/fallback escalation). race condition 가드는 secondary; timeout 이 먼저. Reference 구현: `apple/AgentDeck/Daemon/Gateway/OpenClawAdapter.swift` 의 `connectRPCResponseTimeoutNanoseconds` + `completeRPCTimeout` + `handleConnectTimeout` 패턴

- **A Claude `SubagentStop` is not always a dispatched worker.** Claude 2.1.261's internal fork queries (prompt suggestions / agent summaries) enter the query loop without `SubagentStart` and still emit `SubagentStop` with an explicitly empty `agent_type`. Live captures produced `wait for it…` and `<no suggestion>` as fake worker completions. Both daemons consume these empty-type stops when no active child matches, without a timeline row, census increment or APME event. Typed orphan stops, absent legacy types and known children still count; never synthesize starts to balance a stop count. `TaskCompleted` is also a one-sided task event, so aggregate APME started/completed counts are not a hook-loss ratio. Ordinary Agent calls were verified marker → HTTP → tracker → APME with matching IDs. Named/background Agent calls can instead create a separate session in 2.1.261 and use `SessionStart`/`Stop`; do not invent a parent link.
- **A folded Codex project row must expose the member waiting on the user.** General activity ranking prefers processing, but that rule inside the fold hid a live `PermissionRequest` behind another processing task in the same project. `foldCodexSessionsForDisplay` and both Swift fold consumers rank awaiting members first and keep that member's ID, question, controls and tool together. A sibling's tool must never overwrite the waiting member's tool.

- **Claude quota authorization is distinct from session connectivity.** The Node daemon alone enables bounded recovery (`claude-usage-recovery.ts`) when a credential expires or the usage endpoint rejects it with 401. Claude Code owns refresh-token rotation and its locks; AgentDeck asks the user's CLI for one tool-free, customization-free Haiku reply (small quota cost, 25s timeout), then re-reads credentials before retrying usage. Never add this subprocess to Swift. A persisted recovery cooldown survives daemon restart (30 min, then 6 h after the third attempt); `AGENTDECK_CLAUDE_USAGE_RECOVERY=0` disables it. `tokenStatus` must explicitly emit `unknown` as well as valid/expired/missing so a previous auth error can be retracted. The app preserves this field and shows the quota failure reason independently of working session hooks. API `Retry-After` is scheduling metadata, never a replacement for the cache's successful `fetchedAt` stamp.

## Design System

Aquarium-tide design system. Spec: [DESIGN.md](DESIGN.md). Source of truth for color/type/spacing tokens: [design/tokens.css](design/tokens.css). **Resource map (which directory is SSOT for what, and which gate stops drift): [design/RESOURCES.md](design/RESOURCES.md)** — bound into the Pages viewer via `catalog.json`; update it in the same commit when a design-resource location or gate changes. Visual reference: [docs/design/Design System.html](docs/design/Design%20System.html). Coverage matrix + lint rules: [docs/design/Design Audit.html](docs/design/Design%20Audit.html).

`agentdeck-design-system/` is the integration and handover layer, and its scope is the **whole designed surface** — visual language, system architecture, hardware and surface specs, product policy, and validation evidence — not just tokens. `catalog.json` binds those canonical Markdown sources to the GitHub Pages viewer (27 documents across Governance / Foundations / Architecture / Specifications / Policy / Validation), `docs/handover.md` defines ownership and evidence levels, and `locales/{ko,ja}/` contains reader translations. English is always canonical. Every catalog document has YAML frontmatter; translations must match the canonical `source_revision`. Validate with `pnpm design-system:check`, build with `pnpm design-system:build`, and never edit generated `dist/design-system/` content.

**Coverage gate — this is what stops doc fragmentation.** `catalog.json` carries a `coverage` block (`scan` directories + `exclusions` map). Every `docs/*.md` must be either cataloged or excluded *with a stated reason*, and `pnpm design-system:check` fails otherwise. **Adding a doc to `docs/` therefore requires a decision in the same commit**: bind it (frontmatter + catalog entry) or write down why it does not belong. Excluding is legitimate — runbooks, credential setup, exploratory studies, and untranslated rationale essays are excluded today. The Asset library is likewise indexed from the real files (brand marks, generated masks, creatures, icons, brand type, product marks, hardware photography, reference surfaces); images ≤1 MiB ship inline, larger ones become pointer cards.

**Markdown gate:** `pnpm docs:check` validates tracked and newly added Markdown local links and anchors, rejects machine-local Markdown links, and requires exactly one H1 in `README.md` and each `docs/**/*.md` file. `.github/workflows/design-system.yml` runs the same checker directly with Node.

**Token bindings** (all mirror `design/tokens.css`; CSS stays canonical — update every mirror in the same commit when CSS tokens change). Seven mirrors are gated: the four language bindings below plus three non-binding copies (`apme-dashboard` HTML, Stream Deck PI `design-tokens.css`, and the Build Health generator `scripts/generate-html-report.py`) that `verify-tokens-sync.py` also checks — the verifier's own footer prints the count, so read it there rather than trusting this sentence:
- Browser JS — `design/tokens.js` (IIFE that exposes `window.DT.{Tide,Ink,Kelp,Coral,Amber,Status,UI,Brand}`). Used by `docs/design/data.js` and Design System.html mockups
- TS — `shared/src/design-tokens.ts` (re-exported via `@agentdeck/shared`). Use for plugin renderers, bridge, hooks
- Swift — `apple/AgentDeck/UI/Common/DesignTokens.swift` (`DesignTokens.Tide.s50` etc.). Existing `StateColors` stays as legacy
- Kotlin — `android/app/src/main/kotlin/dev/agentdeck/ui/theme/DesignTokens.kt` (`DesignTokens.Tide.s50` etc.). Existing `AgentDeckColors` stays as legacy
- Sync verification: `python3 design/verify-tokens-sync.py` — diffs all seven mirrors against tokens.css and exits non-zero on drift

**Rules** (DESIGN.md §10 — enforced by `bash design/lint.sh`):
1. **No raw hex.** Use tokens (`var(--ink-900)`, `DesignTokens.Ink.s900`, etc.). Tokens are the only place hex literals live
2. **No `#fff` / `#000`.** Whites lean toward `--tide-50` sand, blacks toward `--ink-900` aquarium green
3. **Two faces only.** IBM Plex Sans (+ KR/JP) and JetBrains Mono. Never Inter / Roboto / Arial / Fraunces
4. **Status colors are semantic.** `--status-idle` / `--status-processing` / `--status-awaiting` / `--status-error`. Only **amber awaiting** animates; never animate kelp or coral
5. **Marketing vs product UI palette split.** Marketing surfaces (landing, docs, print) use the warm tokens. Product UI (menubar / e-ink / hardware / TTY) may also use the brighter `--ui-*` set. Marketing must NEVER touch `--ui-*`
6. **Brand marks are upstream — do not redraw.** `design/brand/{claudecode,codex,openclaw,opencode,antigravity,kiro}.svg` are the canonical agent marks. Brand colors (#C07058 / #6166E0 / #FF4D4D / #3a3a3a / #5F6368 / #7C3AED) are the only saturated reds/blues allowed, and each one is a `--brand-*` token in `design/tokens.css` — a mark whose colour is quoted in this rule but absent from that file is the gap that shipped Kiro and Antigravity to every renderer while the design-system page could not draw either
7. **Real assets > drawn ones.** Hardware shots and brand marks come from `assets/` and `design/brand/`. Never illustrate hardware with hand-drawn SVG; ship the diagonal-hatch placeholder pattern (`.ad-hatch` / `.ad-placeholder`) when real assets aren't ready

**Dot-matrix brand assets:** Pixoo64/iDotMatrix use the generated 24×24 alpha masks, Timebox Mini uses generated 9×9 masks, and TC001 uses generated 8×8 masks emitted by `pnpm generate-micro-glyphs` from `design/brand/*.svg`. Node, Swift, and ESP32 consumers may add device-specific color, shading, pulse, rails, and particles, but must not replace those masks with hand-drawn agent geometry. Regression tests preserve each official mark's defining negative space. Pixoo64's 64×64 usage HUD identifies Claude/Codex rows with 9×7 silhouettes sampled from those same official masks and gives both the same provider-row grammar: primary/5h and secondary/7d percentage fills plus reset countdowns; do not reintroduce letter keys or provider-specific standalone rails there.

**Migration**: existing UI uses pre-design-system palettes (`StateColors.Hex.*`, `AgentDeckColors.*`). New code reaches for `DesignTokens.*`; migration is incremental, not a sweep. Run `bash design/lint.sh` for the violation count baseline

## App Store build invariants

The macOS app ships through the App Store and must stay **self-contained** under App Review Guidelines 2.5.2 (no bundled interpreters) and 4.2.3 (no routing users to outside installs). The guardrails below are enforced in code, CI, and docs — preserve them on every change.

- **`AGENTDECK_APP_STORE` compile flag** is set on the macOS target in `apple/project.yml`. macOS == App Store; the legacy non-App-Store macOS GUI build is no longer maintained. The flag is retained as a defense-in-depth gate, but the macOS source tree itself contains no `Process()`, `/bin/sh`, `osascript`, `.command` script writer, or external-CLI probe (`security`, `sqlite3`, `adb`, `openclaw`, `whisper-cli`) — those code paths were removed on 2026-04-19. Do not reintroduce subprocess paths under any guard; route new functionality through entitlement-backed APIs or surface it as a "requires desktop bridge" capability gated on `DaemonService.isUsingExternalDaemon`.
- **No companion-install prompts.** App-Store-reachable UI (Setup card, Settings, menubar, alerts) must not tell the user to install, register, or launch a companion binary. Setup card copy is identical regardless of whether an `agentdeck` CLI exists on disk — differentiating based on external state is an App Review 4.2.3 red flag. See [apple/AgentDeck/UI/Monitor/SetupNeededCard.swift](apple/AgentDeck/UI/Monitor/SetupNeededCard.swift) for the canonical copy.
- **No session-launch UI in the App Store build.** The previous `Launch Session` entry point was removed on 2026-05-10 across the menubar, dashboard empty-state, and AgentDeckApp Window scenes — App Store builds never spawn Terminal windows, `.command` files, AppleScript prompts, or child processes. Sessions appear automatically once the user starts Claude Code / Codex / OpenCode in their own workspace and the AgentDeck hooks pick them up. `apple/AgentDeck/Daemon/Core/SessionLauncher.swift::showAppStoreLaunchInfo` remains as defense-in-depth (NSAlert-only path, no callers in shipped UI).
- **CI verifier**: `apple/scripts/verify-appstore-archive.sh` runs after the macOS archive step and fails the build if the shipped `.app` Mach-O contains any forbidden subprocess path string or any bundled executable besides the signed AgentDeck binary itself. Run it locally before releasing: `bash apple/scripts/verify-appstore-archive.sh $PATH_TO_APP`.
- **Feature matrix is canonical**: [docs/appstore-feature-matrix.md](docs/appstore-feature-matrix.md) is the one place that records which features are in the App Store build vs. only the terminal-managed daemon. New features land in the table before any implementation touches the App Store target.
- **Progressive enhancement on `isUsingExternalDaemon`**: capabilities that depend on the separately-installed Node.js daemon (Claude subscription quota gauges, ADB-tier device previews, Android/TC001 topology rows) render only when `DaemonService.isUsingExternalDaemon` is true. When false, the relevant UI sections are hidden — never replaced with a "sandbox limitation" notice — so the standalone app reads as feature-complete instead of broken.
- **A release step marked "manual" is an interactive portal, not a user-only task, and CI green is not "released."** Store submission has no API, so RELEASING.md calls it manual — that describes the missing API, not a missing capability: portals take a signed-in browser and browser automation is available here (the tools are often **deferred**, so `ToolSearch` for `mcp__claude-in-chrome__*` before concluding they are absent). Read portal state freely (Play review status, ASC builds and submission readiness, Maker/Ulanzi status); ask before pressing anything that changes external state. And keep the five states apart — CI succeeded / artifact exists / uploaded / submitted / live — reporting one you did not measure is how a build sitting in a portal gets called a release (2026-08-09). See [RELEASING.md § A release has five states](RELEASING.md)
- **A GitHub Release body is rendered from `CHANGELOG.md`, never hand-written into a workflow.** All six release workflows used to hardcode a static `body:` — the same install blurb every version — so `npm-v1.0.21` published 18 lines that never said what changed, and the round that shipped Kiro observation across five channels announced it nowhere a user could read (2026-08-19). `scripts/release-notes.mjs` resolves a delivery tag to its CHANGELOG section and appends the channel's install text from `.github/release-notes/<channel>.md` (ESP32 passes its artifact-rendered board table via `--template`, since a table built from what actually compiled cannot be a checked-in file). Heading format is `## <YYYY-MM-DD> — <Channel> <version>`, and one heading names every channel when a round is cut across several — which is what a simultaneous cut is, since all five tags then point at one commit. **There is deliberately no bare-version fallback**: the channels stopped sharing a patch number, so `## 1.0.7` was npm's on 2026-08-06 while Apple reached 1.0.7 on 2026-08-18 with unrelated content, and publishing one channel's notes under another's tag is worse than publishing none. `verify-release-version.mjs` fails on a missing entry as the **first** step of every release workflow, before anything is built, published or tagged — the procedure text alone ("update user-facing release notes") had been in RELEASING.md the whole time and was skipped without consequence. Backfilling history is out of scope by rule: versions that shipped without notes are listed as *Known gaps* rather than reconstructed, because a plausible sentence derived from a commit log is a release note nobody measured. Gate: `scripts/__tests__/release-notes.test.ts`
- **Review notes**: [apple/APP_REVIEW_NOTES.md](apple/APP_REVIEW_NOTES.md) is the text that ships to the reviewer — its claims ("does not spawn any subprocess", "no home-relative-path entitlement", "local WebSocket only accepts same-machine + paired iOS companion") must stay factually correct. Update both the code and this doc when touching anything in that surface area.

## Worktree 자동 정리 (workmux)

현재 작업 경로(`pwd`)가 `__worktrees` 를 포함하면 workmux worktree 안에서 작업 중인 것이다.
이 경우 **작업이 완전히 끝났을 때 (모든 서브에이전트/teammate 완료 포함)** 다음을 실행한다:
